### 공유할만한 인사이트

#### 1. OS의 고유 DNA는 본인 직업 본능에서 나온다

내 OS 청사진의 핵심 DNA는 "정보를 보는 사람에 따라 디테일을 다르게 보여주는 것 (본인용 / 외부용 분리)"인데, 이건 마케터로서 매일 하는 일(메시지 압축, 대상별 톤 조정)이 무의식적으로 OS 설계에 들어온 결과였다. 인터뷰 도중 Claude가 짚어줘서 처음 인지함. → 본인 직업 본능을 OS 부품 설계에 의식적으로 활용하면 자연스럽게 차별화된다.

#### 2. 통점은 (a) 시동 / (b) 집중 / (c) 정리·전달 셋 중 어디가 비싼지로 좁힌다

내 경우 답은 압도적으로 (c). 이걸 좁히는 순간 부품 우선순위가 명확해졌다. "캡처를 자동화하는 도구"보다 "사후 정리·통합을 자동화하는 도구"가 나에게 더 효과 큼.

#### 3. 첫 부품 선택 기준은 효과 크기가 아니라 시간 호흡

처음에 효과 더 큰 #2(통합 대시보드)와 효과 중간인 #3(work-helper) 사이에서 갈등. 결국 결정 기준은 "이번 주 안에 손에 쥘 수 있느냐". 효과보다 시간 호흡이 우선.

#### 4. AI 활용에 대한 관점 전환 — "0에서 시나리오 짜기"가 아니라 "체크리스트 빠짐 방지"

처음엔 "AI한테 컨텍스트 다 설명하느니 내가 직접 짜는 게 빠르다"는 회의감이 컸다. 풀린 답: 머릿속 80%를 받아서 빠진 20%를 채워주는 도구. 0에서 짜는 게 아님. + 컨텍스트는 한 번 적어두면 재사용. + AI가 직접 grep으로 검색해서 알아냄.

#### 5. 부트캠프 의도 추측 X — 예시·README 직접 확인이 빠르다

"PRD(C 형태)가 권장일 것"이라고 추측했다가, 부트캠프 예시 폴더(`examples/content-creator-weekly-review/`)를 직접 보니 A 스킬 형태였다. 짐작에 시간 쓰는 대신 예시 한 번 보는 게 1분 만에 끝. → 앞으로 부트캠프 과제 헤맬 때마다 examples/ 폴더 우선 확인.

#### 6. 첫 부품을 한 번 폐기하고 다시 만든 게 미션 1의 진짜 가치

work-helper → cycle-os 피벗 자체가 가장 큰 학습. "최종 구현 결과물"을 내 손으로 보여줄 수 있느냐를 기준으로 잡으니, 회사 자료가 필요한 work-helper와 본인 데이터만 있으면 되는 cycle-os 사이 차이가 명확해졌다. 부품 선택 기준 하나가 더 추가됨: "지금 이 환경에서 검증 가능한가."

9. **첫 데이터 누적**: 5/9 수면 02:00→09:30, 점심 중식, 저녁 냉면·육전·불고기, 운동·명상·일기 ✗
#### 삽질 포인트
- **1421 대사 루틴**: 여성의 주기에 1421 대사 루틴 개념을 접목하려고 했으나 검색해도 정확한 정의 안 나옴 (인스타 영상 출처). 결과적으로 의학적 근거 있는 4 Pillars로 전환 = 오히려 시스템 정확도 ↑

- **"v2"라고 잘못 명명**: cycle-os v0.1이 아직 1주차에 만들어지는 중인데 "v2 작업"이라 부른 게 어색. 1주차 통합 빌드로 정정

- **"이 세션으로 돌아와야"라는 오해**: 데스크톱 Claude Code는 새 세션에서도 같은 SKILL이 자동 발동. 세션 연속성 ≠ 데이터 연속성

- **모바일 입력 욕심**: 1주차에 인프라 셋업까지 하면 빡셈. 차주로 미루고, 데이터 며칠 쌓아본 뒤 정말 필요한지 검증
### 공유할만한 인사이트
#### 1. 벤치마크는 "도메인"이 아니라 "패턴"을 빌리는 것

처음엔 Diet_OS의 다이어트 도메인을 따라가야 하나 망설였음. 결국 사이클·웰니스 도메인은 유지한 채 영상의 패턴(측정→추세→코칭 / 1파일 진화 / 측정 강제)만 가져왔음. **레퍼런스 OS의 도메인이 본인 일과 안 맞아도, 패턴만 추출하면 자기 도메인에 이식 가능.** 영상 봐서 "이거 내 일이 아니네" 하고 끄지 말고, "여기서 내가 훔칠 패턴이 뭐지?"로 보면 활용 폭이 넓어진다.

#### 2. 마케터(비개발자)도 시각 대시보드를 빌드할 수 있다

Diet_OS는 48,000줄 풀 웹앱. 처음엔 "나는 코드 못 짜는데" 했음. 근데 **SKILL.md 1파일 + HTML 1파일 + Claude Code가 매번 HTML 통째로 재생성**하는 *사이드카 패턴(메인 시스템 옆에 보조 파트를 따로 두고, 메인이 보조를 갱신하는 구조)*이면 풀 웹앱·서버·DB·React 다 필요 없음. 풀 빌드 부담돼서 시작 못 하고 있으면 이 패턴이 진입 장벽을 낮춰줄 것.

#### 3. "그냥 빌드"보다 brainstorming → spec → plan → build 4단계가 훨씬 빠르다

처음엔 "그냥 만들면 되지" 생각. superpowers 플러그인의 **brainstorming 스킬**이 한 번에 하나씩 결정 끌어내고 → **design doc**이 결정 로그를 남기고 → **writing-plans 스킬**이 task 단위로 끊어줌 → 빌드. 느려 보이지만 빠뜨리는 게 적고, **미래의 나에게 공유 가능한 자료**가 자동으로 남는다. Claude Code 자동 스킬이라 별도 셋업 X. 같은 스킬 호출하면 같은 흐름. 사실 직접 호출하지 않았는데, 클로드가 알아서 브레인스토밍 스킬을 작동해줬다.

#### 4. "원래 계획"에 매달리지 말 것 — 갈아엎기도 빌드의 일부

1421 대사 루틴 정확한 정의를 못 찾았을 때 거기서 멈출 수 있었음. 대신 의학적 합리성 있는 4 Pillars 프레임으로 전환 → 시스템 정확도 ↑. **AI랑 작업하면 자주 일어남: "안 됐다"가 아니라 "더 좋은 길 발견"**. 첫 계획 70% 살리고 30% 갈아엎는 게 정상이라고 받아들이면 멈춤이 줄어든다.

#### 5. 세션 연속성 ≠ 데이터 연속성 (Claude Code 작은 깨달음)

빌드 중간에 "이 세션으로 돌아와서 입력해야 하나?" 헷갈렸음. 답은 NO. **새 세션이어도 같은 SKILL.md가 자동 발동되고, 데이터는 파일에 누적**되어 있음. Claude Code의 핵심 작동 원리인데 처음엔 헷갈리기 쉬움.
