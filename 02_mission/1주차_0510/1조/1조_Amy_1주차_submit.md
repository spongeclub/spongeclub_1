# 1주차 과제 — Amy

## 미션 1: claude code 로 인터뷰스킬 사용해서 인터뷰 까지 진행

### Summary

기획안을 넣으면 기능정의서·화면정의서가 나오는 Claude 스킬을 만들고 설치한 뒤, 실제 업무 기획안으로 테스트까지 마쳤다

---

### 최종 구현 결과물

**만들어진 것 2: `srs-to-sds` Claude 스킬**

Claude에게 기획안을 붙여넣으면 → SRS 초안 → 기능정의서 → 화면정의서까지 단계별로 만들어주는 스킬. `~/.claude/skills/`에 설치되어 있어서 "기능정의서 뽑아줘"라고 말하면 바로 발동된다.

**만들어진 것 3: 실제 SDS 문서**

테스트로 넣은 기획안: _OKR-WBS-업무일지 연동 프로젝트 관리 시스템_  
결과물: SRS 요약 + 기능정의서 14개 + 화면정의서 19개짜리 마크다운 1장

---

### 과정 (타임라인별 + 삽질)

**① 스킬 설치 확인 (5분)**

GitHub에서 `os-interview` 스킬 레포를 찾았고, README 보니 `~/.claude/skills/`에 복사하면 된다고 해서 했더니 — 이미 설치되어 있었다. 그냥 바로 시작.

**② os-interview 스킬 발동 → 인터뷰 (40분)**

"내 OS 만들고 싶어"라고 입력했더니 스킬이 켜졌다.

처음엔 단순하게 답했다. 일 3가지 나열하고, 힘든 거 말하고. 그런데 Claude가 그냥 받아 적지 않고 계속 되물었다. "그 작업의 어느 부분이 비용이에요? 시작 전? 진행 중? 끝낸 뒤?" 이런 식으로. 그러다 보니 내가 몰랐던 걸 발견했다 — 나는 내용을 쓰는 게 힘든 게 아니라, **문서를 시작하는 것**과 **다 쓴 걸 팀 양식으로 옮기는 것**이 진짜 비용이었다.

이상향 질문에서 나온 한 문장이 OS 선언문이 됐다.

**③ 삽질: Plan Mode가 중간에 껴들었다**

인터뷰 도중 Claude Code가 Plan Mode로 들어가서 파일을 저장하려 하면 계속 막혔다. 인터뷰는 잘 되고 있는데 저장이 안 되는 상황. ExitPlanMode를 호출해서 해결했는데, 이게 왜 켜졌는지는 아직도 잘 모르겠다.

**④ srs-to-sds 스킬 5개 질문으로 완성 (10분)**

인터뷰 결과로 만들 부품이 정해지니까, 스킬 만드는 건 빨랐다. Claude가 5개 질문만 물어봤다:

- 이 스킬 한 줄 정체성이 뭐예요?
- 어떤 말 하면 발동돼야 해요?
- 몇 단계로 흘러요?
- 각 단계 핵심 질문은?
- 결과물 형태는?

다 답하니까 SKILL.md 파일이 나왔고, `~/.claude/skills/srs-to-sds/`에 설치됐다.

**⑤ 실제 기획안으로 테스트 (15분)**

예시 데이터 쓰기 싫어서 진짜 업무 기획안을 붙여넣었다. 회사 SRS 양식도 함께 넣었더니 — 그 양식 그대로 SRS가 나오고, 기능정의서, 화면정의서까지 나왔다. 실무에서 쓸 수 있는 수준이었다.

---

### 공유할만한 인사이트

**스킬이 스킬을 낳는다**

os-interview 스킬을 쓰면 인터뷰 결과로 다음 스킬이 나온다. 이번에 srs-to-sds가 나왔고, 청사진에는 이미 다음 부품 2개가 적혀 있다. 한 번 돌리면 다음에 뭘 만들지가 보인다.

**통점은 "뭐가 힘들어요?"로 안 나온다**

"힘든 거 말해봐"라고 물으면 뭉뚱그려 답하게 된다. 그런데 "시작 전이 힘들어요, 진행 중이 힘들어요, 끝낸 뒤가 힘들어요 — 셋 중 하나만 고르면?"이라고 물으니까 비로소 정확하게 보였다. 질문의 형태가 답의 정밀도를 결정한다.

**코딩 없이 오늘 만든 도구를 오늘 썼다**

Claude 스킬(A형)은 파일 하나다. 만들고 설치하고 발동까지 한 세션에 끝났다. 뭔가를 만들어서 실제로 쓰는 데까지 걸리는 마찰이 거의 없었다.

### 과정 (타임라인별 + 삽질)

**1단계: 목표 탐색 (인터뷰)**

- 처음엔 "유튜브에서 개인 OS 벤치마킹 하고 싶다"로 시작
- 근데 아이디어가 없다 → 파고들었더니 진짜 문제는 "내가 뭘 하고 싶은지 모름"
- "2시간이 생기면 뭐 할 것 같아?" → "내가 뭘 할 수 있는지 찾아볼 것 같아"
- "잘하는 거 뭐야?" → **로컬 지도/맛집/공간 탐색**이 나옴
- 이미 친구들한테 검증받고 있었음 ("거기 진짜 좋더라")
- **첫 번째 할 일 결정**: 네이버 지도 즐겨찾기에 추천할 때마다 저장하기

**2단계: 앱 아이디어 → 설계**

- "병렬로 여러 개 처리하는 연습 웹앱 만들어볼까" → B안(실제 관리 도구)으로 방향 결정
- 내 삶 트랙 기반의 일정 관리: 업무, 셀피쉬클럽, 사이드프로젝트
- 핵심 니즈: "전체적으로 잘 가고 있는지 감이 없음"
- 유튜브 영상 레퍼런스 추가 → 마중물 개념 반영

**3단계: 반복 개선 (v1→v5)**

- v1: 기본 칸반 3개 + 신호등 + 마중물
- v2: 목표 발견 인터뷰 모달 + 단계 쪼개기 가이드 추가
- v3: 트랙 자유 추가/삭제/수정 (칸반 동적화)
- v4: 컨디션 4종 → 8종으로 확장 (아픔, 우울함, 불안함, 번아웃 추가) + 활동 로그
- v5: 데일리 체크 탭 전체 추가 (스프레드시트 레퍼런스 기반)

**삽질 포인트**

- localStorage key를 버전업마다 바꿔야 했음 (v1~v5), 이전 데이터 충돌 방지
- 탭 전환 시 데일리 탭 렌더를 `switchTab` 시점에 호출하도록 구조 변경 필요
- 과거 행 수정 시 "오늘 저장" 버튼 onclick을 동적으로 교체하는 방식 사용 (약간 hacky)

### 공유할만한 인사이트

**1. 시스템보다 방향이 먼저다**  
"할 일 관리가 안 된다"는 말의 진짜 원인은 툴이 아니었음. 목표가 없으면 어떤 시스템도 돌아가지 않는다. 인터뷰로 파고들어서 강점을 먼저 발견한 게 핵심.

**2. 마중물 원칙은 앱 설계에도 통한다**  
처음부터 완성본을 만들려고 하지 않고, 대화에서 발견한 것부터 시작하여 완성본을 만드는 것이 중요함
