## 미션 1: claude code 로 인터뷰스킬 사용해서 인터뷰 까지 진행

### Summary

`/os-interview` 슬래시 커맨드로 6단계 OS 인터뷰 스킬을 발동, **20~30분 만에** OS 청사진 1장 + 즉시 사용 가능한 첫 부품(스킬) 1개를 손에 쥠.

가장 큰 발견 한 줄로 압축:

> **"우선순위를 정한다고 생각했는데, 사실 '걸리는 시간'은 고려하지 못하고 있었다."**

OS 선언문도 박힘:

> **나는 '결정'만 하고, 나머지(아카이빙 + 형식 변환 + 도구 간 동기화)는 시스템이 한다.**

### 과정 (타임라인별 + 삽질)

**총 20~30분, 3 Phase / 6 Step**

**Phase 1 · 청사진 (사고 파트너 톤)**

|Step|핵심 흐름|발견|
|---|---|---|
|1 풍경|직업 라벨 4개 → 동사 3개 → "기획→만들기→배포" 같은 골격|"무언가를 만들어 사람한테 전달하는 일" 한 문장으로 압축|
|2 통점|워크샵 셋업 + 캐러셀 발행 두 장면 → (b) 컨텍스트 스위칭 + (c) 노가다 **둘 다**|본체 1개를 채널 5~7곳에 손으로 변주하는 두 얼굴|
|3 이상향|"90% 자동화된 아침" 그림 그리기 → 4구역(아침/콘텐츠/워크샵/커리큘럼)|**OS 선언문 확정**|
|4 부품 매핑|4구역 → 부품 후보 6개로 분해|(b) 결정 보조 + (c) 출력 생성이 가장 절실|

**Phase 2 · 첫 부품 결정 (전환 톤)**

|Step|흐름|
|---|---|
|5(a) 부품|① 모닝 브리프 vs ④ 워크샵 셋업 갈림 → "**매일 검증 가능 + 선언문 직결**" 기준으로 ①|
|5(b) 형태|A(스킬) / B(플러그인) / C(프로덕트) → **A 스킬** (가장 가벼움)|

**Phase 3 · 결과물 (효율 톤)**

4가지 빠른 질문 → 답 → 두 파일 동시 출력.

**삽질·머뭇거린 지점**

- Step 1에서 "동사로 좁혀달라"는 요청에 처음엔 명사형(교육 커리큘럼 제작 등)으로 다시 답함. 한 번 더 좁히는 가설을 받고 나서야 골격이 압축됨.
- Step 4에서 ⑥ 커리큘럼 라이브러리가 자동으로 후보에서 빠진 걸 보고 "왜 없어졌어?"라고 의문 — (a) 입력 처리 묶음을 본인이 의식적으로 후순위로 분류했음을 그제야 인지.
- Step 5에서 ① vs ④ 갈림. "다 안 되면 슬플 것"과 "자주 쓸 것"의 답이 다르게 나와 한 단계 더 좁히는 가설이 필요했음.

→ 큰 막힘은 없었지만, **답이 한 번에 안 나오고 가설을 받아 좁히는 사이클이 2~3번** 도는 게 인터뷰의 자연스러운 결.

---

### 공유할만한 인사이트

**1. 우선순위 ≠ 시간 배분**  
나름 우선순위를 정한다고 생각하고 있었는데, **'걸리는 시간'은 고려하지 못하고 있었음**. 모닝 브리프의 출력 형식을 "시간순 타임라인"으로 자연스럽게 고른 게 그 증거. 우선순위 리스트만으론 부족하고, 그게 시간 슬롯에 박혀야 진짜 OS가 굴러감.

**2. "나도 모르는 내가 필요한 부분"이 드러남**  
혼자 생각만 했으면 그냥 "워크샵 운영 자동화부터 만들어야지"였을 텐데, 인터뷰가 가설을 던져주니까 ① 모닝 브리프가 더 먼저 와야 한다는 게 보임. **외부에서 가설을 받는 것 자체가 OS 설계의 첫 부품**이었던 셈.

**3. 직업 라벨 4개의 본질은 1개**  
PM / 마케터 / 커리큘럼 / AI Creator — 라벨은 4개지만 동사로 풀면 "기획→만들기→배포"의 같은 골격. 그래서 OS 선언문이 4개가 아니라 1개로 충분히 박힘. 자기 정체성을 라벨 대신 동사로 정의하면 시스템 설계가 훨씬 단순해짐.

**4. 첫 부품은 임팩트보다 빈도**  
④ 워크샵 셋업이 한 건당 임팩트는 더 큰데, 첫 부품으로는 ① 모닝 브리프가 맞다는 결론. 이유: **매일 검증 가능 + OS 위에 살고 있는 감각을 매일 느낌**. 한 달에 한 번 켜는 강력한 도구보다, 매일 켜는 가벼운 도구가 첫 부품의 자격.

**5. OS = 스킬 + MCP + cron 합주**  
스킬 하나만으로는 안 굴러감. 자동 발동(cron) + 데이터 연결(MCP)이 같이 와야 "내가 결정만 하는" 그림이 진짜로 작동. 스킬은 OS의 시작이지 끝이 아님.

## 전체 제작 과정

- **브레인스토밍 → 요구사항 구체화**: 콘텐츠 마케터로서의 페인포인트(노션/스프레드시트에 자료 흩어짐)를 파악하고, AskUserQuestion으로 한 질문씩 사용자/기능/채널/기술 방향을 좁혀나감. 3가지 접근법(아카이빙 중심 / 기획 중심 / AI 중심) 제안 후 A+C 혼합으로 결정.
- **와이어프레임 목업**
    - **디자인 시스템 적용**: 비주얼 컴패니언(로컬 HTML 서버)으로 목업을 브라우저에서 실시간 확인하며 피드백 반영. Noto Sans KR → Nunito 폰트 변경, 모바일 → 데스크탑 전환, Charcoal/Red/Sage 컬러 시스템 적용까지 총 5번 반복 수정.
- **실제 구현 → 배포**: Next.js 프로젝트 생성, API Route(URL 크롤링 + Gemini AI 요약/태그 추출), 사이드바/탑바/카드그리드/모달 컴포넌트 구현. 노션 MCP로 실제 "AI 자료 모음" DB에서 18개 자료를 가져와 시드 데이터로 반영. Vercel 배포 후 커스텀 도메인(dani-content-hub) 설정. 아이디어 전환 기능(채널 선택 + 참고자료 연결)까지 구현.
### 공유할만한 인사이트
- **브레인스토밍 스킬**
    - 처음부터 코드를 쓰지 않고, 한 질문씩 요구사항을 좁히고 → 접근법 비교 → 디자인 확인 → 스펙 문서화 순서로 진행하니 "내가 뭘 만들고 싶은지"가 명확해짐.
    - 기술을 모르는 마케터도 의사결정에 자연스럽게 참여할 수 있었음.
- **노션 MCP 연동의 가능성**
    - Claude Code의 Notion MCP 도구로 실제 워크스페이스 DB를 바로 읽어와서 웹 서비스에 반영할 수 있었음.
    - "노션 데이터가 콘텐츠 허브에 보이는" 경험을 빠르게 프로토타이핑할 수 있다는 점이 강력했음.
    - `/schedule`로 매시간 자동 동기화까지 설정.
