# 1주차 과제 — 초보자(명근)

## 미션 1: claude code 로 인터뷰스킬 사용해서 인터뷰 까지 진행

### Summary

`os-interview-skill`을 Claude Code에 설치하고 6단계 인터뷰를 완주했다.
인터뷰 결과로 **OS 청사진 1장 + 아침 브리핑 플러그인(v0.1)**이 만들어졌다.

**OS 선언문**: "나는 의사결정만 하고, 나머지는 시스템이 한다."

### 최종 구현 결과물

**생성된 파일:**
- `os-blueprint.md` — OS 청사진 (현황·통점·이상향·부품 로드맵)
- `morning-brief-plugin/` — Claude Code 플러그인 폴더
  - `plugin.json` — 플러그인 메타데이터
  - `commands/morning-brief.md` — `/morning-brief` 슬래시 커맨드
  - `hooks/session-start.md` — 세션 시작 시 자동 브리핑 훅
  - `data/tracking-template.md` — 업무·프로젝트·이메일 트래킹 시트 템플릿
  - `README.md` — 설치 및 사용법

**플러그인 기능 요약:**

```
트래킹 시트 (tracking.md)
        ↓
/morning-brief 실행 (또는 Claude Code 시작 시 자동)
        ↓
오늘 마감 업무 + 진행 프로젝트 + 팔로우업 이메일 + 리스크 항목
        ↓
한눈에 보이는 브리핑 출력 → 필요시 이메일 초안·리스크 보고서로 연결
```

### 과정 (타임라인별 + 삽질)

1. **스킬 설치** — `~/.claude/skills/`에 `os-interview` 레포를 클론. Windows에서는 `ln -s`(symlink) 대신 `git clone`으로 직접 설치해야 했다.

2. **인터뷰 진행 (Phase 1~2)** — 6단계 중 핵심인 Step 3(이상향)에서 처음 답이 짧아서 한 번 더 파고드는 과정이 있었다. "나는 의사결정만 하고, 나머지는 시스템이 한다"는 한 문장이 나오기까지 풍경→통점→이상향 순서로 차근차근 도출됐다.

3. **형태 선택** — 처음엔 A(스킬)가 더 가볍다고 안내받았지만, 자동 트리거와 외부 시트 연동이 필요해서 B(플러그인)로 결정. 나중에 Google Sheets MCP를 붙이는 업그레이드 경로도 설계해뒀다.

4. **플러그인 설계** — 로컬 마크다운 파일을 트래킹 시트로 쓰는 방식 선택. API 키 없이 바로 시작 가능하고, Obsidian에서도 편집할 수 있어서 실용적.

### 공유할만한 인사이트

- **인터뷰 스킬의 진짜 가치는 "이미 알던 걸 꺼내주는 것"** — Step 3(이상향) 질문 전까지는 막연하게 "효율화"라는 단어만 떠올랐는데, 인터뷰를 통해 "아침에 판단 목록이 준비돼 있어야 한다"는 구체적인 그림이 나왔다.

- **리스크 트래킹 섹션이 핵심** — 평소 리스크를 제기해도 묻히는 패턴이 반복됐는데, 이걸 시스템으로 기록·추적하는 구조를 만들면 "나는 말했다"는 게 남는다. 이게 단순 브리핑보다 훨씬 중요한 부분.

- **처음 부품은 가볍게** — 플러그인도 일단 로컬 파일 기반으로 시작하고, 안정되면 클라우드(Google Sheets)로 업그레이드하는 방식이 현실적이다.

## 미션 2: 따라해보고 싶은 개인/업무/삶 OS 따라서 만들어보기 - SNS(유튜브 등) 에서 찾아 벤치마킹 해오기

### Summary

안드레 카파시(Andrej Karpathy)의 **LLM Wiki** 개념을 벤치마킹했다.
AI를 실질적인 에이전트로 활용하려면 **잘 정리된 데이터(컨텍스트)** 가 먼저라는 걸 깨달았고, Obsidian 마크다운으로 개인 위키를 구성하는 중이다.

참고 링크: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

### 최종 구현 결과물

- Obsidian 마크다운 파일 기반 개인 위키 구성 시작 (진행 중)
- 회사 업무용 위키는 아직 구성 전 — 데이터 정리 방식 설계 단계

### 과정 (타임라인별 + 삽질)

카파시의 LLM Wiki를 접하고 핵심 구조를 파악했다:

```
원본 출처 (불변)
    ↓ LLM이 합성
위키 페이지 (누적·갱신)
    ↓
질문 → 위키 검색 → 답변
```

기존 RAG와의 차이: RAG는 매 쿼리마다 재검색하지만, LLM Wiki는 **합성이 한 번만 일어나고 지식이 쌓인다**. 이 "compounding knowledge" 개념이 인상적이었다.

현재 Obsidian으로 개인 위키를 만들고 있는데, 데이터 정리가 먼저라는 걸 실감하는 중.

### 공유할만한 인사이트

**핵심 인사이트 2가지:**

1. **방향(목표)을 정해줘도 하니스(harness)가 필요하다** — AI에게 "이렇게 해"라고 방향만 주는 것으론 부족하다. AI가 실제로 동작할 수 있는 구조적 틀(harness)이 있어야 한다. 미션 1에서 만든 `morning-brief-plugin`도 결국 이 하니스를 만드는 작업이었다.

2. **데이터가 잘 정리되어 있어야 한다** — AI를 내 에이전트로 쓰려면 컨텍스트가 필수다. 컨텍스트는 결국 잘 정리된 데이터에서 나온다. 지금 Obsidian 위키를 만드는 이유가 바로 이것 — 나의 업무·생각·기록이 AI가 읽을 수 있는 형태로 쌓여야 진짜 자동화가 가능하다.
