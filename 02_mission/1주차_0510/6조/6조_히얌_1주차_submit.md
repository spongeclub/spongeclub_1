### 공유할만한 인사이트
**1. 인터뷰의 R톤(사고 파트너) vs Q톤(발판형) 분리가 진짜 가치를 만든다**
- 단순 질문→답 수집이 아니라, _답 듣고 가설 던지고 검증받는_ 형태
- "그러면 X가 핵심 같은데, 맞아요?" / "이건 사실 Y의 다른 표현 아닐까요?"
- 사용자가 _본인도 몰랐던 구조_를 발견하게 됨 (예: "정리 사이클에 샌드위치된 본 작업")
**2. 형태(form) 결정은 보통 2~3번 피벗한다 — 부담스러워 말 것**
- 첫 형태 결정은 _표면적 요구_만 반영 → 사용자가 "여러 사람", "비용 0원", "API X" 같은 진짜 제약을 차츰 드러냄
- 첫 결정에 매몰되면 나중에 더 큰 비용
- 피벗 시 _기존 자산을 폐기/축소_하는 결정도 같이 검토 (안 그러면 낙오된 산출물이 누적됨)
**3. "추가 비용 0원"은 사용자 보유 자산을 발견하면 자주 가능하다**
- 처음엔 "Anthropic API + 호스팅 + 인프라" 로 자연스럽게 디자인
- _회사 Workspace Gemini, 본인 Claude Code 구독, 사내 GCP_ 같은 이미 가지고 있는 자산을 발견하면 비용 모델이 무너지고 새로 짤 수 있음
- "자동 드래프팅 = 사용자 손의 LLM에 위임" 패턴이 의외로 잘 통함
**4. 군더더기 제거는 _정보 중복_부터 본다**
- 같은 정보를 두 번 입력? 두 번 표시? 두 번 전달?
- 사용자가 측면패널 Gemini를 쓴다 → Gemini는 thread를 _이미 보고 있음_ → 봇이 thread 인용하면 중복
- 사용자가 매일 정형화된 회신을 보낸다 → 본인 직전 메시지가 이미 매체별 템플릿 → 외부 시트로 관리하면 중복
- **외부에서 가져올 거 없이 thread 자체에 있는 자산을 쓰는** 패턴이 강력
**5. 자동화 100%를 고집하지 말 것 — 사용자 손에 남기는 단계가 핵심 가치**
- 봇이 LLM 안 쓰니 _드래프팅 한 단계는 사용자가 직접_ (측면패널 Gemini 호출)
- 대신 봇이 thread 검색·정리·태깅·프롬프트 빌드까지 해줘서 _수기 정리 비용은 사라짐_
- "전부 자동" 보다 "부수 사이클을 시스템에, 본 작업은 사람에" 가 OS 선언문과 정렬됨
**6. 메모리는 _제약_과 _맥락_만 적는다 — 코드/경로는 적지 않는다**
- `user_role.md`: 직업, 일 흐름 사이클 → 다음 인터뷰에서 Phase 1 짧게 가능
- `feedback_no_paid_apis.md`: 유료 API 제약 → 다음 부품 디자인 시 자동 적용
- 코드/파일 경로는 변경되면 stale → 메모리에서 빠짐 (재구성은 PRD/blueprint 보면 됨)
**7. PRD를 single source of truth로 만들면 정리가 쉬워진다**
- 인터뷰 산출물(SKILL/스킬 폴더/메모/blueprint) 여러 곳에 정보 흩어지기 쉬움
- 한 곳(PRD)에 다 흡수하면, 나머지를 정리할 때 _PRD에 있나?_ 만 체크해서 의사결정 가능
- "혹시 모르니 남겨두자" 가 가장 흔한 군더더기 패턴 — PRD에 있으면 과감히 폐기

### 공유할만한 인사이트
### 1. 사용자 발화의 "표현"과 "정체성"을 구분해야
"글감/구조 짜기는 익숙" ≠ "나는 콘텐츠 제작자". 발화 단어를 정체성으로 점프하지 말 것. **한 번 더 가설로 던져서 검증** 받자. 🎯
### 2. 워너비의 "도구"를 그대로 쓰는 것이 가장 직접적인 모방
마담초이 = 노션 → 나도 노션. 도구가 같으면 템플릿 그대로 흡수 가능. **AI를 메인으로 쓰더라도 홈 그라운드는 매일 만지는 도구여야** 한다.
### 3. AI(클로드)는 메인 도구가 아니다 — 역할 분리
- 클로드 = **인터뷰형/생성형/일회성** 작업 (라이프 OS 인터뷰, 의사결정 정리, 부품 제작)
- 노션 = **매일 보는 자료 + 누적되는 자료**
- 둘 다 도구지만 역할이 다름. 매일 보는 걸 클로드 안에 두면 접근성 박살.
### 4. OS 부품 빌딩 순서: 매일 루틴 < 인생 맥락 정리
"매일 회고 스킬"부터 만들면 운영 방향이 흔들림 — 카테고리/우선순위가 없으니 회고 대상이 모호해진다.
> **순서**: ① 기초공사(맥락/카테고리/우선순위) → ② 회고/리뷰 → ③ 매일 루틴 → ④ 영역별 자동화
### 5. YouTube transcript는 WebFetch로 못 따냄
채널/영상 페이지 모두 footer만 추출됨. 우회 경로: `youtube-digest` 스킬 / yt-dlp / **사용자가 본 핵심 메시지 1줄 직접 입력**. 영상 정리 부품을 분리 설계하는 게 안전.
### 6. 가설을 빨리 던지고 빨리 깨뜨려라
1차 빌드가 잘못된 가정 셋 위에 있었지만, **피드백 한 번에 셋 다 가시화** → 메모리 3원칙으로 영구 반영. 박살난 가설이 명시적으로 잡혔다는 건 다음 부품에서 같은 실수 안 한다는 뜻. **MVP는 깨지라고 만든다**.
