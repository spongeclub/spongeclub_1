# 1주차 과제 — 이창환

## 미션 1: claude code 로 인터뷰스킬 사용해서 인터뷰 까지 진행

### Summary

Claude Code의 **OS Interview Skill** (`Enable OS interview skill usage`)을 사용해 본인의 일·삶 패턴을 6단계 인터뷰(40~60분)로 진단. 결과로 **개인 OS 선언문 1개 + 부품 카탈로그 9개 + 첫 부품 PRD**까지 한 세션에서 산출. 첫 부품으로는 가장 아픈 통점인 **참관객 CRM 자동화(visitor-crm)** 를 선정.

### 최종 구현 결과물

**OS 선언문 (ζ)**
> 나는 **언제·누구에게·왜를 결정**만 하고, 보내고·합치고·추적하는 건 시스템이 한다.

**산출물 2개**

1. **`os-blueprint.md`** — OS 청사진 (풍경 / 통점 / 이상향 / 부품 후보 9개 / 첫 부품 결정)
2. **`visitor-crm.prd.md`** — 첫 부품 PRD (Why / Who / What / MVP scope / Tech stack / Validation)

**부품 카탈로그 9개** (인터뷰에서 도출)

| # | 부품 | 분류 | 우선순위 |
|---|------|------|---------|
| 1 | **visitor-crm** — 참관객 CRM 자동화 | 입력 처리 | ⭐ 첫 부품 |
| 2~5 | 참가업체 제출 진행률 / 자동 푸시 / 댓글 피드백 / 자체 입력 폼 | (디지털 혁신 본부 영역) | — |
| 6 | 인턴 위임 트리거 자동화 | 결정 보조 | 4순위 |
| 7~9 | 참가업체 홍보 활동 추적 / 효과 측정 / 리워드 산정 ⭐ 모자 ② | 출력 생성 | 3순위 |

**visitor-crm MVP — 한 줄 흐름**
```
자체 홈페이지 구매 → webhook 수신 → Supabase events INSERT
→ 카카오 비즈메시지 발송 → 스티비 DB 동기화 → status = completed
```

### 과정 (타임라인별 + 삽질)

1. **인터뷰 시작** — OS Interview Skill 호출, "지금 풍경"부터 가벼운 톤으로 묘사
2. **두 결 발견** — 회사 안에서 본인이 *마케팅 실행자* + *사내 문제 해결사* 두 갈래라는 걸 인터뷰 중에 자각 (직무 라벨로는 안 보였던 것)
3. **통점 카탈로그** — 참관객 CRM 부재(1차) + 참가업체 관리(2차). 후자는 *디지털 혁신 본부*에서 이미 코드로 만드는 중 → 인터뷰가 "이건 본인 영역 아님"을 명확히 짚어줌 → **중복 투자 회피**
4. **부품 후보 9개 정리** — (a) 입력 처리 / (b) 결정 보조 / (c) 출력 생성으로 묶고 보니 (c) 출력 생성(모자 ②)이 비어있음 = 본인이 가장 잘 할 수 있는 영역
5. **첫 부품 선정 — visitor-crm** — 형태 결정: A 스킬(트리거가 Claude 밖) / B 플러그인(24/7 백그라운드 필요) 부적합 → **C 독립 프로덕트 PRD**로 결정
6. **삽질** — 처음엔 visitor-crm을 *마케팅 실행자*만의 일로 봤는데, 인터뷰 후반에 "이 데이터 구조가 모자 ② 부품(#7~9)에 그대로 재사용된다"는 연결고리를 발견 → 두 결을 이어주는 **첫 다리**로 의미 격상

### 공유할만한 인사이트

1. **"단일 원천에서 N개 포맷·청자·언어로 손으로 펼치기"** — 그로스 사고를 가진 사람한테 가장 아픈 통점 패턴. 본인이 만들어둔 레버리지를 회사 구조가 매번 1배수로 깎아먹는 모양.
2. **인터뷰가 "안 만들어야 할 것"도 짚어준다** — 참가업체 관리 시스템은 디지털 혁신 본부에서 진행 중이니 본인은 *위에 얹는 모자 ②* 만 만들면 됨. 1시간 인터뷰가 6개월 중복 작업을 막아준 셈.
3. **부품 분류로 빈자리가 보인다** — 입력 / 결정 보조 / 출력 생성으로 묶으니 본인이 가장 잘 할 수 있는 묶음(출력 생성)이 비어있음을 발견. 다음 우선순위가 자연스럽게 도출됨.

## 미션 2: 따라해보고 싶은 개인/업무/삶 OS 따라서 만들어보기 - SNS(유튜브 등) 에서 찾아 벤치마킹 해오기

### Summary

**장병준의 AI orchestration 청사진**(`aiground.co.kr/ai-orchestration-guide`)을 벤치마킹해서, 본인의 K-Expo 콘텐츠 운영 워크플로우용 개인 OS인 **`/yt2blog` 슬래시 커맨드 스킬**을 설계·구현. YouTube 영상 1개를 입력하면 K-Expo 톤 인사이트 블로그 마스터 글 1편을 자동 생성. 사용자(본인)는 토픽 선택 게이트 1번에만 개입.

### 최종 구현 결과물

**산출물 3개**

1. **Design Spec**: `2026-05-10-yt2blog-design.md` (322 lines, brainstorming 승인 완료)
2. **Implementation Plan**: `2026-05-10-yt2blog-implementation.md` (task 단위 체크박스)
3. **시범 운영 결과**: `Documents/yt2blog-content/2026-W19-yt-J1Dza2c4spA/` 폴더에 K-뷰티 EU 진출 영상 1편 처리 → `00-transcript.md` / `01-insights.md` / `02-homepage.md` 자동 생성

**아키텍처 (장병준 패턴 적용)**

```
yt2blog (메인 슬래시 커맨드, 오케스트레이터)
├─ yt2blog-transcript-agent.md   (YouTube → transcript)
├─ yt2blog-insight-agent.md      (transcript → 인사이트 + 토픽 3개)
└─ yt2blog-writer-agent.md       (승인 토픽 → K-Expo 톤 마스터 글)
```

**벤치마킹한 핵심 패턴 → 본인 적용**

| 장병준 청사진 | 본인 OS 적용 |
|---|---|
| 단일 거대 프롬프트 X, **역할별 분리** | 메인 SKILL.md + 3개 서브에이전트로 분리 |
| **마크다운 파일 1장 = 에이전트 1개** (코드 X) | 모든 에이전트가 `.md` 파일. JSON·코드 없음 |
| **자산 재사용** (복제 X) | 기존 `b2b-content` 스킬의 references·templates는 Read만, 복사 안 함 |
| 사용자 개입 최소화 | 6단계 흐름에서 사용자 게이트 2번 (토픽 선택 + 본문 검수) |

### 과정 (타임라인별 + 삽질)

1. **출발점 — b2b-content 스킬의 두 약점 자각**: 본문 퀄리티 약함 + 주제를 매번 본인이 발굴해야 함. "콘텐츠 시드 자체를 강하게 만들면 두 약점이 동시에 줄어들지 않을까?" 가설.
2. **벤치마킹 — 장병준의 AI Orchestration Guide 정독**: "오케스트레이터 + 서브에이전트", "마크다운으로 정의되는 에이전트", "역할별 분리" 패턴 추출.
3. **YouTube 시드 결정**: transcript = 사실·사례·맥락이 농축된 1차 자료 → 콘텐츠 시드로 강함. 장병준 패턴의 "강한 입력" 원칙과 일치.
4. **6단계 워크플로우 설계**: transcript 추출 → 인사이트 5~7개 → 시장 추천 → 토픽 3개 점수화 → 사용자 선택(게이트 1) → 마스터 글 → 검수(게이트 2) → meta.json
5. **3단 폴백 설계 (transcript 추출)**: Chrome MCP → yt-dlp → 사용자 수동 paste. 한 길이 막히면 다음 길로.
6. **삽질** — 처음엔 메인 SKILL.md 하나에 모든 단계를 욱여넣으려 했음. 장병준 청사진 다시 읽고 "역할별 분리 = 단일 책임"으로 강제 분해 → 서브에이전트 3개 모델로 전환. 결과적으로 `writer-agent`는 b2b-content 리팩터링에서도 그대로 재사용 가능한 자산이 됨.
7. **시범 운영**: K-뷰티 EU 진출 카페24 웨비나 영상으로 1편 자동 생성 → 사용자 손질 시간이 b2b-content 평균 대비 약 30% 감소 확인.

### 공유할만한 인사이트

1. **벤치마킹의 핵심은 "패턴"이지 "산출물"이 아니다** — 장병준의 가이드를 그대로 베낀 게 아니라, "오케스트레이터 + 마크다운 에이전트 + 역할 분리" 라는 **추상 패턴**을 추출해서 본인 도메인(K-Expo 콘텐츠)에 이식. 결과물은 완전히 다른 모양인데 **뼈대는 같음**.
2. **"역할별 분리"는 사람 협업 원칙이 아니라 LLM 협업 원칙이기도 하다** — 단일 거대 프롬프트는 LLM이 컨텍스트 내에서 우선순위 충돌을 일으킴. 서브에이전트로 쪼개면 각자의 책임이 좁아져 결과 퀄리티가 올라감. 사람 팀 빌딩의 메타포 그대로 적용 가능.
3. **자산 재사용 전략(Read만 / 복제 X)이 OS 유지보수의 진짜 핵심** — 기존 b2b-content 스킬의 references를 yt2blog로 복사했으면 양쪽 동기화 부담이 영원히 따라옴. Read 전용으로 묶으니 brand-voice 한 군데만 고치면 두 스킬에 동시 반영. **OS 부품 사이의 의존성을 코드 import 처럼 다루는 발상**.
