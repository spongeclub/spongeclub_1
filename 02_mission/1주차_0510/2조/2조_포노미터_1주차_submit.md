### 공유할만한 인사이트
1.R 톤 가설 검증의 위력 — 사용자 답을 듣고 가설을 던지고 정정받는 사이클이 통점을 정확히 좁혀줌. 사용자 본인도 모르던 통점이 드러남.
2.OS 선언문은 빈칸 채우기로 잡힌다 — "나는 ___만 하고, 나머지는 시스템이 한다" 빈칸 발판 3개 깔아주면 사용자가 가장 가까운 것을 고름.
3.첫 부품은 "효과 큰 것"이 아니라 "완성이 빠른 것" — 큰 통점부터 가지 않고 작은 승리부터 모멘텀 쌓는 순서가 결국 더 빠름.
4.드러그푸딩이 인터뷰의 진짜 가치 — 인터뷰 끝나고 바로 사용하면서 발견되는 정정 사이클이 핵심. Ep.7 한 사이클로 디자인 시스템 4번 정정 + 통점 재발견 + 결론 도달.
5.명세 ↔ 실제 정합성이 진짜 검증 — 머릿속·작업 흐름엔 있지만 문서로 안 박힌 부분이 부품을 직접 사용해야 드러남.
6.통점은 만들어가는 중에 진짜 모습이 드러난다 — 인터뷰 Step 2에서 짚었던 통점("일관성 깨짐 무한 루프")보다 부품을 쓰면서 발견된 통점("클로드 디자인과 분리됨")이 본질에 더 가까웠음. 인터뷰만으로는 다 못 잡음.

## 미션 2: 따라해보고 싶은 개인/업무/삶 OS 따라서 만들어보기 - SNS(유튜브 등) 에서 찾아 벤치마킹 해오기

### Summary
zemma-carousel.vercel.app (스폰지클럽 인스타 시리즈 자동 생성기)을 벤치마킹해서 SyncAlive 맥락에 맞춘 SyncAlive 캐러셀 생성기 v3를 설계·구현. PRD 작성 후 Claude Code 새 세션이 자동 구현 → localhost:5173 작동 확인.

### 최종 구현 결과물
1.PRD 문서 (02_carousel_app/PRD.md)
-13개 섹션 (Context, Problem, Goal, User Flow, 기능 요구, 기술 스택, 디자인 시스템 통합, 마일스톤, 검증, 진화 방향)
-Claude Code 새 세션이 보고 자동 구현 가능한 수준
2.SyncAlive 캐러셀 생성기 v3 MVP (작동 중, localhost:5173)
-Vite + React + TypeScript
-디자인 시스템 v2.5 컴포넌트화 (TypeA/B/C)
-입력 폼 → 카드 8장 실시간 미리보기 → PNG 8장 ZIP 일괄 다운로드 ← v3 핵심
-캡션·해시태그 자동 조립
3.url: https://syncalive-carousel.vercel.app

### 과정 (타임라인별 + 삽질)
1.벤치마킹 분석

zemma carousel(zemma-carousel.vercel.app) 컨셉 파악: "원소스 멀티유즈" 도구
사용자가 다른 채팅창에서 사전 작업해둔 v2 HTML(프롬프트 생성기) 자산 확인
v2의 한계: Claude Design 프롬프트만 출력, 실제 PNG는 따로 작업해야 함

2.zemma carousel ↔ SyncAlive v3 차별점 정의

3. PRD 작성 (~30분)

OS 인터뷰 스킬의 형태 C (독립 프로덕트 PRD) 활용
폴더 생성 (02_carousel_app)
13개 섹션 작성 — Claude Code가 보고 자동 구현 가능한 수준의 디테일

4.Claude Code 새 세션이 v3 MVP 자동 구현

사용자가 새 세션 켜고 PRD 던짐
M1 (Vite scaffold) → M5 (캡션 조립)까지 자동 진행
localhost:5173 작동 확인 ✅
"잘 되는 거 확인했다" — 검증 완료

### 공유할만한 인사이트
1.벤치마킹 ≠ 복제 — zemma carousel의 컨셉 (원소스 멀티유즈)은 가져왔지만, 디자인 시스템·페르소나·출력 형식은 본인 맥락에 맞게 완전히 새로 짬. 같은 도구를 만들어도 사람마다 톤·흐름이 다름.
2.본인의 strict한 명세가 있으면 AI 도구는 오히려 불필요해진다 — Claude Design을 쓰던 이유는 "AI 디자인 도움"이었지만, 디자인 시스템 v2.5가 strict해지자 AI 능력 안 쓰임. 결정론적 코드로 대체가 더 깔끔하고 일관성 100%.
3.PRD 분리의 효율 — OS 인터뷰 세션에서 PRD까지만 만들고, 실제 코딩은 새 Claude Code 세션에서 진행. 토큰 절약 + 컨텍스트 분리. PRD 한 파일이 6시간 분량 코드를 자동 생성하는 진짜 자산.
4.부품끼리 통합되면서 청사진이 압축됨 — 부품 A·D가 웹앱 v3에 흡수되어 청사진 부품 4개 → 실질 2개로 정리. OS는 부품 누적이 아니라 통합되며 단순화되는 방향이 건강함.
5.벤치마킹의 진짜 가치는 "자기화" — zemma 도구를 그대로 쓰지 않고 본인 SyncAlive 맥락에 맞춰 새로 만든 것이 핵심. 본인 디자인 시스템·페르소나·시리즈 컨벤션이 박힌 도구는 본인만 쓸 수 있는 자산이 됨.
6.벤치마킹의 어려운 부분은 "남의 OS의 무엇이 본인 맥락에 정합한가"를 가려내는 것 — zemma carousel의 모든 기능이 본인에게 필요한 것은 아니었음. 입력 폼 구조·캡션 조립 로직은 fork했지만, 출력 방식(Claude Design 프롬프트 vs 직접 PNG)은 완전히 새로 짬.
7."분리감"이 OS의 진짜 적 — 도구 사이 컨텍스트 스위칭이 통점의 본질. v3가 클로드 디자인 단계를 제거하면서 OS 선언문의 60~70% 자동화 달성.
