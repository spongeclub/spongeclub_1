# 1주차 과제 — 개미

## 미션 1: claude code 로 인터뷰스킬 사용해서 인터뷰 까지 진행

### Summary

[selfishclub/os-interview-skill](https://github.com/selfishclub/os-interview-skill)을 Claude Code에 설치한 뒤,
**GPT 세션과 Claude 세션 두 곳에서 병행으로** OS 인터뷰를 진행했다.
같은 사용자, 같은 인터뷰 스킬, 같은 working directory였지만 두 세션의 결과물(청사진·첫 부품)이 **서로 다른 모양으로 갈라진 점**이 가장 흥미로운 수확이었다.

- 결과물: **OS 청사진 2종** + **Claude 스킬 2종** (단일 채널형 1, 멀티 채널형 1)
- 두 부품을 직접 사용·비교한 뒤 **GPT 세션 부품을 인스타 카드뉴스 자동 출력까지 가능한 v0.2로 업그레이드** — 한 부품 안에 단일 채널 깊이 + 조건부 멀티 채널을 결합
- 부수적 학습: 두 세션의 격리·통합 운영, 입문자가 헤맬 만한 함정 5개

### 최종 구현 결과물

> GPT 세션 = "스레드 한 편만 잘 쓰자"의 **깊이형** / Claude 세션 = "한 번에 여러 채널로 흩뿌리자"의 **펜아웃형**.

### 과정 (타임라인별 + 삽질)

**Phase 1 — 인터뷰 시작 + 격리 규칙 도입**
처음에는 GPT 세션 한 곳에서만 인터뷰를 진행했다 (`os-blueprint.md` 1차 산출).
이후 같은 working directory에서 Claude 세션을 추가로 열어 **두 세션 병행 운영**으로 전환.
두 결과물이 섞이지 않도록 **세션별 접미사 규칙**을 도입했다.

- GPT 세션 산출물 → `*-gpt` 접미사
- Claude 세션 산출물 → `*-claude` 접미사
- 각 세션은 다른 세션 파일을 **읽지도 수정하지도 않음** (격리)

**Phase 2 — 인터뷰 6단계 진행 (양 세션 모두)**
- **Step 1 풍경**: 1인 크리에이터 — 소설·SNS·모임 운영·자기관리 4개 축
- **Step 2 통점**: 메모 흩어짐 / 변환 수동 / 데이터 안 보임 / 영감-콘텐츠 단절
   - 양 세션이 통점 정의에서 갈라짐 — GPT는 4개를 종합으로, Claude는 "변환 시간 1.5h × 매일 = 주 10.5h" **단일 핵심**으로 압축
- **Step 3 이상향**: OS 선언문 도출 (양 세션이 다른 문장으로 마무리)
- **Step 4 부품 매핑**: GPT 6개 후보, Claude 5+1개 후보
- **Step 5 첫 부품 결정**: 둘 다 "스레드 변환"으로 수렴
- **Step 6 SKILL.md 작성**: GPT는 단일 채널 + 적합도 진단, Claude는 멀티 채널 + 트렌드·무게 분기

**Phase 3 — 첫 부품 설치 + 발동 테스트**
- `~/.claude/skills/<부품 이름>/SKILL.md` 위치로 PowerShell·bash 복사
- 새 Claude Code 세션 열기 → 트리거 문구로 발동 확인

**Phase 4 — 두 부품 사용 비교 후 GPT 부품 v0.2 업그레이드**
- 두 부품을 모두 발동시켜 같은 메모로 변환을 돌려보았다.
- 결과: **GPT 부품의 스레드 톤이 본인 스타일(휴머니즘·서정·따뜻함)에 더 가깝다**는 판단.
- 그러나 인스타 캐러셀까지 만들어주는 건 Claude 부품 쪽이라 한 부품으로는 부족했다.
- 결정: GPT 부품을 **단일 채널 깊이 유지 + 조건부로 인스타 카드뉴스 자동 출력**까지 하는 v0.2로 업그레이드.
- 인스타 자료(피드 캡처 2장, 캐러셀 7장, 캡션 1장)를 working directory의 `instagram-references/`에 모아 톤·디자인 명세 추출 → SKILL.md에 [인스타 카드뉴스 변환 규칙] 섹션 추가 (6개 하위 규칙).
- **자동 출력 조건**: 6장 이상 풀어낼 분량 + 캐러셀 시각 구조 적합 + 인스타 반응 유도 가능 — 셋 다 충족 시 사용자가 "인스타도"라고 따로 말하지 않아도 자동 출력.

**삽질 1 · 두 세션 병행 시 격리가 필요하다는 걸 늦게 알았다**
처음에는 두 세션을 병행해도 자동으로 안 섞일 줄 알았다. 실제로는 한 세션의 Claude가 working directory에 있는 다른 세션 파일을 자동으로 읽어버렸다.
**사용자가 명시적으로 "다른 세션 파일은 읽거나 수정하지 마세요"라고 규칙을 줘야** 격리가 작동했다.
→ 입문자가 두 세션을 동시 운영할 거면 **시작 전에 격리 규칙부터 박아두기**.

**삽질 2 · 스킬을 만든 직후 같은 세션에서 발동 안 된다**
SKILL.md를 `~/.claude/skills/`로 복사한 직후 **같은 채팅창에서** 트리거 문구를 던졌더니 발동되지 않았다.
스킬은 **세션 시작 시점에 한 번** 로드되기 때문에 새 Claude Code 세션을 열어야 인식된다.
→ 만들고 나서 Claude 창을 새로 열어야 한다. (현재 켜진 창은 안 꺼도 됨)

**삽질 3 · `~/.claude/skills/`와 `~/.claude/commands/`는 다르다**
스킬은 `skills/`, 슬래시 커맨드는 `commands/` 폴더에 넣어야 발동된다. 둘이 비슷해 보여서 입문자는 헷갈리기 쉽다.
→ 새 부품을 만들 때마다 **어느 폴더에 들어가야 하는지** 한 번 더 확인.

**삽질 4 · 참고 자료 확보 책임이 모호했다**
"다른 분들 과제를 참고해서 만들어달라"고 했더니, Claude가 처음에는 자체 추측으로 작업을 진행하려 했다.
**"직접 깃헙에 들어가서 확인한 다음 작성해주세요"** 라고 행동을 명시해야 Claude가 깃헙을 먼저 확인하고 톤을 맞춰주는 흐름으로 들어갔다.
→ 입문자가 "이거 보고 만들어줘"라고만 하면 Claude는 자료 확보 단계를 건너뛸 수 있음. 행동을 직접 지시하기.

**삽질 5 · 파일 격리 절차의 시작 신호를 명시적으로 줘야 한다**
"격리를 일시 해제해 다른 세션 파일을 읽고, 다시 격리"라는 절차를 정해도, 시작 신호 없이 Claude가 미리 읽어버리는 일이 있었다.
→ **각 단계마다 명시적인 진행 신호**를 줘야 안전.

### 공유할만한 인사이트

**1. 같은 인터뷰가 다른 결과로 갈라진다 — 비교해보니 일부 답이 나왔다**
GPT 세션과 Claude 세션의 결과물이 **단일 채널 vs 멀티 채널**, **적합도 진단 vs 무게 분기** 같은 형태로 갈라졌다. 같은 인터뷰 스킬, 같은 사용자였는데 왜?

처음엔 1~2주 사용 후 디깅하려 했지만, **양쪽 부품을 같은 메모로 돌려본 즉시 한 가지 답이 나왔다**:
- **글의 톤은 GPT 부품이 본인 스타일에 더 가깝다** (휴머니즘·서정·따뜻함이 그대로 살아남)
- **시각 변환은 Claude 부품이 더 멀리 간다** (캐러셀·블로그까지 한 번에)

→ 그래서 **GPT 부품에 인스타 카드뉴스 출구만 추가**하는 v0.2로 합쳤다. 단일 채널 깊이 + 조건부 인스타 = 본인 스타일 유지하면서 채널 확장.

남은 가설 (계속 디깅):
- (a) AI의 가설 던지는 방식이 세션마다 미묘하게 다르다 (R톤의 변주)
- (b) 사용자(나)가 두 세션에서 서로 다른 부분을 강조했다
- (c) 둘 다 "정답"이고, 작업량·기분·맥락에 따라 어울리는 부품이 다르다

**6. 두 부품을 다 만들어보고 합치는 것도 전략이다**
처음엔 한 부품을 처음부터 잘 설계하려 했지만, **다른 결의 부품을 두 개 만들어 비교한 뒤 좋은 부분만 합치는** 방식이 더 빨랐다. 인터뷰 단계에서 한 번에 정답을 뽑으려 하지 않아도 됨.

**2. 두 세션 병행 운영의 가치 — 한쪽만 봤으면 놓쳤을 그림**
청사진 1개만 만들었다면 "이게 내 OS의 모양"이라고 단정했을 것이다.
두 개를 만들어 비교하니 "이 사용자의 OS는 사실 **두 갈래로 운영 가능**하다"는 더 풍부한 그림이 나왔다.
단일 채널 부품과 멀티 채널 부품을 **둘 다 손에 두고 상황별로 골라 쓰는** 방식도 가능하겠다.

**3. 격리 규칙은 작업 시작 전에 박아두는 게 맞다**
두 세션 병행 시 "각 세션은 본인 결과물만 만든다 / 다른 세션 파일은 읽지도 수정도 않는다"는 규칙을 **시작 전에 명시**해야 한다. 일단 섞이고 나면 정리 비용이 크다.

**4. Claude에게는 행동을 명시해야 한다**
"X를 참고해서 Y를 만들어줘"라고 하면, Claude는 X를 어떻게 가져올지 자체 판단하다가 어긋날 수 있다.
**"직접 깃헙에 들어가서 확인하고 만들어달라"** 처럼 행동 자체를 명시하면 정확하다. 입문자에겐 이 차이가 의외로 크다.

**5. 첫 부품은 "지금 가장 자주 쓸 것"으로 — Nina의 인사이트에 동의**
인터뷰에서 나온 여러 부품 중 "스레드 변환"을 첫 번째로 고른 이유 — **매일 발생**하는 작업이고, 자동화의 체감이 가장 빠르기 때문. 분석·위젯·회고 같은 부품은 1차에선 의식적으로 미뤘다.

## 미션 2: 따라해보고 싶은 개인/업무/삶 OS 따라서 만들어보기 - SNS(유튜브 등) 에서 찾아 벤치마킹 해오기

### Summary

미션 2 명세는 SNS(유튜브 등)에서 OS 사례를 찾는 것이었지만, **벤치마킹 자료를 같은 1기 동기들의 작업물 저장소(`spongeclub/spongeclub_1`)로 변형**했다.
이유는 (1) 같은 미션·같은 시점에 작성된 자료라 톤·디테일이 가장 가깝고, (2) SNS 알고리즘으로 걸러지지 않은 1차 자료이기 때문.

이번 세션에서는 **벤치마킹 본 작업이 아니라 그 사전 단계인 "분석 대상 지도 만들기"까지만** 수행했다. 549개 md 파일을 다 읽으려 들면 시작도 못 하므로, 1차 패스를 매핑·압축에 한정하고 본문 정독은 다음 세션으로 분리.

- 새 작업 폴더 `sponge-os-analysis/`에 안전 규칙(원본 read-only, 별 폴더 산출, git 명령 금지)을 박은 뒤, GitHub Trees API로 549개 md 파일 + 76개 첨부 PNG를 한 번에 매핑.
- 결과물: **저장소 지도 1개** (`analysis_output/00_repo-map.md`, 8개 섹션, 692줄)
- 핵심 발견: 1주차에 OS 청사진 미션이 있었고, 분석 1순위 4개 파일이 모두 1주차에 집중되어 있음 — 549개 → 4개로 우선 정독 대상 압축.
- 부수 산출물: 다음 세션 트리거 문구 1세트 — 새 채팅창 첫 메시지로 그대로 붙여넣을 수 있는 12줄 컨텍스트 묶음.

|---|---|
| `_tree_raw.json` | GitHub Trees API 원본 응답 (파일 목록 캐시) |
| `_processed.json` | 주차/조별 그룹핑 + 메타데이터 가공본 |
| `_extract.js` | 트리 → 가공본 변환 스크립트 |
| `_build_md.js` | 가공본 → 마크다운 지도 변환 스크립트 |

**3) 핵심 발견 (지도가 알려준 것)**

| 발견 | 내용 |
|---|---|
| 1주차 = OS 청사진 미션 | 1주차 폴더에만 비표준 산출물(`os-blueprint.md` 2종 + `두뇌창고.prd.md` + `_missions.md`) 4개가 모여 있음. 본인 1차 산출물 목록 1번이 정확히 `os-blueprint.md`인 것과 일치. |
| 분석 1순위 압축 | 549개 md 중 4개로 우선 정독 대상 압축 — 시간 절약 효과 ≒ 99% |
| 명명 규칙 변동 | 0~4주차 폴더에는 날짜 접미사(`_0510`)가 있지만 5·6주차에는 없음. 분석 스크립트는 폴더명에 의존하지 말고 "N주차" 패턴으로 매칭하도록 작성. |
| 5조 인원 | 1주차부터 12명으로 다른 조(13명)보다 1명 적음. 분석 시 표준편차 기준점으로 활용. |

**4) 부수 산출물 — 다음 세션 트리거 문구**

새 채팅창에 붙여넣기만 하면 같은 톤·같은 컨텍스트로 이어지는 12줄 묶음 1세트. 페르소나·작업 폴더·이전 산출물 위치·산출물 목적·안전 규칙·결정 사항을 한 번에 넘김. 두 자리(`[분석 폭]`, `[본인 제출 처리]`)만 채우면 즉시 새 세션 시작 가능.

### 과정 (타임라인별 + 삽질)

**Phase 1 — 의도 설계 (첫 메시지)**
첫 메시지에서 **페르소나 + 5개 산출물 방향 + 안전 규칙 + 첫 실행에서 할 일/하지 말 일**을 한 번에 박았다.

- 안전 규칙 9개: 원본 read-only, 별 폴더 산출, 스크립트·git 명령 금지, 추측 금지, 입문자 풀이 등
- "이번 세션은 1차 매핑까지만, 본문 분석은 다음 세션"이라고 범위 명시
- 산출물(`00_repo-map.md`) 8개 섹션 구조까지 미리 지정

이 묶음 덕분에 Claude가 끝까지 범위를 안 벗어났고, 세션 종료 시점에 다음 세션 트리거 문구를 자연스럽게 도출할 수 있었다.

**Phase 2 — 저장소 접근 + 트리 매핑**
- WebFetch로 `https://github.com/spongeclub/spongeclub_1`이 공개 저장소임을 확인.
- GitHub Trees API(`git/trees/main?recursive=1`)로 전체 파일 트리를 한 번에 받아 `_tree_raw.json`에 캐시.
- `truncated=false` 확인 → 누락 없음. 02_mission 안 md 파일 549개 + 첨부 PNG 76개 식별.

**Phase 3 — 매핑 작성 + 압축**
- 주차/조별 그룹핑 → 사이즈 밴드 부여 → 마크다운 표로 출력.
- 1주차에서만 비표준 파일 4개 발견 → "1주차 미션 = OS 청사진 작성"이라는 가설 도출 → 다음 분석 1순위로 확정.
- 8개 섹션의 `00_repo-map.md` 작성 (692줄).

**Phase 4 — 다음 세션 트리거 문구 도출**
세션 종료 직전 사용자 요청으로 정리. 12줄 묶음 1세트 — 두 자리만 채우면 새 세션 즉시 시작.

**삽질 1 · 본인을 다른 사람으로 잘못 추측**
0주차 OT 데이터에서 `1조_임솔_*.md`가 보이자 Claude가 사용자(나)를 "1조 임솔"로 단정했다.
실제 사용자는 **3조 개미**였고, `00_repo-map.md` 본문 곳곳에 "임솔님"이라고 적힌 게 다 틀린 추측이었다.
원인: 첫 메시지의 페르소나 섹션에 본명·닉네임을 명시하지 않음 → Claude가 다른 데이터(레포 안 임솔 파일)에서 패턴 매칭으로 추측.
→ Claude에게 본인 식별 정보를 **첫 메시지에 명시**하지 않으면 데이터에서 추측한다.
→ 다음 세션 트리거 문구의 `# 내 페르소나` 섹션이 처음부터 닉네임을 박는 형식인 이유.

**삽질 2 · curl이 한글 폴더명을 깨뜨림**
`curl -s ... -o file.json` → PowerShell `ConvertFrom-Json`으로 검증 시도 → "잘못된 객체가 전달되었습니다" 에러.
원인: curl이 Windows 기본 코드페이지로 파일을 저장해 한글 일부 바이트가 깨짐.
→ 한글 파일·경로가 들어가는 작업은 처음부터 PowerShell `Invoke-WebRequest` 또는 명시적 UTF-8을 사용해야 함.

**삽질 3 · PowerShell ConvertFrom-Json도 실패**
PowerShell로 재시도해도 같은 한글 인코딩 이슈.
원인 추정: 응답 본문 안 일부 한글 시퀀스가 깨진 채 저장됨.
해결: Node.js의 `JSON.parse`로 우회 → 한 번에 통과(Node가 기본 UTF-8 처리).
→ 입문자 관점 교훈: **Windows에서 한글 데이터 다룰 때 도구 트라이앵글**(curl / PowerShell / Node) 중 한 개 막히면 빠르게 다른 도구로 갈아타기.

**삽질 4 · Claude Code 플랜 모드가 중간에 켜짐**
작업 중간에 Claude Code의 플랜 모드(Plan Mode)가 자동 활성화돼 일시 정지됨. 모든 쓰기 도구가 막히고 계획서만 작성 가능 상태로 전환.
대응: 안내대로 계획서를 별도 경로에 작성한 뒤 ExitPlanMode로 진행 재개.
→ 흐름은 끊겼지만 결과적으로 계획 단계가 명문화돼 안정성 ↑. 입문자에겐 "AI가 갑자기 멈춰서 동의 받는다" 정도로만 받아들이면 OK.

**삽질 5 · 549개 표를 한 파일에 다 담을지 고민**
지시는 "조별 파일 목록 표"였지만 549행 단일 표는 비실용적.
대응: 7개 주차 서브 테이블로 분리 + 추정 유형(개인 제출 / 조 공동·템플릿 / OS 청사진 / PRD / 미션 정의) + 사이즈 밴드 부여로 스캔 가능성 ↑.
→ "지시문은 글자대로 따르되, 사용자 이익이 더 큰 변형은 명시적으로 언급하고 적용" 패턴.

**삽질 6 · 본인 결정 사항을 묻지 않고 추측해 진행**
새 세션 트리거 문구를 만들 때 분석 폭·본인 제출 처리 같은 결정 사항을 사용자에게 미리 묻지 않고 "전수 / 분석 포함"으로 기본값을 박아둠. 사용자가 "이런 부분은 사전에 물어봐달라"고 명시적 피드백을 줌.
→ 결정 사항·환경 정보·본인 식별은 **AI가 추측 말고 사용자에게 사전 질문**해야 함. 입문자에겐 잘못된 가정을 되돌리는 비용이 가장 크다.

**삽질 7 · 분석 대상 저장소의 자동 제출 워크플로우를 늦게 발견**
GitHub 제출 단계로 넘어갈 때야 spongeclub 저장소가 이미 자동 제출 워크플로우(브랜치 → PR → squash 머지의 7단계)를 정의해뒀음을 알게 됨. 그 전까지 PR 직접 만들기·gh CLI·웹 UI 옵션을 풀어 설명하느라 시간을 씀.
→ 분석 대상 저장소의 `.claude/`·슬래시 커맨드 정의는 작업 시작 전에 한 번 훑어볼 것. **저장소가 이미 만들어둔 자동화는 그대로 쓰는 게 가장 빠르다.**

### 공유할만한 인사이트

**1. 벤치마킹 1차 자료로는 SNS보다 동기 저장소가 더 깊다** `#SNS마케팅` `#강의자료`
원래 미션 명세는 "SNS에서 찾아 벤치마킹"이지만, 같은 1기 동기들의 GitHub 제출물이 (a) 같은 미션·같은 시점에 작성됐고 (b) SNS 알고리즘으로 걸러지지 않은 1차 자료라 더 가까운 톤을 보여줬다.
SNS는 "잘 정리된 결과"만 노출되고 그 사이의 시행착오는 거의 안 보이지만, 동기 저장소는 시행착오가 그대로 남아있어 입문자에게 더 실용적이다.

**2. 1차 패스는 "본문 읽기"가 아니라 "지도 그리기"부터** `#OS반영` `#입문자재현`
549개 파일을 전수로 읽으려 들면 시작도 못 했을 것. 지도 그리기 → 1순위 4개 도출 → 다음 세션에서 그 4개부터 정독 — 이 단계 분리가 결정적이었다.
"전체를 보고 우선순위를 압축한 뒤 한 곳을 깊게 판다"는 방식 자체가 OS의 부품 후보로 넘어갈 수 있다(가칭 `repo-map`).

**3. 산출물 뼈대를 첫 메시지에 박아두면 끝까지 흐트러지지 않는다** `#OS반영` `#강의자료`
"이번 세션은 매핑까지만 / 5개 산출물 방향만 인지 / 분석은 다음 세션"이라고 적어둔 덕에, 세션 끝까지 범위를 벗어나지 않았고 트리거 문구도 자연스럽게 도출됐다.
미션 1의 인터뷰 스킬과 같은 원리 — **결과물 자체와 별개로 "다음 단계로 어떻게 넘기는가"를 부품처럼 출력**.

**4. 안전 규칙을 명문화하면 AI가 임의로 클론·커밋하지 않는다** `#입문자재현` `#강의자료`
"원본 read-only / 별 폴더 산출 / git 명령 금지"를 박아둔 덕에 본 세션 어디서도 spongeclub_1 저장소를 클론하거나 수정하지 않았다.
입문자가 가장 무서워하는 "AI가 멋대로 뭘 했는지 모름" 상황이 발생하지 않음.
안전 규칙 묶음 자체가 다른 수강생에게 그대로 줄 수 있는 [공통 템플릿 요소].

**5. 한글 + Windows 환경 도구 트라이앵글** `#입문자재현`
한글 파일·경로가 들어가는 작업은 한 도구가 막히면 빠르게 다른 도구로 갈아타는 게 정석.
- curl: 쉽지만 Windows 기본 코드페이지 때문에 한글 깨짐 위험
- PowerShell `Invoke-WebRequest`: 공식 도구지만 일부 JSON 인코딩 이슈
- Node.js `JSON.parse`: 가장 안정적이지만 입문자에겐 진입 장벽

이 트라이앵글을 미리 알아두는 것만으로도 막히는 시간이 절반.

**6. 지시문의 글자보다 의도를 따르되, 변형은 명시적으로** `#강의자료` `#OS반영`
"조별 파일 목록을 한 표로"라는 지시는 549행 단일 표를 의미하지만, 그건 사용자 이익에 반함. 7개 서브 테이블로 분리하되 그 변형 사실을 본문에서 명시 → 사용자가 다시 펼쳐달라고 요청할 수 있게 열어둠.
미션 명세 자체를 "SNS 벤치마킹 → GitHub 동기 저장소 벤치마킹"으로 변형한 것도 같은 패턴.

**7. 사전 확인 원칙 — 본인 식별·환경·결정은 추측 말고 묻기** `#입문자재현` `#OS반영`
삽질 1·6의 교훈을 부품화. 다음 세 가지는 데이터로 추측하지 말고 **사용자에게 사전 질문**한다:
- **본인 식별**: 소속·닉네임. 데이터에서 패턴 매칭으로 추측 금지.
- **환경 상태**: 작업 폴더가 git 저장소인지, GitHub 인증이 돼 있는지, 어느 도구로 진행할지.
- **결정 사항**: 분석 폭, 비교군 처리, 산출물 형식 등 — 선택지 2~3개를 제시하고 사용자가 고르게.

이미 추측한 산출물이 있으면 정정 시점에 "어디에서 어떻게 추측했고 어떻게 정정했는지"를 명시. 입문자에겐 잘못된 가정의 되돌림 비용이 가장 크다.

**8. 다음 세션은 "전수 + 비교군으로만"으로 진행** `#OS반영` `#강의자료`
1주차 인사이트 추출 세션의 운영 옵션 두 가지를 결정:
- **분석 폭 = 전수**: 1주차 모든 조의 모든 제출물 정독. 이유: 품질 우선이라 시간을 양보. 동기 저장소 1차 자료가 다 모인 기회를 한 번에 흡수.
- **본인 제출 처리 = 비교군으로만**: 본인 제출(3조 개미)은 분석 본편에서 빼고, 결과물 마지막에 별도 비교 섹션. 이유: 다른 학우들의 좋은 패턴을 먼저 흡수한 뒤, 영향 받지 않은 시점의 본인 작업을 재확인하기 위함.

다른 옵션(샘플링 / 분석 포함 / 자기 진단 별도 / 별도 산출물 등)도 가능성을 열어둠 — 다음 주차 분석부터는 톤·시간에 따라 다르게 갈 수 있음.

**9. 분석 대상 저장소의 자동화는 그대로 쓰는 게 가장 빠르다** `#입문자재현` `#OS반영` `#강의자료`
spongeclub 저장소가 이미 자동 제출 워크플로우(브랜치 → PR → squash 머지의 7단계)를 정의해둔 것을 늦게 발견. 트리거 문구 한 줄(`"3조 개미입니다. 1주차 과제 ... 제출합니다"`)로 7단계가 자동 실행됨. 사용자가 git 명령을 외울 필요 없음.
→ 본인 OS의 부품도 **"트리거 한 줄로 멀티 스텝이 발동"하는 형식**을 기본 패턴으로. 입문자가 외울 명령어 수를 0에 가깝게.
→ 분석 대상 저장소의 `.claude/`·슬래시 커맨드 정의는 **작업 시작 전에 한 번 훑어볼 것**.
