# 1주차 과제 — Nina

## 미션 1: claude code 로 인터뷰스킬 사용해서 인터뷰 까지 진행

### Summary

- PM으로서 반복 업무 통점 발굴 → 첫 도구 **리뷰 브리핑 스킬** 설계 및 제작
- 스킬 실행 시도 → 파일 위치 오류 2회 + Claude 오해 1회 삽질 끝에 성공
- 실제 피그마 → 브리핑 문서 자동 생성까지 완료
- 부가: 빈 폴더에서 x86-64 OS 커널 코드 처음부터 작성 (학습 목적)


### 최종 구현 결과물

**1. OS 청사진 문서 (`os-blueprint.md`)**  
내가 어떤 사람이고, 무엇이 반복적으로 힘들고, 어떤 상태가 되면 좋겠는지를 정리한 문서. 앞으로 새 도구를 만들 때마다 이 문서를 출발점으로 쓸 수 있다.

**2. 리뷰 브리핑 스킬 (`review-briefing.skill.md`)**  
피그마 링크(또는 기획 문서)를 Claude에게 던지면, 디자이너·개발자에게 전달할 수 있는 리뷰 브리핑 문서를 자동으로 생성해주는 도구. `~/.claude/commands/` 폴더에 넣어야 `/review-briefing`으로 실행 가능.

> ⚠️ OS 인터뷰에서 만든 스킬 파일이 실제로 동작한 게 아니었다는 것이 나중에 밝혀짐. 동작한 건 별도로 존재하던 다른 구현체. OS 자체가 제대로 세팅되지 않은 상태였던 것이 원인이었음

**실제 출력 결과물**: `briefing-2026-05-09-(메뉴명).md`
- 저장 위치: `~/.claude/plugins/review-briefing/output/`
- 내용: 프로젝트 배경·범위·구현 스코프·오늘 결정할 것·참고 문서 구조로 생성됨![[Pasted image 20260509184049.png|155]]


**3. x86-64 OS 커널 코드 (부가 작업)**  
별도로 "실제 운영체제 커널"도 빈 폴더에서 처음부터 만들었다. 이건 프로그래밍 학습 목적의 결과물이다.


### 과정 (타임라인별 + 삽질)

**14:30 — "내 OS 만들고 싶어"**  
완전히 빈 폴더에서 시작. 실제 운영체제 커널 코드를 처음부터 설계하고 작성하기 시작했다.

**15:59 — OS 인터뷰 시작**  
"나만의 워크플로우 시스템 짜고 싶어"라고 입력했더니 인터뷰가 시작됐다.

- **Phase 1**: 지금 어떤 일을 하는지 이야기함. PM이고, 레퍼런스 찾기 / 기획 문서 작성 / 디자이너·개발자에게 설명하는 회의 / 와이어프레임 그리기(본인 전문 분야 아님)에 주로 시간을 쓴다고 답했다.
- Claude가 "그 중에 가장 비용이 큰 건 어디냐"고 파고들었고, **와이어프레임 그리기**(디자이너가 훨씬 빠른데 내가 직접 하게 되는 상황)가 가장 불필요한 시간 낭비라는 걸 함께 발견했다.
- 커리어 트렌드를 파악할 시간이 없다는 고민도 나왔다.
- **결론**: "나는 기획과 의사결정만 하고, 나머지는 시스템이 한다"는 방향으로 첫 도구 = **리뷰 브리핑 스킬**을 만들기로 결정.
- ⚠️ **삽질**: `/os-interview` 명령이 Claude에 등록되지 않아 Unknown command 오류가 났다. Claude가 스킬 파일을 직접 열어서 수동으로 인터뷰를 실행하는 방식으로 해결.

**17:29 — 리뷰 브리핑 스킬 첫 실행 시도 (실패)**  
인터뷰가 끝나고 바로 스킬을 써보려 했다.피그마 링크와 함께 `/review-briefing` 명령을 입력했는데, 또 Unknown command 오류.

- ⚠️ **큰 삽질**: Claude가 오류를 무시하고 "혹시 이 피그마 화면을 코드로 구현하고 싶은 건가요?" 식으로 완전히 다른 방향으로 질문을 3개나 던졌다. "뭔소리야"를 3번 입력하고 세션을 강제 종료했다.
- **원인**: 스킬을 설치했어도 Claude가 새 세션을 열기 전까지는 인식하지 못한다. 같은 세션에서 만들고 바로 쓰려 해서 생긴 문제.

**08:32 (다음 날) — 파일 위치 오류 발견 및 수정**
새 세션에서 `/review-briefing` 재시도 → "여기서 인식되지 않는 명령어입니다" 오류 재발.
- ⚠️ **삽질**: Claude가 원인을 진단 — 파일이 `~/.claude/skills/`에 있었는데, Claude Code의 슬래시 커맨드는 `~/.claude/commands/` 폴더에서만 인식된다.
- Claude가 PowerShell로 파일을 올바른 위치로 이동시킴.
- Claude Code 재시작 요청 → 사용자가 중간에 인터럽트.

**이후 — 실제 성공적인 실행**
- `/review-briefing` 명령 입력 → 피그마 자료 제공 방식 선택 (링크 붙여넣기 선택)
- Capora Admin 피그마 링크 입력, 기획 문서는 없음으로 선택
- Claude가 Figma API를 직접 호출(curl)해서 화면 구조 파싱
- 브리핑 자동 생성 및 파일로 저장
- ✅ 슬랙에 바로 붙여넣을 수 있는 형태로 완성

> ⚠️ **사후 확인**: 실제로 동작한 것은 OS 인터뷰에서 만든 스킬 파일이 아니라 별도로 존재하던 구현체였다. OS 인터뷰 스킬 자체가 제대로 세팅되지 않은 상태였기 때문.



### 공유할만한 인사이트

**1. 슬래시 커맨드 파일은 `~/.claude/commands/`에 넣어야 한다**
`~/.claude/skills/`는 Claude가 스킬 설명을 읽는 폴더고, `/명령어` 형태로 실행하려면 `~/.claude/commands/`에 파일이 있어야 한다. 이 차이를 모르면 "인식되지 않는 명령어" 오류가 계속 난다. → **새 스킬을 만들면 어느 폴더에 저장됐는지 반드시 확인.**

**2. 스킬 만들고 바로 쓰면 안 된다**
Claude 스킬은 새 세션을 열어야 로드된다. 만든 직후 같은 세션에서 쓰려 하면 Unknown command 오류가 난다. → **만들고 나서 Claude 창을 새로 열어야 한다.**

**3. 인터뷰 스킬의 핵심은 "파고드는 것"**  
"뭐가 힘드세요?"에 "효율화요"처럼 모호하게 답하면 Claude가 더 구체적인 장면을 계속 요청했다. "최근 1주일 안에 그걸 떠올리게 한 장면 1개만"이라는 방식이 실제로 답하기 쉬웠고, 결과도 훨씬 구체적이었다.

**4. 첫 도구는 가장 자주 쓸 것으로**  
인터뷰에서 나온 여러 불편함 중 "리뷰 브리핑"을 첫 번째로 선택한 이유 — 피그마 리뷰는 매주 하는 일이고, 자동화됐을 때 체감이 가장 빠른 것이었기 때문이다.

**5. "모르는 것"도 명확히 말하면 된다**  
삶에서 시간을 많이 쓰는 활동을 묻는 질문에 "평소 깊이 생각해본 적 없어서 잘 모르겠다"고 답했는데, Claude가 그걸 그대로 받아서 업무 중심으로 인터뷰를 재조정해줬다. 모든 질문에 완벽하게 답할 필요 없다.

## 미션 2: 따라해보고 싶은 개인/업무/삶 OS 따라서 만들어보기 - SNS(유튜브 등) 에서 찾아 벤치마킹 해오기

### Summary

닥터가드너의 유튜브 콘텐츠를 벤치마킹해 "수집 → 소화 → 실행" 철학 기반의 라이트 OS를 설계하고, Obsidian + OneDrive 조합으로 Windows에 실제 구축까지 완료했다.

### 최종 구현 결과물

**툴:** Obsidian (Windows 기반 운영, 모바일은 추후 연동 예정)

**폴더 구조:**

```
📁 MyOS/
├── 📁 00_수집함/
│   └── 빠른메모.md       ← 판단 없이 즉시 던져넣기
├── 📁 01_오늘/
│   ├── 템플릿_오늘.md
│   └── 2026-05-09.md    ← 오늘의 하나 + 할 일
├── 📁 02_지식노트/
│   └── 템플릿_지식노트.md ← 읽고 소화한 것 3줄 요약
├── 📁 03_주간점검/
│   └── 템플릿_주간점검.md ← OS 자체를 개선하는 루프
└── 📁 99_아카이브/
```


**운영 루틴:**

```
매일 아침   → 오늘의 하나 정하기
틈새 시간   → 빠른메모에 수집
저녁 10분   → 빠른메모 정리 + 지식노트 이동
주 1회      → 주간점검 작성 (잘된 것 / 불편한 것 / 바꿀 것)
```

---

### 과정 (타임라인별 + 삽질)

**벤치마킹 탐색**

- 해외 크리에이터 조사: Tiago Forte(PARA), August Bradley(PPV), Thomas Frank, Ali Abdaal
- 한국 크리에이터 조사: 닥터가드너, 공여사들, 시리얼
- 닥터가드너 콘텐츠 직접 시청 → CCC + PACER 2단계 학습 프레임워크, GTD 기반 Second Brain OS 파악

**OS 설계**

- 풀버전(PARA + GTD + Second Brain) 대신 라이트 버전으로 시작하기로 결정
- 핵심 철학 2가지만 추출: "수집 습관 먼저", "매일 루프 돌리기"
- 주간점검을 OS 자체 개선 도구로 포함시키기로 결정

**툴 선정**

- 노션 외 대안 탐색 → Obsidian, Logseq, OneNote, Capacities 비교
- 환경 조건(Windows + Android) 적용 → Obsidian + OneDrive 무료 동기화로 결정

**세팅 과정**

- PC: Obsidian 설치 → OneDrive 폴더에 Vault 생성 → 폴더/파일 구조 자동 생성 → 정상 작동
- Android 삽질 ①: Remotely Save 플러그인 설치 → OneDrive 연결 성공 → 동기화했으나 파일 0개
- Android 삽질 ②: 한글 폴더명 문제 의심 → 영문으로 변경 → 그래도 안 됨
- Android 삽질 ③: OneDrive 앱으로 오프라인 동기화 시도 → Obsidian에서 폴더 경로 못 찾음
- **최종 결정:** 일단 PC로 시작, 모바일 동기화는 추후 해결

### 공유할만한 인사이트

**1. OS는 완성하고 쓰는 게 아니다**  
처음부터 PARA + GTD + Second Brain 풀셋을 구축하려다 시작도 못하는 경우가 많다. 핵심 루프(수집 → 정리 → 점검) 하나만 작동시키는 것이 훨씬 중요하다.

**2. 주간점검이 OS의 심장이다**  
"잘 된 것 / 불편한 것 / 바꿀 것" 3가지 질문을 매주 기록하면 OS가 스스로 진화한다. 닥터가드너도 10년에 걸쳐 시스템을 다듬었다.

**3. 툴 세팅에 너무 많은 에너지를 쓰지 말 것**  
모바일 동기화에 1시간 넘게 쓴 것처럼, 툴 완성에 집착하면 정작 습관 형성을 못 한다. 지금 쓸 수 있는 것으로 일단 시작하는 게 낫다.

**4. 벤치마킹은 나를 이해하는 도구다**  
남의 OS를 그대로 따라 하는 것이 목적이 아니다. 1~2주 테스트에서 수집함에 뭐가 쌓이는지, 어떤 노트를 다시 여는지를 보면 내가 실제로 어떤 사람인지 데이터가 나온다.
