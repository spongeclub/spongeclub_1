### 미션 1: 개인용 → 공용(멀티유저) 전환

#### Summary

|항목|내용|
|---|---|
|무엇을|나 1인용으로 만든 Career FIT OS를, 누구나 자기 기준으로 쓸 수 있는 멀티유저 구조로 전환|
|왜|MVP 검증 후 "남들도 써보고 싶다" 반응 확인 → 찐고객 피드백을 받으려면 그들이 자기 직무로 써봐야 했음|
|핵심|판단 기준을 내(K-뷰티)에게 하드코딩 → 사용자 프로필에서 동적 생성으로|

#### 최종 구현 결과물

- ==**하드코딩 제거**: 최지예/K-뷰티 특화 기준·화장품 필터를 코드에서 걷어내고 범용 템플릿으로==
- ==**사용자별 기준 생성**: 온보딩에서 이력서 넣으면 AI가 그 사람의 3축 기준(직무·환경·성장)을 추출·저장, 결과 화면에서 수정 가능==
- **판정 연결**: 공고 분석이 사용자 프로필 기준으로 판정 (없으면 기본값 폴백)
- **필수 요건 감지 일반화**: "화장품 경력 필수" → 산업 중립으로. 사용자 프로필에 없는 필수 조건을 감지해 경고
- **데이터 분리 유지**: 사용자끼리 데이터 안 섞이게 브라우저별 분리

#### 과정 (타임라인 + 삽질)

**왜 1인용으로 시작했었나** 처음엔 일부러 1인용으로 뾰족하게 만들었다. 범용으로 만들려다 막힌 경험이 있어서, 고객을 나 한 명으로 좁히니 빠르게 완성됐다. 그게 MVP까지 왔다.

**전환 결정** 발표 후 "남들도 써보고 싶다"는 반응. 찐고객 피드백을 받으려면 그들이 자기 직무로 써봐야 하는데, ==내 K-뷰티 기준이 박혀 있으면 다른 직무 사람한테 무의미했다. 그래서 멀티유저로.==

**삽질 — "수정은 되는데 판정은 하드코딩"** 프로필 화면에서 기준 수정은 됐지만, 실제 판정은 코드에 박힌 내 기준을 쓰고 있었다. UI만 동적이고 속은 하드코딩인 상태. 이걸 5단계로 나눠서(하드코딩 제거→기준 추출→판정 연결→필수요건 일반화→점검) 단계별 커밋하며 해소.

**삽질 — 거르개가 너무 느슨했음** "뷰티 B2B 경력 3년 필수" 공고를 넣었는데 "지원 막는 요건 없음"으로 통과됐다. 직접 써보다가 발견. AI가 "B2B 해외영업은 되니 통과"로 느슨하게 판단한 것. 이건 나만의 문제가 아니라 모든 사용자에게 거르개가 작동 안 하는 구조적 문제였다. "필수로 명시 + 사용자가 명백히 없음"일 때 경고하도록 조여서 해결.

**배운 것 — 버그는 내가 찾는다** AI(Claude Code)는 시키는 걸 만들 뿐, "맞게 작동하나"는 못 본다. 직접 써보면서 틈을 찾는 게 만드는 사람의 역할이었다.

#### 공유할만한 인사이트

==**1. 좁게 시작해서 넓히는 게 정석** 1인용 → 공용은 방향 전환이 아니라 예정된 다음 단계였다. 일부러 좁혀서 빨리 검증하고, 검증되니 넓혔다==. 넓게 시작해서 좁히는 것보다 항상 싸다.

**2. UI가 동적이어도 로직은 하드코딩일 수 있다** "수정 기능 있으니 멀티유저 됐겠지"는 착각. 겉(화면)과 속(판정 로직)이 따로 놀 수 있다. 진짜 확인은 직접 다른 직무로 써보는 것.

**3. 거르개가 핵심이면 거르개부터 정확해야 한다** 내 제품 차별점이 "지원 전 거르개"인데, 그게 느슨하면 차별점 자체가 무너진다. 기능 추가보다 핵심 기능의 정확도가 먼저.

## 미션 2: 찐고객 2명 페르소나 피드백

#### Summary

| 항목     | 내용                                                 |
| ------ | -------------------------------------------------- |
| 누구     | ① 이직 준비 중인 구직자 ② 최근 이직한 데이터 연구직 친구                 |
| 왜 이 2명 | 타깃("또 잘못 이직하기 싫은 사람") 정중앙 + 나와 다른 직무라 멀티유저 실전 검증까지 |
| 방식     | 직접 써보게 한 뒤 5문항 + 자유 피드백                            |

#### 최종 구현 결과물 (받은 피드백 정리)

**철학 검증 — 방향이 맞았다**

- "내가 회사를 선택한다는 기조 자체가 취준생·이직러에게 큰 도움"
- "정확도 90% 이상. 내가 놓치는 지점을 짚어주고, JD 분석까지 야무지게 매칭
- "지원 전 1순위로 분석 돌려놓고 정리하면 좋겠다 — 공고 분석은 지속하면 주관적이 되니까" 

**개선점 — 우선순위로 분류**

**_긴급(버그): 해결필요_**

- **없는 경력(CVAT 레이블링)을 이력서 초안에 지어냄  — 신뢰 직결**
- **지원현황 갔다 오면 분석 결과 날아감** 

_철학 핵심(높음):_

- 웹 제작 포폴 PDF가 빈 텍스트로 안 읽힘 → 이미지 업로드 보완 필요 — 입구 장벽
- 커버전략을 바탕으로 이력서/자소서 수정 문구까지 제시

_보강(중간):_

- 이직 이유 복수선택 
- 지원동기 너무 짧고 자기소개 첫 줄 너무 김
- 점수 시각화(원형/막대 그래프) 

_기타:_

- 마감일·면접 예상질문  — 예상질문은 원티드에 이미 있음
- 회사 정보 찾아주기  — "지원 돕기"라 거르개 철학과 다른 방향
- 연봉 분석 

#### 과정 (타임라인 + 삽질)

**페르소나 선정**  이직 준비자 + 최근 이직한 친구 2명 먼저. 서로 다른 시각(준비 중 vs 막 끝남)이라 피드백이 겹치지 않고 풍부했다.

**삽질 — 멀티유저 실전 검증이 여기서 됐다** ==데이터 연구직 친구(나와 완전히 다른 직무)가 자기 이력서로 써본 게 곧 멀티유저 테스트였다. 그 친구 초안에서 "없는 경력 지어내기" 버그가 잡혔다. 내 직무로만 테스트했으면 못 봤을 것.==

#### 공유할만한 인사이트

**1. 피드백은 다 반영하는 게 아니라 철학으로 거른다** 좋은 아이디어(회사 정보, 연봉 분석)도 "지원 전 거르개"라는 철학에서 멀면 곁가지. ==다 하려다 또 "만드는 시간 > 쓰는 시간"에 빠진다. 철학이 우선순위의 기준선이 된다.==

**2. 칭찬보다 "당황했다ㅋㅋ"가 100배 값지다** 은영이 "없는 정보 넣었다ㅋㅋ"라고 가볍게 말했지만, 이게 제일 위험한 신호였다. ==이력서 도구가 거짓을 만들면 신뢰가 끝.== 가벼운 농담 속 진짜 문제를 잡아내는 게 피드백의 핵심.

**3. 다른 직무 유저가 곧 멀티유저 검증이다** 나와 같은 직무 사람만 테스트했으면 "잘 되네"로 끝났을 것. ==다른 직무 친구가 써봐야 "내 가정이 다른 사람한텐 안 맞는다"가 드러난다.==
