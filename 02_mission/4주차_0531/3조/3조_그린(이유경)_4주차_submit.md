### 과정 (타임라인별 + 삽질)

#### 1단계: 5/29 (목) — 세션 1, MVP 심장 완성

**삽질 1: CLAUDE.md를 닻으로 박았다**  
5/24까지는 PRD/디자인 레퍼런스만 있었는데, 매 세션마다 "이번엔 어떻게 일하라"는 작업 원칙은 반복 설명. CLAUDE.md를 본체로 만들고 AGENTS.md를 포인터로 단순화. 매 세션 잔소리가 0이 되면서 가장 큰 속도 차이가 났다. **이게 사실상 진짜 게임 체인저였다.**

**삽질 2: 3상태 칩 설계가 핵심이었다**  
PRD에서 가장 미묘했던 "측정 안 함 vs 변동 없음" 구분. UI에서 칩 3개로 풀어내니, 데이터 모델이 UI에 그대로 드러나서 시드 데이터 만들 때도 명확해졌다. "측정 안 함" → 행 자체가 없음, "변동 없음" → 직전 값 복사 + `unchanged` 플래그.

#### 2단계: 5/30 (금) — 세션 2~4, 하루에 11화면

**삽질 3: BackButton을 11번 따로 짰다**  
5/24에 한번 겪었던 "history 꼬임" 문제(`router.back()`이 앱 밖으로 나감)가 이제 11곳에 흩어진 셈. 세션 4 끝나기 직전에 공용 컴포넌트로 추출하고 11개 화면을 일괄 교체. **"3번 반복되면 추출하라"는 룰을 11번까지 끌고 갔다.** 늦었지만 그래도 패턴(modal close vs page back vs onboarding skip)이 명확해진 다음에 뽑은 셈.

**삽질 4: 시드 데이터가 프로덕션에 노출**  
개발용으로 만든 가상 프로필 "지윤"이 Vercel 빌드에 그대로 들어가서, 프로덕션 첫 진입 시 더미 데이터가 보였다. **온보딩이 안 떴다.** `process.env.NODE_ENV === 'development'`로 게이팅해서 프로덕션은 빈 DB → 온보딩으로 가도록 격리. AI는 "이건 dev용"이라는 컨텍스트를 알고 있었지만, "프로덕션에 들어가면 안 된다"는 결정은 내가 명시 안 했다.

**삽질 5: 온보딩 폼 = 본진 폼 중복**  
온보딩 5화면 마지막에 "질환 추가" 폼이 필요한데, 이미 본진에 똑같은 폼이 있었다. 처음엔 따라 만들었다가, 폼 공용 컴포넌트로 추출해서 두 곳에서 같은 폼 재사용.

#### 3단계: 5/31 (토) — v0.2 implementation

(피드백 자체는 미션 2에서 정리. 여기선 구현 측면.)

**삽질 6: Dexie v1 → v2 마이그레이션이 무서웠다**  
마일스톤 백필을 위해 `datePrecision` 필드 추가하면서 기존 데이터에 기본값 `'day'`를 채워넣어야 했다. 실수하면 손으로 직접 만든 시드 21개 기록이 날아간다. 별도 브랜치(feat/milestone-backfill)에서 격리 → 충분히 테스트 → 머지. 결과적으로 마이그레이션은 한 번에 통과.

**삽질 7: Recharts strokeDasharray가 애니메이션과 충돌**  
정밀도별 점선/실선 만드는 과정에서, 첫 렌더에 점선 패턴이 안 그려지고 일자선으로 떴다가 애니메이션이 끝나야 점선이 나타나는 버그. `isAnimationActive={false}`로 우회. **결국 점선 자체를 폐기하면서(피드백 ③) 자연 해소됐지만**, 라이브러리 동작에 시간 낭비.

**삽질 8: 핵심 원칙을 의식적으로 깨야 했다**  
CLAUDE.md 핵심 원칙 #3 "서버 X — 모든 데이터는 IndexedDB에만"이 Supabase 동기화 도입으로 깨졌다. 그냥 지우는 게 아니라, **"v0.2 #5 결정으로 개정. 근거: data-durability spec §2"** 라고 개정 이력을 박았다. 미래의 본인(또는 Claude)이 "왜 원칙이 바뀌었지?" 헷갈리지 않게.

### 공유할만한 인사이트

**1. CLAUDE.md가 Claude Code의 뇌**  
PRD가 "무엇을"이라면 CLAUDE.md는 "어떻게 일할 것인가". 매 세션 시작할 때 잔소리가 0이 되니까 작업 흐름이 끊기지 않는다. PRD/디자인 레퍼런스에 작업 원칙까지 다 욱여넣으려 했던 5/24 미션 때보다 압도적으로 빨라졌다.

**2. 공용 컴포넌트는 패턴 종류가 분명해진 다음에 추출**  
BackButton을 11번 짠 다음에야 패턴이 명확해졌다. 세션 1에서 미리 추출했으면 "modal close vs page back vs onboarding skip" 시나리오 3가지를 다 못 떠올렸을 것. "3번 반복"이 정설이지만, 패턴이 다양한 경우엔 좀 더 기다리는 게 오히려 견고한 추출로 이어진다.

**3. AI는 의도를 모르고 패턴만 따른다**  
시드 데이터 프로덕션 노출은 100% 내 책임. Claude Code는 "이건 dev 데이터"라는 컨텍스트를 알고 있었지만, "프로덕션 빌드에 들어가면 안 된다"는 결정은 명시 안 했다. **환경 분기 같은 "당연한 것"도 명시해야 안전.** AI는 내 머릿속 의도를 못 읽는다.

**4. 35 커밋 / 3일 — 속도는 정리력에서 나왔다**  
코드 자체보다, CLAUDE.md / CHECKLIST.md / 디자인 레퍼런스 / PRD가 **항상 코드와 동기화**되어 있는 게 핵심이었다. 한 기능 끝나면 4개 문서를 한꺼번에 갱신 → 다음 세션이 그 위에서 바로 시작. 정리 안 하고 코드만 짰으면 5/31 즈음엔 컨텍스트가 무너졌을 것.

**5. 원칙은 개정 가능, 단 근거를 남길 것**  
"서버 X" 원칙이 동기화 도입으로 깨졌다. 지우지 말고 "왜 바뀌었는지"를 spec 링크로 박아둠. **원칙을 종교처럼 모시지 말고, 의식적으로 개정하되 근거를 남기는 게 더 견고하다.** 진짜 견고한 시스템은 변하지 않는 게 아니라, 왜 변했는지를 기억하는 시스템이다.

### 공유할만한 인사이트

**1. "내가 내 고객"이 진짜로 작동하려면 진짜로 써야 한다**  
PRD에 "본인이 페르소나"라고 적어두는 것과, 가상 케이스를 만들어 한 줄씩 입력해보는 건 완전히 다른 경험이다. 마일스톤 백필 문제는 PRD 단계에선 한 번도 안 떠올랐는데, 사용 10분 만에 나왔다. **만든 직후가 dogfooding의 골든 타임.** 머릿속 모델이 살아있을 때 사용자 입장에 서면 의사결정 비용이 가장 낮다.

**2. Mockup이 예뻤다고 실사용이 좋다는 보장은 없다**  
그래프 점선/실선 정밀도 인코딩은 디자인 레퍼런스에선 우아했다. 실제 데이터에 얹으니 "고장난 그래프"로 보였다. **눈으로 보는 것과 손으로 만지는 것은 완전히 다르다.** 본인 가상 케이스로 실사용 안 했으면 v2.3에서 멈춰서 "왜 그래프가 이상해 보이지" 모르고 출시했을 것.

**3. 도그푸딩 안에 도그푸딩이 있다 — 재귀 사이클**  
마일스톤 백필을 만들었더니, 그걸 써보고 다시 "백필과 현재 기록이 구분 안 됨"이라는 새 문제가 나왔다. 한 번 만들고 끝이 아니라, **개선 → 다시 사용 → 다음 개선** 사이클이 짧을수록 발견되는 문제가 깊어진다. 5/31 하루에 같은 영역에서 사이클이 두 바퀴 돌았다.

**4. 사이클 닫는 속도 = 학습 속도**  
발견 5건 중 4건이 같은 날 코드까지 들어갔다. 사이클이 24시간을 넘어가면 "그게 정말 문제였나?" 흐려진다. Claude Code 덕분에 발견 → 구현 사이의 마찰이 거의 0이었고, 그래서 즉시 피드백 루프가 돌았다. **AI 시대의 코딩은 양이 아니라 사이클을 닫는 속도로 차이가 난다.**

**5. 가상 페르소나도 충분히 정직하다**  
구체적인 본인 케이스가 아니라 **가상의 만성질환 시나리오**로 테스트했지만, 발견된 문제는 다 진짜였다. 페르소나 인터뷰를 1주 잡지 않더라도, "내가 사용자라면 여기에 뭘 입력해야 하지?"라는 단순한 질문 하나로도 mockup 단계에선 못 잡는 문제들이 줄줄이 나온다. **본인의 실제 사례가 없어도 dogfooding은 가능하다.** 가상으로도 정직한 손맛이 나온다.

**6. 발견의 80%는 "직접 입력해본 직후"에 나왔다**  
디자인 검토나 PRD 리뷰에선 안 나오던 문제들이, 실제로 입력 폼을 한 번 띄워보고 한 줄 적어보는 순간 다 나왔다. **"이걸 사용자가 어떻게 느낄까"를 머리로 시뮬레이션하는 건 한계가 있다.** 직접 손으로 입력해봐야 보인다. 5/31 하루가 가장 농도 짙은 사용자 리서치 세션이 됐다 — 인터뷰 한 번 안 하고도.

**7. 원칙은 의식적 개정이 가능하다 (단, 근거 필수)**  
"서버 X — 모든 데이터는 IndexedDB에만"이라는 핵심 원칙이 도그푸딩 피드백 ④로 깨졌다. 그냥 지우는 게 아니라 spec 링크와 함께 개정 이력을 박아둠. **원칙을 종교처럼 모시지 말고, 사용자 피드백 앞에서 의식적으로 개정하되 근거를 남기는 게 더 견고하다.** 진짜 견고한 시스템은 변하지 않는 게 아니라, 왜 변했는지를 기억하는 시스템이다.
