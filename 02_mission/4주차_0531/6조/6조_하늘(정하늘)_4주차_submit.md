## 미션1: <지난주 워크숍 반영하여 프로덕트 개선선>

### Summary
이번 주 미션은 **"지난번에 만든 영양 자가진단 도구를, 클로드 코드 작업 환경 관점에서 점검하고 손보기"**였다. 점검의 핵심 질문은 다섯 가지였다 — 쉽게 풀면 이렇다.

| 점검 항목       | 쉬운 말로                                          |
| ----------- | ---------------------------------------------- |
| ① CLAUDE.md | 클로드에게 주는 **"작업 설명서"** (이 프로젝트는 이런 거야, 이건 하지 마) |
| ② PRD       | **"기획서"** (이 제품이 정확히 뭔지 한 곳에 정리)               |
| ③ memory    | 클로드의 **"지난 결정 기억장치"**                          |
| ④ SKILL     | 자주 하는 작업을 **"버튼 하나로 만든 도구"**                   |
| ⑤ agent     | 특정 일만 전담하는 **"전문 검사역"**                        |

** 하네스 점검표 (5개 기둥)**

| 기둥          | 상태        | 근거 (실제 파일)                                                                                     |
| ----------- | --------- | ---------------------------------------------------------------------------------------------- |
| ① CLAUDE.md | ◎ 탄탄      | 3단 상속: 전역(OMC) → Why project/CLAUDE.md(전략·디자인토큰) → `supplement-tool/CLAUDE.md`(절대규칙·기술스택·빌드순서) |
| ② PRD       | ◎ 탄탄      | `docs/spec.md` 480줄, "single source of truth" 명시, v0.4 LOCKED, 학습가설 H1·H4, changelog 규칙        |
| ③ memory    | △ 있으나 이중화 | native memory 5개+인덱스 ↔ 별도로 `.omc/project-memory.json` 존재. **두 메모리가 서로 모름**                     |
| ④ SKILL     | ▽ 빈약      | 제품 전용은 `/worklog` 커맨드 1개뿐. 반복 워크플로(가설톤 점검·새 시스템 추가·리드 테스트)를 담은 SKILL 없음                        |
| ⑤ agent     | ✕ 비어 있음   | `.claude/agents/` 없음. 제품 전용 에이전트 0개, OMC 범용 에이전트에만 의존                                          |

**비어 있는 곳:** ⑤ agent(전무), ④ SKILL(worklog 외 없음)

**연결 끊긴 곳:**

1. **브랜드 절대규칙(가설 톤) ↔ 검수 장치 단절.** CLAUDE.md·PRD 모두 "가설 톤, 확정 처방 금지"를 #1 규칙·#1 KPI(H1)로 못박았는데, 결과지 카피를 고칠 때 이를 점검하는 skill/agent가 없음 → **사람 기억에만 의존**.
2. **memory 이중화.** native memory와 `.omc/project-memory.json`이 동기화 안 됨 → 결정이 한쪽에만 적히면 다른 세션이 놓침.

**가장 먼저 채우면 좋을 한 가지 → ⑤ "가설톤 검수 에이전트"(tone-guard)**

이유: 비어 있는 칸(agent)을 채우면서 **동시에 최대 위험(톤 일탈)을 막는** 가장 레버리지 높은 한 수. 

결론 한 줄: **설명서와 기획서는 잘 갖춰져 있는데, "규칙을 매번 지키는지 검사하는 장치"가 없다.** 이게 이 제품의 가장 중요한 약점이자, 다음에 가장 먼저 손볼 곳.

### 과정 (타임라인별 + 삽질)
1. **가장 중요한 규칙을 "글"로만 적어둔 상태다.**  
    이 제품의 절대 규칙은 *"영양제를 처방하듯 단정하지 말고, 가설처럼 말하기"*다. 설명서에는 잘 적혀 있다. 그런데 **클로드가 결과지 문구를 고칠 때마다 이 규칙을 진짜 지켰는지 확인해주는 장치가 없다.** 지금은 내가 매번 직접 읽어보고 기억해야 한다. → 이 검사 역할을 클로드에게 "전담 검사역"으로 맡겨두면, 앞으로 문구를 고칠 때마다 알아서 잡아준다.
2. **기억이 두 군데에 따로 적힌다.**  
    결정한 내용이 한쪽에만 저장되면, 다음에 작업할 때 다른 쪽만 보고 까먹을 수 있다. → 결정은 한 곳으로 모으는 습관.

이 둘만 정리하면 점검표의 빈칸(검사역·기억)이 채워지면서 가장 큰 위험도 같이 막힌다.
### 공유할만한 인사이트

클로드 코드를 쓰다 보니, **잘 만드느냐보다 "처음에 무엇을 깔아두느냐"가 결과를 더 좌우한다**는 걸 느꼈다.

- **"절대 어기면 안 되는 규칙 1개"를 정하고, 그걸 _어떻게 매번 확인할지_까지 같이 정해라.** 가장 큰 깨달음. 규칙은 적어두기만 하면 안 지켜진다. 글로 적은 규칙은 "규칙"이 아니라 "바람"에 가깝다. 누가(또는 무엇이) 매번 검사하는지를 정해야 비로소 규칙이 된다.
- **시키기 전에 "내가 뭘 만들려는지" 한 장으로 적어라(기획서).** 이게 있으면 클로드가 헤매지 않고, 나중에 "이거 왜 이렇게 했지?" 하고 되돌아볼 때 기준이 된다. 실제로 이 프로젝트는 기획서가 탄탄해서 오늘 수정이 빠르고 헷갈림 없이 끝났다.
- **결정한 건 그때그때 한 곳에 적어둬라.** 머릿속 결정은 다음 작업 때 거의 증발한다.
- **"이미 배포했는데 고칠 수 있나?"는 거의 항상 Yes.** 처음엔 망설였지만, 고치고 다시 올리면 끝이었다. 배포는 끝이 아니라 언제든 다시 손볼 수 있는 상태일 뿐 — 작게 자주 고치는 게 정답.
