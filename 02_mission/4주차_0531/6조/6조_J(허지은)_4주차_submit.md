## 미션1: 하네스 구조로 블로그 브리핑 봇 개선하기

### Summary
 3회차에 만든 네이버 블로그 글감 브리핑 봇이 "동작하는 코드"는 있었지만, 하네스 구조는 없었다. CLAUDE.md 하나에 API 코드·프롬프트·UI 로직·디자인 규칙·작업 단계가 전부 몰려 있었고, 메모리도 없었다. 오늘 세션에서 배운 대로 CLAUDE.md를 헌법으로 얇게 만들고, 기능별 PRD 4개와 MEMORY.md를 분리해서 하네스 구조를 완성했다.

### 최종 구현 결과물
- `CLAUDE.md` — 핵심 규칙 + PRD 참조 링크만 (기존 대비 70% 분량 축소)
- `MEMORY.md` — 현재 진행 단계(1~4 완료, 5 미완료), 주요 결정 사항, 다음 할 일
- `PRD/api.md` — Gemini API 구조 및 확정 코드
- `PRD/prompt.md` — 프롬프트 정의 (수정 금지 명시)
- `PRD/ui-logic.md` — 결과 렌더링, 캐싱, 에러처리 로직
- `PRD/design.md` — 디자인 이식 규칙 및 금지 함수 목록
![416](attachments/스크린샷%202026-05-31%20오후%205.39.31.png)

### 과정 (타임라인별 + 삽질)
**문제 인식**

- 오늘 세션에서 "Claude.md에 모든 걸 집중하면 수천 줄이 되어 오류 반복"이라는 말이 내 현재 파일 그대로였음
- CLAUDE.md를 열어보니 API 코드 블록, 프롬프트 전문, 더보기 JS 코드, 에러처리 표, 작업 단계 체크리스트가 전부 한 파일에 있었음
- 마크다운 간 호출 관계도 없었고, 메모리 파일도 없었음

**구조 설계**

- "뭘 남기고 뭘 뺄 것인가"가 핵심 판단 기준이었음
- CLAUDE.md에 남길 것: 한 줄 정의, 파일 구조, 기술 스택, 진행 규칙, MVP 제외 목록, PRD 참조 테이블
- 뺄 것: 모든 코드 블록, 프롬프트 전문, 작업 단계 → 각각 PRD 파일로 이동

**삽질 포인트**

- PRD를 몇 개로 나눌지 애매했음. 처음엔 2개(api.md, ui.md)로 하려다가 "작업 시 어떤 파일 열면 되지?"를 기준으로 4개로 분리
- MEMORY.md에 뭘 써야 할지 몰랐는데 → "새 세션에서 Claude에게 가장 먼저 알려줘야 할 것"을 기준으로 채움
- 카카오 발송 방식 변경 이력(REST API → PlayMCP)을 MEMORY.md 결정 사항에 넣어야 한다는 걸 뒤늦게 파악

**완료**

- CLAUDE.md + MEMORY.md + PRD/ 4개 파일 생성

### 공유할만한 인사이트
- **"뺄 것"을 먼저 정하는 게 핵심**: 뭘 PRD로 옮길지 기준이 없으면 결국 CLAUDE.md에 다 들어감. "이 파일은 규칙만, 코드는 PRD로"라는 원칙을 먼저 세우고 나니 분리가 빨라졌음
- **MEMORY.md는 나를 위한 파일**: 클로드에게 설명하는 게 아니라, "다음 세션에서 내가 어디까지 했는지 클로드가 바로 알게 하는 것"이 목적. 결정 사항·현재 단계·다음 할 일 3가지면 충분함
- **마크다운 간 호출 관계 필수**: PRD 파일을 만들어도 CLAUDE.md에서 "이 작업 할 땐 PRD/api.md 참조"라고 명시하지 않으면 Claude는 그 파일의 존재를 모름. 참조 테이블 한 줄이 생각보다 중요함

## 미션2: 고객 페르소나에게 피드백 받기

### Summary
만든 브리핑 봇을 실제로 네이버 블로그를 운영하는 2명에게 직접 보여주고 솔직한 반응을 들었다. "있으면 좋겠다"가 아니라 "지금 당장 쓸 것 같냐"를 기준으로 피드백을 수집했다.

![](attachments/스크린샷%202026-05-31%20오후%205.54.50%201.png)
### 최종 구현 결과물
- 피드백 대상: 일상·맛집 블로거 1명, 리뷰 전문 블로거 1명
- 피드백 수집 방식: 직접 화면 보여주며 구두 인터뷰
- 수집한 피드백 내용 정리본
### 과정 (타임라인별 + 삽질)

**피드백 대상 선정**

- "정말 쓸 사람" 기준으로 선정. 블로그를 주 3회 이상 올리고, 주제 선정에 실제로 시간을 쓰는 사람
- 지인 중 해당하는 2명에게 연락

**피드백 세션**

- 도구 소개 없이 바로 화면 보여주며 "이거 어떻게 쓸 것 같아?"로 시작
- 유도 질문 없이 반응 먼저 관찰

**수집된 피드백**

두 명 모두 네이버 블로그를 주 3회 이상 운영 중인 블로거. 도구 소개 없이 화면만 보여주고 반응을 먼저 관찰했다.

공통 반응은 "아예 주제가 없을 때 초안 잡기에 좋다"였다. 오늘 뭘 써야 할지 막막할 때, 카테고리 선택 몇 번으로 글감 후보가 10개 나오는 구조 자체가 유용하다는 반응. "검색해서 찾는 게 아니라 추천받는 느낌"이라는 말도 나왔다.

구체적인 피드백은 아래와 같았다.

| 항목         | 피드백 A                      | 피드백 B                     |
| ---------- | -------------------------- | ------------------------- |
| 가장 유용한 상황  | 글감이 아예 없을 때, 시작점 잡기        | 주제는 있는데 각도를 못 잡을 때        |
| 아쉬운 점      | 글감 제목이 너무 포괄적, 좀 더 구체적이었으면 | 왜 지금 핫한지 이유가 한 줄인데 더 길었으면 |
| 실제로 쓸 것 같냐 | 매일은 아니고, 막히는 날에 열 것 같다     | 카테고리 선택이 직관적이면 쓸 것 같다     |


### 공유할만한 인사이트
**유즈케이스가 생각보다 좁았다**: "매일 쓰는 블로거의 일상 도구"라고 생각했는데, 피드백 들어보니 "아예 주제가 없을 때 초안 잡는 도구"가 더 정확한 포지셔닝이었음. 타깃 유즈케이스가 명확해지면 프롬프트도, UI도 다르게 설계해야 함
**페르소나 검증은 완성 후보다 초기가 더 유용**: 카테고리 구조를 처음부터 피드백받았으면 설계 단계에서 바꿀 수 있었는데, 완성 후 받으니 재작업 비용이 생김
