## Summary

이번 주 핵심은 두 가지. **(1) "한눈에 들어오게" 화면을 정리**하고, **(2) "여러 명이 쓸 수 있는 구조(각자 키)"로 전환**한 것.

발표 후 멀티유저로 열고 → 찐고객 5명 테스트 → 그 피드백으로 화면을 다듬고 버그를 잡았다. 그러다 "여러 명이 어떻게 쓰게 하지"라는 가장 큰 난제에 부딪혔고, 각자 API 키 입력 방식으로 풀어냈다. "나만 쓰는 것"에서 "남들이 쓸 수 있는 것"으로 제품 단계가 올라간 한 주.

도메인도 career-fit-os → mycareerfit으로 정리

---

## 최종 구현 결과물

**1. 공고 판단 화면 도식화 — "한눈에 보기"**

- 결과 맨 위에 요약 블록: 점수·판정 + 한 문장 결론 + ✓강점/⚠걸리는점.
- 중복 제거(점수가 3번 나오던 것 → 1번), 상세는 "자세히 보기"로 접기.
- 효진(AI 비숙련)의 "글 많아 헷갈린다"가 해결됨.

**2. 자기소개서 초안 (이전 "이력서 초안"에서 정체성 정리)**

- 이력서(사용자가 이미 보유) ≠ 자소서(AI가 도울 영역) 구분.
- 자기소개·핵심경험·지원동기를 복붙 가능한 서술형으로.
- "AI가 만든 초안이에요, 본인 경험과 말투로 다듬어 쓰세요" 안내 문구 추가.

**3. 거르개 정확도 수정 (3건)**

- 필수 요건을 "업종으로 추측"하지 않고 "공고에 명시된 것"만 잡게. (일레븐 사례: 뷰티 회사라고 뷰티 경력 필수로 넘겨짚던 오판 수정)
- 필수 요건 미충족이 점수·판정에 반영되게. (아렌시아: 82점 추천 → 모순 → 수정)
- 필수 미충족 시 "검토 필요"로 판정 (패스 아님 + "그래도 지원" 경로 유지).

**4. 각자 API 키 입력 전환 (이번 주 최대 성과)**

- "내 키 공유 + 비번" → "각자 본인 키 입력(키만 게이트)".
- 사용자가 자기 키·자기 비용으로 씀 → 내 비용 0 → 스폰지클럽에 열 수 있음.
- 입력 시점 검증: 빈 값/형식 불일치는 차단, 유효성 테스트 호출(max_tokens:1). 401=재입력, 429·크레딧=통과(키 유효), 네트워크오류=따로 처리.
- 보안: 키 로깅 금지, 헤더로만 전송. (원래 기획 "각자 키, 각자 비용"으로 복귀)

**5. 부가**

- JD 다중 이미지 업로드 (잡코리아 등 긴 공고 여러 장).
- 링크 가져오기 실패 안내 (노션·피그마 등 못 읽는 링크 → 텍스트·이미지 안내).
- 도메인 변경(mycareerfit) + 옛 주소 redirect.

## 과정 (타임라인 + 삽질)

**1) 도식화 — 추가가 아니라 빼기였다** 처음엔 "점수를 그래프로" 생각 → 아니었음. 진짜 문제는 "내용이 주르륵"이라 **중복 제거 + 접기**가 답. 요약 블록 추가했더니 기존 FIT SUMMARY와 중복돼서 점수가 3번 나옴 → 합침. 점수 폰트 키웠다가 너무 커져서 → 다시 줄임. 교훈: 화면 정리는 "더하기"가 아니라 "빼기".

**2) 커버 문구 — 만들었다가 뺐다 (삽질이지만 의미 있는)** 은영 피드백("수정 문구 줘") 보고 "바로 쓸 수 있는 수정 문구" 기능 추가. → 만들고 보니 기존 "이력서 초안"과 중복. 화면만 복잡해짐. → 제거. 깨달음: 은영이 원한 건 "새 기능"이 아니라 "초안 품질 개선"이었음. 사용자 말의 표면이 아니라 진짜 니즈를 봐야 함.

**3) 자소서 — 딥하게 갔다가 환각 폭탄** "==복붙 수준으로 딥하게" → AI가 그럴듯한 거짓을 지어냄. 직접 읽으며 잡아낸 환각==: "5년간"(임의 기간), "8시간 시차"(근거 없음), "Lancôme·Kiehl's"(지어낸 브랜드명). 하나 막으면 또 나옴(두더지 잡기) → 결국 "안전하지만 식상"으로 방향 전환. 교훈: "딥하게 써라"가 환각의 방아쇠. 분량 욕심이 거짓을 부른다.

**4) 거르개 — 너무 빡세게 vs 너무 느슨하게 사이 조율**

- 일레븐: 뷰티 회사라고 "뷰티 경력 필수" 넘겨짚어 막음 → 과한 거르기 → 수정.
- ==아렌시아: 화장품 필수 명시인데 82점 "지원 추천" → 점수와 필수가 따로 놀던 버그. 진단해보니 점수·판정이 requirement를 아예 안 봤음 → 연결.==
- 패스냐 검토냐 고민 → "인사담당자도 칼같지 않다(강점 세면 예외)"는 현실 반영 → 검토 필요. 교훈: 거르개는 "차단기"가 아니라 "현실을 솔직히 알려주는 판단 보조". 단정(거짓)보다 솔직한 애매함이 낫다.

**5) 각자 키 — 가장 큰 난제, 진단부터** "여러 명이 어떻게 쓰게 하지"가 최대 고민. 구독 결제(개발자 친구 제안)는 무겁고 시기상조 → 각자 키로 먼저. 진단해보니 각자 키 기능은 죽어 있었고("비번"은 출입증일 뿐 호출은 다 내 키로) → 원래 기획으로 복귀. 단계별 구현(하위호환→프론트→검증→정리)으로 라이브 안 깨지게. 성공.

**6) 마지막 삽질 — 데이터 날아감** 도메인 바꾸니 그동안 정리한 앱 현황이 다 날아감. → "관리는 엑셀로" 결정이 옳았음을 몸으로 확인. 핵심 데이터는 엑셀에 있었음.

## 공유할 만한 인사이트

**1. 화면 정리는 더하기가 아니라 빼기다.** 요약을 "추가"하면 중복이 생긴다. 진짜 정리는 중복 제거 + 접기. 기능을 넣을 때마다 화면이 무거워진다 — 그게 기능 추가의 숨은 비용.

**2. 사용자 말의 표면이 아니라 진짜 니즈를 봐라.** "수정 문구 줘" = "새 기능 만들어줘"가 아니라 "기존 초안이 부실해"였다. 새로 만들기 전에 "이미 있는 걸로 풀리나?"를 먼저 보자.

**3. AI 글쓰기는 "구체적=환각 위험 / 안전=식상"의 트레이드오프.** 딥하게 쓸수록 그럴듯한 거짓이 섞인다. 거짓이 치명적이니 안전을 택하고, 구체화는 사용자 몫으로 안내. AI는 막막함을 없애는 출발점, 완성은 사용자가.

**4. 거르개는 차단기가 아니라 판단 보조다.** 현실(필수 요건도 칼같지 않음)이 애매하면, OS도 솔직하게 애매함을 전하는 게 맞다. 거짓 단정보다 정직한 "검토 필요"가 낫다. 단, "그래도 결정은 너"의 경로는 항상 연다.

**5. 검증과 실행의 타이밍 — What과 When을 구분하라.** 구독 결제는 필요하다(What 맞음). 단 "돈 낼 의향" 확인 후다(When). 무거운 걸 불확실할 때 만들지 않는다. 각자 키로 먼저 검증하고, 신호 보고 결정.

**6. 사용자에게 너무 많이 요구하면 안 쓴다.** "정보 많이 넣으면 정확하다"는 사실이지만, 그걸 요구사항으로 들이밀면 진입장벽. "엄두 안 나는 걸 없애준다"는 제품이 입력부터 엄두 나게 하면 본말전도.

**7. 앱 데이터는 휘발된다 — 핵심은 들고 나가게(엑셀).** 도메인 바꾸니 데이터 날아감을 직접 겪음. "관리는 엑셀로" 결정의 근거를 몸으로 확인.

**8. 내가 직접 사용자로 써봐야 빈틈이 보인다.** 효진의 "주르륵", 자소서 환각, 키 입력 UX, 노션 링크 막힘, 거르개 오판 — 전부 직접 써보다 발견. 만드는 사람이면서 쓰는 사람의 눈을 가진 게 강점.
