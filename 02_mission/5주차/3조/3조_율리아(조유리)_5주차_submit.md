## 미션1: 삽질을 줄이는 나만의 Agentic OS 만들기

### Summary

스폰지클럽 1기 동안 제가 만들고 싶었던 것은 단순한 앱 하나가 아니라, **내 목적을 agent가 실행 가능한 workflow로 바꾸는 나만의 OS**였습니다.

처음에는 “내가 개입하지 않아도 agent가 실제 업무를 수행하고, 나는 결과를 검수만 하면 되지 않을까?”라는 기대에서 출발했습니다. Paperclip도 써보고, Hermes도 붙여보고, agent에게 업무를 위임하는 여러 방식을 실험했습니다.

하지만 해보니 핵심은 agent 성능이 아니었습니다. agent에게 일을 맡기기 전에, 제가 목적과 범위와 성공 기준을 충분히 구체화해야 했습니다. 그래서 SDD 흐름을 기반으로 Interview, Clarify, Spec, Plan, Tasks, Execute, Verify가 문서와 agent profile로 이어지는 workflow를 만들었습니다.

결국 이 미션의 핵심 결과는 “AI에게 알아서 해달라고 맡기는 방법”이 아니라, **AI가 실패하기 어렵게 일의 길을 먼저 깔아주는 방법**을 정리한 것입니다.

### 최종 구현 결과물

1. **SDD 따라하기 가이드**
   - 막연한 아이디어를 바로 구현하지 않고, 먼저 `spec`, `plan`, `tasks` 같은 문서로 고정하는 흐름을 정리했습니다.
   - agent가 다음 단계에서 무엇을 읽고 무엇을 해야 하는지 알 수 있도록, 대화를 파일 산출물로 남기는 방식을 만들었습니다.

2. **Hermes agent profile workflow**
   - profile을 단순한 말투나 성격이 아니라, 각 단계의 역할 설명서로 정의했습니다.
   - interviewer는 목적을 질문으로 구체화하고, planner는 구현 계획을 만들고, executor는 승인된 task만 실행하고, verifier는 독립적으로 검수하는 식으로 역할을 나눴습니다.

3. **Paperclip 기반 control plane**
   - issue, 상태, 승인, handoff를 남기는 업무 흐름의 중심으로 Paperclip을 사용했습니다.
   - 긴 계획, 실행 기록, 검수 결과는 파일로 남기고, Paperclip은 현재 상태와 연결 지점을 관리하는 역할로 정리했습니다.

4. **Clarify + 검수 agent 반복 루프**
   - Clarify를 한 번 지나가는 단계가 아니라, 필요할 때마다 다시 돌아가는 질문 루프로 봤습니다.
   - OMC 같은 skill 기반 agent를 붙여서 `spec`, `plan`, `tasks`, 구현 결과가 나올 때마다 verifier, security-reviewer, critic 같은 검수 agent가 중간 확인을 할 수 있는 구조로 정리했습니다.

### 과정 (타임라인별 + 삽질)

**1단계. 처음 기대: agent가 일하고 나는 검수만 하기**

처음에는 목표만 잘 말하면 agent가 알아서 업무를 수행하고, 저는 최종 결과만 검수하면 될 거라고 생각했습니다. agentic workflow를 통해 실제 업무 자동화가 가능할 것 같았고, Paperclip과 Hermes를 붙이면 업무 control plane이 만들어질 것이라고 기대했습니다.

**삽질:** 목표가 너무 넓고 애매하면 agent는 각자 다르게 해석했습니다. 어떤 agent는 범위를 넓게 잡고, 어떤 agent는 중요한 맥락을 놓치고, 어떤 agent는 검증이 부족한 상태에서 완료했다고 말했습니다.

**2단계. Paperclip/Hermes 실험: 도구보다 구조가 먼저라는 걸 깨달음**

여러 도구를 붙여봤지만, 도구를 붙인다고 자동으로 좋은 workflow가 생기지는 않았습니다. Paperclip은 상태를 남기는 데 좋고, Hermes는 실행 흐름을 만들 수 있지만, 그 안에 들어갈 역할과 문서 구조가 없으면 agent가 안정적으로 움직이지 않았습니다.

**삽질:** control plane을 먼저 만들면 자동화가 될 줄 알았는데, 실제로는 control plane에 태울 “잘게 쪼개진 일”이 먼저 필요했습니다.

**3단계. SDD 도입: 바로 구현하지 않고 먼저 문서화하기**

그래서 SDD 흐름을 가져왔습니다. 아이디어를 바로 코드로 보내지 않고, Interview로 목적을 구체화하고, Constitution으로 지켜야 할 원칙을 정하고, Spec으로 무엇을 만들지 고정하고, Plan과 Tasks로 실행 단위를 쪼개는 방식입니다.

**삽질:** 처음에는 문서를 “사람이 보기 위한 정리” 정도로 생각했습니다. 그런데 실제로는 문서가 다음 agent가 읽고 행동하는 입력값이 되어야 했습니다. 문서가 애매하면 다음 agent도 애매하게 움직였습니다.

**4단계. Clarify 재발견: 질문은 한 번이 아니라 계속 돌아야 함**

Clarify는 생각보다 중요했습니다. 비개발자는 보통 자신이 무엇을 빠뜨렸는지 모르는 상태에서 시작합니다. 그래서 Spec을 쓸 때만 질문하는 것이 아니라, Plan을 짜다가도, Tasks를 나누다가도, Execute 중에도 애매함이 보이면 다시 Clarify로 돌아가야 했습니다.

**삽질:** Clarify를 선형 단계 중 하나로 보면 부족했습니다. 실제 업무에서는 중간에 계속 새로운 불확실성이 나오기 때문에, Clarify는 필요할 때마다 돌아가는 루프에 가까웠습니다.

**5단계. Executor와 Verifier 분리**

처음에는 실행한 agent가 스스로 결과를 설명하고, 그 설명을 그대로 믿는 구조가 되기 쉬웠습니다. 하지만 만든 사람이 자기 결과를 승인하면 위험합니다. 그래서 executor와 verifier를 분리했습니다.

**삽질:** executor가 “완료했다”고 말하는 것과 실제로 요구사항을 만족하는 것은 달랐습니다. diff, 테스트 결과, scope creep, secret 노출, spec 일치 여부를 별도의 눈으로 다시 봐야 했습니다.

**6단계. OMC 같은 검수 agent를 중간마다 붙이기**

마지막 검수만으로는 부족하다고 느꼈습니다. Spec이 나오면 요구사항 빈틈을 보고, Plan이 나오면 실행 순서와 위험을 보고, 구현 후에는 테스트와 보안 위험을 보는 식으로 중간 산출물마다 검수가 필요했습니다.

**삽질:** 검수를 마지막에 몰아두면 앞 단계의 애매함이 뒤에서 크게 터졌습니다. 그래서 analyst, verifier, security-reviewer, critic 같은 agent를 중간마다 붙이는 구조가 더 안전했습니다.

**7단계. Profile을 역할 설명서로 재정의**

마지막으로 Hermes profile을 “친절한 말투”나 “똑똑한 성격”이 아니라 역할 설명서로 다시 정의했습니다. 각 profile에는 입력, 출력, 중지 조건, 검증 조건, 금지 행동이 있어야 했습니다.

**삽질:** profile을 prompt 조각처럼 만들면 재사용성이 낮았습니다. 반대로 역할과 산출물이 분명하면, profile 하나가 workflow의 안정적인 단계가 됐습니다.

### 공유할만한 인사이트

1. **agentic workflow의 병목은 실행력이 아니라 계획의 구체성이다.**

agent가 똑똑한 것보다, agent에게 주는 계획이 얼마나 구체적인지가 더 중요했습니다. 입력, 출력, 범위, 성공 기준, 중지 조건, 검증 조건이 분명할수록 agent는 안정적으로 일했습니다.

2. **자동화는 자유를 주는 일이 아니라 실패하기 어렵게 만드는 일이다.**

agent에게 “알아서 해줘”라고 하는 것은 자동화가 아니었습니다. 자동화는 agent가 따라갈 길을 만들고, 그 길에서 벗어나기 어렵게 만드는 일이었습니다.

3. **문서는 보고서가 아니라 실행 인터페이스다.**

`spec.md`, `plan.md`, `tasks.md`는 사람에게 보여주기 위한 정리 문서가 아니라, 다음 agent가 읽고 행동하기 위한 입력값입니다. agent 시대의 문서는 곧 실행 인터페이스입니다.

4. **Clarify는 필요할 때마다 돌아가는 질문 루프다.**

질문은 초반에만 하는 것이 아니었습니다. 구현 중에 애매함이 생기면 다시 질문하고, 그 답을 스펙과 계획에 반영해야 workflow가 흔들리지 않았습니다.

5. **검수는 마지막이 아니라 중간마다 들어가야 한다.**

완성된 결과만 보는 것보다, spec, plan, tasks, diff가 나올 때마다 다른 agent가 검수하는 편이 훨씬 안전했습니다. 특히 보안, 권한, 개인정보, 운영 위험은 중간에 질문하지 않으면 뒤늦게 발견되기 쉽습니다.

6. **Profile은 성격이 아니라 역할 설명서다.**

좋은 profile은 “친절하게 답해줘”가 아니라 “무엇을 읽고, 무엇을 남기고, 언제 멈추고, 무엇을 검수하고, 무엇을 하지 말아야 하는지”를 적은 작업 약속에 가깝습니다.

7. **비개발자에게 필요한 것은 코딩 지식만이 아니라 좋은 질문 구조다.**

장기적으로는 Interview와 Clarify를 더 강화해서, 비개발자도 보안, 운영, 롤백, 비용, 장애 대응 같은 질문을 놓치지 않게 만들고 싶습니다. 그렇게 되면 비개발자도 단순한 데모가 아니라, 개발자가 만든 것처럼 완성도와 운영성을 갖춘 프로덕트에 가까워질 수 있습니다.

8. **나만의 OS는 앱 하나가 아니라 반복 가능한 사고 구조다.**

중요한 것은 특정 도구가 아니라, 어떤 목적이 생겼을 때 그것을 질문, 스펙, 계획, 작업, 실행, 검수로 바꾸는 반복 가능한 구조였습니다. 이 구조가 있으면 Codex, Claude, OpenCode 같은 worker는 바뀌어도 workflow는 유지될 수 있습니다.
