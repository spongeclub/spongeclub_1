# 3주차 과제 — Iny

## 미션1: 내 고객은 누구고 왜 쓰는가 — 클로드 코드로 프로덕트 구현하기

### Summary

**"Inked — 잉크로 새겨진, 누적되는 포트폴리오"** 웹사이트를 클로드 코드 터미널로 만들었다. 텍스트만 붙여넣으면 7개 필드 카드로 누적되는 1인 포트폴리오 사이트.

- **출발점**: 원래 비전은 본업 💼 + 스폰지클럽 📚 + 일상 🏠을 한 번에 관리하는 작은 OS였는데, 한 번에 그걸 다 짓는 건 무리. → "가장 귀찮았던 것부터" = **포트폴리오 업데이트**로 범위를 좁혔다. (큰 OS 비전은 "나를 중심으로 만들어 → 같은 고민의 사용자로 확장"이라는 다음 단계로 살려둠)
- **내 고객은 누구**: 1차 — 본인 + 같은 직군 주니어 / 스폰지클럽 동료. 2차 — 포트폴리오를 자주 업데이트해야 하는 카피라이터·콘텐츠 크리에이터·기획자.
- **왜 쓰는가**: 매 프로젝트마다 회고·정리·포트폴리오 업데이트가 미뤄지는 페인. 한 번 포트폴리오 만들면 양식·디자인에 갇혀서 추가가 부담됨. → "텍스트만 던지면 양식대로 정리해서 누적해주는 사이트"가 답.

### 공유할만한 인사이트

- **스펙(`product-spec.md`)을 먼저 쓰는 게 시간 가성비 1등.** Phase 1~5 + 핵심 UI 구조 + Tech Stack + 7개 필드 정의가 전부 미리 있으니까 클로드 코드가 헛돌지 않았다. 스펙 없이 시작했으면 같은 결과 만드는 데 3배는 걸렸을 것.
- **Phase별 확인 게이트가 진짜 효과 있다.** "각 Phase 끝날 때마다 결과 보고하고 확인받아줘" 한 줄이 컸다. 한 번에 다 만들고 나서 디자인 안 예쁘다고 뒤집는 것보다 훨씬 적은 리소스로 방향 틀 수 있었음.
- **비싼 부품(AI 호출)은 빼도 시스템은 굴러간다.** 핵심은 "7개 필드로 정리된 카드"라는 *양식* 자체였고, 그 양식만 강제하면 입력 수단은 무엇이든(직접 입력 / AI / PDF…) 끼울 수 있는 구조였다. 비용 문제 만났을 때 입력만 갈아끼우고 나머지 다 살린 게 가능했던 이유.
- **"진짜 웹사이트처럼"이라는 모호한 피드백을 어떻게 풀까.** 정신없다 = 첫 화면에 입력창이 보임. 토스/에디토리얼 톤이 정답이라기보다 **"작업물을 먼저 보여주는 구조"**가 정답이었다. UI 톤은 후순위.
- **PDF 자동 추출은 환경 의존성이 크다.** poppler 설치 안 되어 있으면 그냥 안 됨. 다음엔 처음부터 "내가 직접 적어줄게" 모드를 디폴트로 두는 게 빠를 듯.
- **"옅게 표시" 같은 작은 규칙 하나가 카드 품질을 살린다.** 빈 필드를 `—`로 보여주는 룰을 spec에 미리 정해둔 덕분에 카드가 어떤 입력이 와도 가지런해짐.

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

### Summary

미션1을 만들면서 **실제로 적용된 하네스와 오케스트레이션**을 정리. 내 식대로의 정의:
- **하네스(Harness) = 양식·규칙으로 산출물 품질을 보장하는 장치**
- **오케스트레이션(Orchestration) = Phase 단위로 끊고 확인 게이트를 두는 진행 방식**

둘 다 "AI를 어디까지 풀어두느냐"를 결정하는 장치. 자유도가 클수록 결과가 들쭉날쭉하므로 미리 좁혀두는 게 핵심.

### 최종 구현 결과물

**Harness — 규칙·환경 6가지**

| 규칙 | 어디에 적용 |
|---|---|
| 출력 양식 강제 | Claude system prompt에 "7개 필드 JSON만 응답" 명시 |
| 카테고리 강제 매핑 | ASK/ACT/ADVANCE 중 하나 — 사용자가 드롭다운에서 미리 고르고 모델은 분류 안 함 |
| 누락 필드 처리 | 빈 필드는 빈 문자열로 반환, 화면에서 `—`로 옅게 표시 |
| 디자인 토큰 통일 | CSS 변수 `--accent` 하나로 — 헤더·태그·버튼·배지 전부 연동 |
| Server-side 키 격리 | API 키는 서버 라우트(`/api/ingest`)에서만 사용. 클라이언트에 노출 X. `.env.local` + Vercel 환경변수 |
| 시드 vs 사용자 데이터 격리 | `inked.seeded` 플래그로 첫 방문 시 1회만 시드. 사용자 입력은 별도 보존 |

**Orchestration — 단계 흐름**

```
[프롬프트 설계] product-spec.md + Phase 1~5 분할 + 각 Phase 끝에 확인 게이트
        ↓
[Phase 1] 셋업 → 보고 → ✅
        ↓
[Phase 2] 데이터/AI 레이어 → 보고 → ✅ (PDF 삽질 → 우회)
        ↓
[Phase 3] UI 컴포넌트 → 보고 → ✅
        ↓
[Phase 4] 동작 테스트 → 보고 → ✅ (키 없음 정상 인식)
        ↓
[Phase 5] README + 배포 안내
        ↓
[피벗] API 비용 → AI 호출 빼고 입력 폼 + 시드 직접 작성
        ↓
[디자인 반복] 1차 톤 → 2차 폰트 → 3차 시각화 추가
```

**적용된 메타 룰 3가지**
- *"시간 부족 시 우선순위 낮은 기능은 README 다음 단계로 미룬다"* → 카드 수정 버튼, 이미지 업로드, Supabase 연동을 실제로 명시적으로 미룸
- *"코드는 단순하게. 추상화는 나중에."* → page.tsx 클라이언트 컴포넌트 한 덩어리로 시작
- *"비싸진 부품은 갈아끼울 수 있어야 한다"* → AI 호출 코드 살려두고 입력 폼만 교체

### 과정 (타임라인별 + 삽질)

- **프롬프트 초기 설계** `product-spec.md` 따로 + Phase 5단계 + "각 Phase 끝에 확인" 한 줄. 이 한 줄이 사실상 오케스트레이션 본체였음.
- **삽질 1 — PDF 자동 추출 막힘** → "내가 직접 보낼게"로 우회. 하네스가 견고하면 입력 수단이 막혀도 시스템은 안 죽음을 체감.
- **삽질 2 — API 키 없는 상태 가드** ingest 500 떨어지면 alert 후 카드 추가 막는 가드가 있었음. "정상 동작인데 사용자 입장에선 오류"로 보이는 모호함 → 입력 폼 모드로 갈아끼울 때 이 부분이 매끄럽게 됐음.
- **삽질 3 — 시드 hydration mismatch** `new Date().toISOString()`을 시드에 쓰면 SSR/CSR 시간이 달라서 React가 경고 → `SEED_TS = "2026-05-24T00:00:00.000Z"` 고정 상수로 해결.
- **삽질 4 — 디자인 톤 한 번에 못 잡음** 세리프로 갔다가 다시 산세리프로. 디자인 톤은 한 번에 정하기 어려우니 컴포넌트는 토큰 기반(`--accent`)으로 짜둬야 갈아끼우기 쉬움.

### 공유할만한 인사이트

- **하네스 = 양식 규칙, 오케스트레이션 = 단계 게이트.** 같은 작업도 이 두 가지 있고 없고에 따라 결과 품질이 다르다.
- **Phase 게이트는 비용 절감 장치이기도 하다.** 잘못 가고 있으면 한 Phase 안에서 발견되니까 다음 Phase에서 코드가 폭발할 일이 없다.
- **하네스가 있으면 비용/환경 제약을 만났을 때 부분 교체가 쉽다.** Inked는 "AI 호출 빼기 + 직접 입력 + 시드 11개"로 갈아끼웠는데, *양식(7필드)·저장소(localStorage)·UI(섹션 3개)* 그대로 살아남았다.
- **CSS 변수 하나가 디자인 토큰 하네스.** `--accent` 하나로 묶어둔 게 컬러 피커 1초 만에 만든 비결.
- **"한 번에 다 만들지 마라"가 진짜 룰 1번.** 5단계로 끊은 게 디자인 2번 뒤집고 비용 피벗 1번 한 것의 비용을 감당 가능 수준으로 묶어줬다.
