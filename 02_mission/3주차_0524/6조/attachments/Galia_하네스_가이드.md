## 이 문서는 뭔가

AI 에이전트에게 "앱 만들어줘"라고 하면, 잘 되기도 하고 엉망이 되기도 한다.
그 차이는 AI 모델의 성능이 아니라, **내가 에이전트에게 어떤 환경과 규칙을 깔아줬느냐**에 달려 있다.

그 "환경과 규칙의 총체"를 **하네스(harness)**라고 부른다.

### 마구와 기수

하네스를 경주마의 **마구(馬具)**에 비유하면, 역할이 선명해진다.

**🐴 말 = AI 에이전트.** 능력은 충분하다. 하지만 혼자 두면 아무 방향으로나 달린다.

**🪢 마구(하네스) = 에이전트에게 거는 장비.**
안장, 고삐, 등자처럼 말에 채워두면 말이 알아서 느끼는 것들이다.
프로젝트 지침, 기능 목록, NOT-DO 리스트, PROGRESS.md, 검증 명령어 — 이런 것들이 마구다. 한번 잘 세팅해두면 에이전트가 매번 읽고 따른다.

**🧑 기수(騎手) = 나.**
마구를 채우는 것만으로는 말이 목적지에 도착하지 않는다. 기수가 해야 할 일이 있다:
- **방향을 정한다** — 어디로 갈지, 뭘 먼저 할지
- **고삐를 당긴다** — 범위를 벗어나면 멈추게 한다
- **눈으로 확인한다** — 결과를 직접 보고, 이상하면 수정 지시한다
- **속도를 조절한다** — 한 번에 하나씩, 급하게 몰지 않는다
- **길을 기억한다** — 어디까지 왔는지, 다음에 어디로 갈지 판단한다

이 문서에서 🤖 표시가 된 항목은 **마구(에이전트에게 세팅하는 것)**이고,
🧑 표시가 된 항목은 **기수의 기술(내가 직접 판단하고 확인하는 것)**이다.

마구가 좋으면 기수의 일이 편해지고, 기수가 능숙하면 마구가 단순해도 잘 달린다.
하지만 **마구 없는 기수**(규칙 없이 매번 감으로 확인)도,
**기수 없는 마구**(문서만 잘 써놓고 결과를 안 봄)도 결국 실패한다.
둘 다 있어야 한다.

---

단, 하네스는 "마크다운에 규칙을 잘 적어두면 끝"이 아니다.
하네스는 **두 축**으로 돌아간다:

- **🤖 에이전트에게 주는 축 (마구)**: 규칙, 맥락, 검증 방법을 문서로 제공한다
- **🧑 내가 직접 하는 축 (기수)**: 결과를 눈으로 확인하고, 방향을 판단하고, 다음을 결정한다

에이전트가 아무리 잘해도, 내가 확인하지 않으면 엉뚱한 방향으로 간다.
내가 아무리 잘 확인해도, 에이전트에게 규칙을 안 깔아주면 확인할 게 너무 많아진다.
**둘이 같이 돌아야 하네스다.**

이 문서는 내가 바이브코딩할 때 적용할 하네스 원칙과 체크리스트를 기록한 것이다.
각 항목마다 🤖(에이전트가 할 일)과 🧑(내가 할 일)을 구분해서 적는다.

## 1. 핵심 마인드셋: 실패하면 모델 탓이 아니라 하네스를 점검한다

에이전트가 이상한 결과를 내놓았을 때, 첫 반응이 "이 AI 멍청하네"가 되기 쉽다.
하지만 대부분의 경우 문제는 이렇다:

- 내가 뭘 원하는지 **충분히 구체적으로 말하지 않았다**
- 프로젝트의 맥락(어떤 기술을 쓰는지, 어떤 구조인지)을 **알려주지 않았다**
- 에이전트가 스스로 "잘 됐는지" **확인할 방법을 주지 않았다**
- 이전 대화에서 했던 결정이 **다음 대화로 전달되지 않았다**

**원칙: 같은 에이전트가 비슷한 작업에서 성공한 적이 있다면, 문제는 하네스에 있다.**

비유하자면 경주마에게 마구(안장, 고삐, 등자)를 안 채우고 "달려!"라고 하는 것과 같다.
말이 못 달리는 게 아니라, 타는 사람이 준비를 안 한 거다.

## 2. 하네스의 5가지 구성 요소

하네스는 하나의 프롬프트가 아니다. 다섯 가지 역할이 모두 갖춰져야 제대로 작동한다.
주방 비유로 생각하면 이해하기 쉽다.

### ① 지시 (레시피 선반)
**= 에이전트에게 "이 프로젝트가 뭔지, 규칙이 뭔지" 알려주는 것**

- 프로젝트가 뭘 하는 앱인지 한 줄 설명
- 기술 스택 (React, Supabase, Tailwind 등)
- 절대 어기면 안 되는 규칙 ("Tailwind만 써", "한국어 UI", "Supabase 인증 사용")
- 폴더 구조 설명

🧑 **내가 할 일**: 프로젝트 지침/CLAUDE.md를 작성한다. 뭘 적어야 할지 모르겠으면 에이전트에게 "이 프로젝트의 지침서를 만들어줘"라고 요청한다.
🤖 **에이전트가 할 일**: 지침을 읽고 따른다. 지침과 충돌하는 상황이 생기면 임의로 판단하지 말고 나에게 물어본다.

👉 실천: Claude 프로젝트의 커스텀 지침, 또는 프로젝트 폴더 안에 `CLAUDE.md` 파일로 작성

### ② 도구 (칼 랙)
**= 에이전트가 실제로 뭘 할 수 있는지**

- 파일을 읽고 쓸 수 있는가?
- 터미널 명령어를 실행할 수 있는가?
- 웹 검색을 할 수 있는가?
- 외부 서비스(DB, API)에 접근할 수 있는가?

🧑 **내가 할 일**: 코드 실행, 파일 생성, MCP 연결 등이 켜져 있는지 확인한다. 에이전트가 "이 도구가 없어서 못 하겠다"고 하면 설정을 확인해준다.
🤖 **에이전트가 할 일**: 사용 가능한 도구를 파악하고, 없는 도구가 필요한 경우 나에게 알려준다. 있는 도구만으로 해결 방법을 찾는다.

👉 실천: Claude에서 코드 실행, 파일 생성이 켜져 있는지 확인. MCP 연결 확인.

### ③ 환경 (가스레인지)
**= 프로젝트가 제대로 돌아가는 상태인지**

- 의존성이 다 설치되어 있는가?
- 환경변수(.env)가 설정되어 있는가?
- 빌드가 깨져 있진 않은가?

🧑 **내가 할 일**: 에이전트가 "환경 문제입니다"라고 하면, 환경변수나 API 키 등 민감한 정보는 내가 직접 설정한다.
🤖 **에이전트가 할 일**: 작업 시작 전에 현재 환경 상태를 점검하고, 문제가 있으면 나에게 보고한다. 환경 문제로 삽질하기 전에 먼저 알려준다.

👉 실천: 새 세션을 시작할 때 "먼저 현재 프로젝트 상태를 확인해줘"로 시작

### ④ 상태 관리 (준비 스테이션)
**= 이전 세션에서 뭘 했는지 기억하게 만드는 것**

AI 에이전트는 새 대화를 시작하면 이전 대화를 모른다.
30분 넘는 작업, 여러 세션에 걸친 작업이면 반드시 필요하다.

🧑 **내가 할 일**: 세션 끝날 때 에이전트에게 정리를 시킨다. 정리된 내용이 맞는지 훑어보고, 빠진 게 있으면 추가한다. 다음 세션 시작할 때 이 파일을 읽으라고 지시한다.
🤖 **에이전트가 할 일**: 요청받으면 진행 상황을 PROGRESS.md에 정리한다. 다음 세션에서 이 파일을 읽고 이어서 작업한다.

👉 실천: 세션이 끝날 때마다 에이전트에게 요청한다:
> "지금까지 한 것, 진행 중인 것, 남은 것을 PROGRESS.md에 정리해줘"

다음 세션 시작할 때:
> "PROGRESS.md 읽고 이어서 작업해줘"

### ⑤ 피드백 / 검증 (품질 확인 창)
**= 에이전트가 "잘 됐는지" 스스로 확인할 수 있는 장치**

이게 없으면 에이전트는 코드를 쓰고, 자기가 보고, "괜찮은 것 같다" 하고 끝낸다.
답안지 없이 시험을 치르고 "잘 본 것 같다"라고 말하는 것과 같다.

🤖 **에이전트가 할 일**: 작업 완료 후 빌드/실행해서 에러 확인, 기존 기능 점검, 완료 기준 대조. 결과를 나에게 보고한다.
🧑 **내가 할 일**: 에이전트의 보고만 믿지 않는다. **직접 실행해보고 눈으로 확인한다.** 에이전트가 "됩니다"라고 해도, 실제로 버튼을 눌러보고, 화면을 확인하고, 이상한 부분이 있으면 짚어준다. 이게 하네스에서 사람이 하는 가장 중요한 역할이다.

👉 실천:
- "완료 후 반드시 빌드해서 에러가 없는지 확인해"
- "완료 후 브라우저에서 직접 실행해보고 결과를 알려줘"
- "기존 기능이 깨지지 않았는지 전체 앱을 한번 점검해줘"

## 3. 기능 목록: "완료"의 기준을 내가 정해준다

에이전트가 가장 많이 저지르는 실수: **"완료했습니다"라고 했는데 실제로는 절반만 된 상태**.

이유는 간단하다. "완료"가 뭔지 알려주지 않았기 때문이다.

### 나쁜 요청
> "할일 앱 만들어줘"

### 좋은 요청
> "할일 앱을 만들어줘. 완료 기준은 다음과 같아:
> - 할일 추가, 수정, 삭제가 되어야 함
> - 완료 체크박스가 있어야 함
> - 데이터가 새로고침해도 유지되어야 함
> - 모바일에서도 보기 좋아야 함
> - 빌드 에러가 없어야 함"

👉 실천: 작업을 시작하기 전에 **기능 목록(feature list)**을 먼저 작성한다.
에이전트에게 직접 만들게 해도 좋다:
> "이 앱에 필요한 기능 목록을 먼저 만들어줘. 각 기능의 완료 기준도 포함해."

그리고 기능이 구현될 때마다 상태를 업데이트한다:
- ✅ 완료됨
- 🔧 작업 중
- ⬜ 아직 안 함

## 4. 작업 범위 제한: 한 번에 하나씩만 시킨다

에이전트에게 "앱 전체를 만들어줘"라고 하면 여기저기 손대다가 하나도 제대로 완성하지 못한다.
이걸 "과도하게 손대고 끝맺지 못하는(overreach & under-finish)" 문제라고 한다.

**원칙: 하나의 기능을 완성하고 → 확인하고 → 다음으로 넘어간다.**

### 나쁜 방식
> "전자상거래 사이트 전체를 만들어줘"

### 좋은 방식
> "1단계: 상품 목록 페이지부터 만들자. 완료 기준은 ..."
> (확인 후)
> "2단계: 장바구니 기능을 추가하자. 완료 기준은 ..."

👉 실천: 큰 프로젝트는 반드시 단계별로 쪼갠다. 에이전트에게 쪼개달라고 해도 된다:
> "이 프로젝트를 5~7단계로 나눠줘. 각 단계별로 뭘 만들고, 완료 기준이 뭔지 정리해줘."

## 4.5. "하지 않을 것"을 정의한다 (NOT-DO 리스트)

> 💡 이기적공유회 인사이트: 할 것보다 하지 않을 것을 정의하는 게 더 강력하다.

에이전트에게 "이걸 해줘"만 말하면, 에이전트는 잘하려는 의욕이 넘쳐서 **요청하지 않은 것까지 "개선"한다.**
기존 코드 구조를 멋대로 바꾸고, 작동하던 로직을 리팩토링하고, 안 시킨 기능을 슬쩍 추가한다.

"할 것"은 해석의 여지가 있지만, **"하지 마"는 명확하다.** 울타리를 세우는 것이다.

### 왜 "하지 마"가 "해라"보다 강력한가

"검색 기능을 추가해"라고 하면 에이전트는 창의적으로 해석한다 — 검색 UI도 바꾸고, 관련 없는 파일도 손대고, 데이터 구조도 슬쩍 바꿀 수 있다. 하지만 "기존 파일 구조를 바꾸지 마"는 오해의 여지가 없다. 에이전트의 행동에 명확한 벽을 세우는 거다.

### 작업할 때 반드시 붙여야 할 NOT-DO 리스트

매 작업 지시마다, "할 것" 아래에 **"하지 않을 것"**을 같이 적는다:

```
[할 것]
- 사용자 프로필 페이지를 추가해줘
- 이름, 이메일, 프로필 사진을 표시

[하지 않을 것 ⛔]
- 기존 파일/폴더 구조를 변경하지 마
- 이미 작동하는 다른 페이지의 코드를 수정하지 마
- 새로운 라이브러리를 추가하지 마 (기존 것만 사용)
- 데이터베이스 스키마(테이블 구조)를 바꾸지 마
- 디자인 시스템(색상, 폰트, 컴포넌트 스타일)을 바꾸지 마
```

### 나의 기본 NOT-DO 리스트 (매번 적용)

프로젝트마다 달라지는 부분도 있지만, 거의 항상 적용되는 것들:

| ⛔ 하지 않을 것 | 이유 |
|----------------|------|
| 기존 파일/폴더 구조를 바꾸지 마 | 에이전트가 "더 깔끔하게" 정리한다며 멀쩡한 구조를 엉망으로 만든다 |
| 작동하는 코드를 리팩토링하지 마 | 고치려다 멀쩡한 걸 깨뜨린다 |
| 안 시킨 기능을 추가하지 마 | "이것도 있으면 좋을 것 같아서"라며 범위를 키운다 |
| 기존 스타일/디자인을 바꾸지 마 | 한 곳 고치면 다른 곳이 틀어진다 |
| 새 라이브러리를 임의로 설치하지 마 | 의존성이 꼬이면 전체가 깨진다 |
| 확인 없이 파일을 삭제하지 마 | 돌이킬 수 없다 |
| 환경 설정(.env 등)을 건드리지 마 | 인증, DB 연결 등 핵심 설정이 날아간다 |

### 실전 프롬프트

```
이번 작업의 범위:
- [할 것을 적는다]

⛔ 절대 하지 않을 것:
- 기존 파일 구조를 변경하지 마
- 이미 작동하는 다른 기능의 코드를 수정하지 마
- 새 라이브러리를 설치하지 마
- 내가 언급하지 않은 기능을 추가하지 마
- 확인 없이 파일을 삭제하지 마

이 규칙을 어기려면 반드시 나한테 먼저 물어봐.
```

### 프로젝트 지침에 넣을 영구 NOT-DO

프로젝트 커스텀 지침이나 CLAUDE.md에 아예 박아두면, 매번 안 적어도 된다:

```
## 절대 규칙 (모든 작업에 적용)
- 기존 파일/폴더 구조를 임의로 변경하지 않는다
- 작동 중인 기능의 코드를 건드리지 않는다
- 새 패키지/라이브러리를 임의로 설치하지 않는다
- 요청하지 않은 기능을 추가하지 않는다
- 위 규칙을 어겨야 할 상황이면, 먼저 이유를 설명하고 허락을 받는다
```

> 핵심: **"할 것"은 방향을 알려주고, "하지 않을 것"은 울타리를 세운다.**
> 에이전트는 울타리가 없으면 반드시 밖으로 나간다.

## 5. 세션 연속성: 대화가 끊겨도 맥락이 살아있게

바이브코딩에서 가장 짜증나는 순간: 새 대화를 열었더니 에이전트가 프로젝트를 처음 보는 것처럼 행동한다.

이유: AI는 새 세션마다 기억이 리셋된다.

### 해결책: 진행 기록을 파일로 남긴다

세션이 끝나기 전에 항상:
> "지금까지의 진행 상황을 정리해줘. 포함할 내용:
> - 완료된 기능
> - 현재 작업 중인 것과 어디까지 했는지
> - 남은 작업
> - 주의사항이나 결정 사항
> - 다음 세션에서 바로 이어가려면 뭘 해야 하는지"

이걸 `PROGRESS.md`나 프로젝트 지침에 기록해두면 된다.

## 6. 진단 루프: 문제가 생기면 어디가 고장났는지 찾는다

에이전트가 실패했을 때, "다시 해봐"만 반복하면 같은 실패가 반복된다.
대신 **5가지 구성 요소 중 어디가 문제인지** 진단한다.

| 증상 | 원인 구성 요소 | 처방 | 누가 |
|------|--------------|------|------|
| 요청한 것과 다른 걸 만듬 | ① 지시 부족 | 기능 목록과 완료 기준 작성 | 🧑 내가 작성, 🤖 초안 도움 |
| 프로젝트 컨벤션을 안 따름 | ① 지시 부족 | 프로젝트 규칙을 지침에 추가 | 🧑 내가 규칙 정의 |
| 안 시킨 것까지 건드림 | NOT-DO 부재 | NOT-DO 리스트 추가 | 🧑 내가 작성 |
| 설치/빌드 에러로 허우적 | ③ 환경 문제 | 환경 상태 점검 먼저 시키기 | 🤖 점검 → 🧑 판단 |
| 이전에 한 걸 또 함 | ④ 상태 관리 없음 | PROGRESS.md 도입 | 🤖 정리 → 🧑 검토 |
| "완료"했는데 안 됨 | ⑤ 피드백 없음 | 검증 절차 추가 | 🤖 자가점검 → 🧑 직접 확인 |
| 여기저기 손대고 하나도 안 끝냄 | 작업 범위 초과 | 한 기능씩 쪼개서 진행 | 🧑 범위 결정 |

👉 실천: 실패할 때마다 위 표를 보고 진단한다. 모델을 바꾸는 건 마지막 수단이다.

## 7. 내 바이브코딩 체크리스트 (두 축 버전)

새 프로젝트를 시작하거나 새 세션을 열 때 이걸 확인한다.
**🧑 = 내가 직접 하는 것, 🤖 = 에이전트에게 시키는 것**

### 프로젝트 시작 시
- [ ] 🧑 프로젝트의 목적과 방향을 내 말로 정리했다
- [ ] 🤖 에이전트에게 프로젝트 지침서 초안을 만들게 했다
- [ ] 🧑 지침서를 읽어보고, 빠진 규칙이나 제약을 추가했다
- [ ] 🤖 에이전트에게 기능 목록 + 완료 기준을 만들게 했다
- [ ] 🧑 기능 목록을 검토하고, 우선순위와 순서를 내가 정했다
- [ ] 🧑 NOT-DO 리스트(하지 않을 것)를 작성해서 지침에 넣었다

### 매 세션 시작 시
- [ ] 🤖 이전 진행 기록(PROGRESS.md)을 읽으라고 했다
- [ ] 🧑 이번 세션의 목표를 명확하게 정했다 (기능 1~2개)
- [ ] 🤖 현재 프로젝트 상태가 정상인지 점검시켰다
- [ ] 🧑 점검 결과를 확인하고, 문제가 있으면 해결 방향을 지시했다

### 작업 진행 중
- [ ] 🧑 에이전트가 범위를 벗어나는 작업을 하고 있진 않은지 중간중간 확인한다
- [ ] 🧑 에이전트가 "이것도 같이 하면 좋겠다"고 제안하면, 지금 할지 나중에 할지 내가 판단한다
- [ ] 🤖 중간 결과물을 보여달라고 요청한다 (한번에 다 하고 보여주지 말고)

### 에이전트가 "완료"를 선언했을 때
- [ ] 🤖 에이전트에게 완료 기준 대조표를 만들게 한다 ("각 기준별로 충족 여부를 알려줘")
- [ ] 🤖 에이전트에게 빌드/실행 확인을 시킨다
- [ ] 🧑 **내가 직접 실행해본다** — 버튼 눌러보고, 화면 확인하고, 입력 넣어보고
- [ ] 🧑 기존에 되던 기능이 안 깨졌는지 내가 직접 확인한다
- [ ] 🧑 이상하거나 부족한 부분을 구체적으로 짚어준다

### 매 세션 종료 시
- [ ] 🤖 에이전트에게 진행 상황 정리를 시켰다
- [ ] 🧑 정리된 내용이 맞는지 훑어보고, 빠진 결정사항이 있으면 추가했다
- [ ] 🤖 기능 목록의 상태를 업데이트시켰다 (✅/🔧/⬜)
- [ ] 🧑 다음 세션에서 할 작업을 내가 정했다

## 8. 실전 프롬프트 모음

### 프로젝트 시작할 때
```
이 프로젝트의 기능 목록을 만들어줘.
각 기능마다:
- 기능 이름
- 상세 설명
- 완료 기준 (이걸 충족해야 "완료"임)
- 우선순위 (높음/중간/낮음)
를 포함해줘.
```

### 작업 범위를 제한할 때
```
지금은 [기능 이름]만 작업하자.
다른 기능은 건드리지 마.
완료 기준:
- [기준 1]
- [기준 2]
- [기준 3]
완료 후 빌드해서 에러 없는지 확인해줘.
```

### 세션 마무리할 때
```
이번 세션을 마무리하자. 다음을 정리해줘:
1. 오늘 완료한 것
2. 현재 진행 중인 것 (어디까지 했는지)
3. 아직 남은 작업
4. 중요한 결정 사항이나 주의할 점
5. 다음 세션에서 바로 시작하려면 뭘 해야 하는지
```

### 이어서 작업할 때
```
이전 세션의 진행 기록을 읽어줘.
현재 프로젝트 상태를 확인하고,
기능 목록에서 다음으로 해야 할 작업이 뭔지 알려줘.
```

### 에이전트가 "완료"했다고 할 때
```
완료했다고 하기 전에 다음을 확인해줘:
1. 빌드 에러가 없는지
2. 이 기능이 실제로 작동하는지 테스트
3. 기존에 작동하던 기능이 깨지지 않았는지
4. 기능 목록의 완료 기준을 모두 충족하는지
확인 결과를 알려줘.
```

## 10. 용어 정리

| 용어 | 의미 |
|------|------|
| **하네스(Harness)** | AI 에이전트가 제대로 일하게 만드는 환경+규칙+검증의 총체. 마구(馬具) 비유. |
| **마구(🪢)** | 하네스 중 에이전트에게 거는 부분. 지침, 기능 목록, NOT-DO, PROGRESS.md 등. 한번 세팅하면 에이전트가 읽고 따르는 것들. |
| **기수(🧑)** | 하네스 중 내가 직접 하는 부분. 방향 판단, 범위 제한, 결과 확인, 다음 결정. 마구만으론 부족하고, 기수의 판단이 있어야 목적지에 도착한다. |
| **오케스트레이션** | 여러 작업, 여러 세션, 여러 에이전트를 조율하는 것. 기수가 경주 전체를 설계하는 것. |
| **바이브코딩** | 코드를 직접 짜지 않고, AI에게 자연어로 설명하며 앱을 만드는 방식. |
| **기능 목록(Feature List)** | 만들 기능과 각 기능의 완료 기준을 적은 목록. 마구의 뼈대. |
| **NOT-DO 리스트** | "하지 않을 것" 목록. 마구 중 가장 강력한 제약 장치. (이기적공유회 인사이트) |
| **완료 기준(Definition of Done)** | "이 조건을 다 충족해야 진짜 완료"라는 명시적 기준. |
| **진단 루프** | 실패 → 원인 파악 → 해당 구성 요소 수정 → 재시도의 반복. 기수가 경기 중 코스를 수정하는 것. |
| **컨텍스트 불안** | 에이전트가 대화가 길어지면 서둘러 마무리하려는 현상. |
| **검증 격차** | 에이전트가 "완료"라고 하는 것과 실제 완성 사이의 차이. 기수가 직접 확인해야 메워지는 간극. |
