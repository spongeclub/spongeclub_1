## 미션1: 내 고객은 누구고 왜 쓰는가 — 클로드 코드로 프로덕트 구현하기

### Summary

운동 센터(필라테스·PT 등) 사장님들을 위한 **올인원 스튜디오 워크스페이스** 빌드 중. 회원·강사 관리, 비용 지급, 일정 관리에 더해 **매출·비용을 가계부처럼 입력해 세금 대비**까지 한 곳에서 처리. 유사 SaaS가 다수 있지만 "세무 대비"가 들어간 건 드뭄 — 얕지만 어느정도의 세무 지식을 차별점으로 얹음. 첫 사용자는 가까운 한 분(여자친구), 검증 후 필라테스 사장님 커뮤니티 홍보까지 단계적 확장 계획.
![](attachments/Pasted%20image%2020260524163424.png)

### 최종 구현 결과물

- **프로덕트**: 스튜디오 워크스페이스 (작업명 미정, 아직 빌드 중)
- **핵심 기능 4축**:
  1. 회원·강사 관리 (등록·세션·출석)
  2. 비용 지급 (강사료 정산 등)
  3. 일정 관리 (예약·시간표)
  4. **매출/비용 가계부 입력 → 세금 대비** ⭐ 차별점
- **현재 단계**: MVP 빌드 중, 첫 사용자(여자친구) 피드백 루프 가동 준비
- **확장 로드맵**: 1차 첫 사용자 검증 → 2차 세무 지식 결합 다듬기 → 3차 필라테스 사장님 커뮤니티 홍보·확산

### 과정 (타임라인별 + 삽질)

1. **고객 정의** — 운동 센터(필라테스·PT) 사장님. 직접 매장 운영하시는 분들. 회원·강사·비용·세금이 따로 굴러가서 머리 아픈 페인.
2. **왜 쓸까** — 기존 SaaS 다수 있지만 "세무 대비"가 결합된 건 드묾. 세무 지식을 살짝 얹어 *입력 단계부터 세금에 대비할 수 있는 가계부형 입력 칸* 차별점. (예상 세액 범위로 알려주고, 매달 어느정도 예비비로 따로 빼둬라고 추천해줌)
3. **첫 사용자 선정** — 가까운 한 분(여자친구). 진짜 매장 운영자 페인을 가까이서 들을 수 있는 자리.
4. **삽질 #1 — API 권한 한계** — 어디까지 API를 가져올 수 있는지, 가져오려면 어떤 자격·권한이 필요한지에서 막힘. **돈낸다고 되는 게 아니라 자격 요건 자체가 막혀 있는 API**도 있더라. 어떤 외부 데이터는 아예 접근이 불가능.
5. **삽질 #2 — 세무 영역의 법적 한계** — 세무 조언은 *세무사 자격이 있어야* 가능한 영역. 어림짐작 안내로 가면 자칫 불법. 그래서 본인이 할 수 있는 표현은 "이 정도 나올 수 있으니 이렇게 대비하자" 수준의 *비조언적 안내*로 한정.
![](attachments/Pasted%20image%2020260524163902.png)
6. **결론** — 한 도메인 전문가가 *자기가 먼저 쓰고 → 점점 개선 → 충분히 좋아지면 홍보·배포*하는 흐름이 가장 안전·자연스러움.

*배포 링크: https://os-for-small-business.vercel.app/
- 배포는 해뒀고, 계속해서 개발중
- 테스트 데이터 삽입하여 사용중
### 공유할만한 인사이트

1. **'클로드 코드 + 도메인 지식'이 진짜 레버리지** — 코딩 자체는 AI가 도와주지만, *무엇을 만들어야 할지·어디서 막힐지·뭐가 합법인지*는 도메인을 모르면 안 보임. 도메인 지식이 곧 PRD를 만드는 능력.
2. **'돈으로도 안 되는' 한계가 있다** — API 권한·자격 요건은 시장에서 사 올 수 없는 것들이 꽤 있음. 시도 전에 *접근 가능성*부터 점검해야 빌드 도중 헛삽질 안 함.
3. **법적 영역은 '안내의 강도'를 디자인 단계에서 정해야 함** — 세무·법률·의료 같은 영역은 "조언"으로 가면 불법, "정보 제공"으로 가면 합법. 이 경계가 UX 카피·기능 범위 결정의 첫 가드레일.

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

### Summary

본인의 본업(전시 주최) 관점에서 **Harness = 전시회 플랫폼이라는 발판** / **Orchestration = 그 발판 위에서 사람들의 만남·이동을 조율하는 행위**로 정의. Harness는 한 번 설계하면 매해 재사용되는 *명사형 인프라*, Orchestration은 매번 새로 일어나는 *동사형 운영 흐름*. 앞으로 자기 프로덕트(스튜디오 워크스페이스)에도 같은 분리를 적용 — 한 번 짜둔 발판 + 매번 새로 조율되는 흐름.

### 최종 구현 결과물

#### 🏗️ Harness = 전시회 플랫폼 자체 (발판)

한 자리에 모여 있는 모든 것. 셀러가 '등록'만 하면 나머지는 자동으로 구성되도록 미리 짜여 있는 구조.

**참여자들 (고정 역할)**
- 셀러 / 바이어 / 통역사 / 컨퍼런스 진행자 / 미디어·카메라맨

**인프라 (세팅)**
- 부스 공간 / 회의실 / 스테이지 / Wi-Fi / 통역 부스

**규칙 (자동화)**
- 셀러 카테고리별 매칭 알고리즘 / QR 체크인 / 시간표

**산출물 (자동 생성)**
- 셀러 카탈로그 인쇄 / 바이어 매칭 리스트 / 통역 배정표

> **핵심**: Harness는 "한 번만 설계하면 계속 쓸 수 있는 틀". 매해 전시회가 열릴 때마다 같은 구조 위에서 돈다.

#### 🎼 Orchestration = 발판 위에서 사람들을 움직이는 행위

Harness라는 발판이 있으면, 그 위에서 *사람들의 이동·만남·대화*를 실제로 조율하는 행위. **매번 다르다.**

**📅 사전 단계 — 기획 & 매칭**
- 셀러 카테고리 파악 (화장품·의류·식품·기계부품…)
- 바이어 사전 리스트 수집 (수입사·유통사·도매)
- 카테고리별 매칭 규칙 세팅 ("화장품 셀러는 뷰티 바이어와 매칭")
- 통역사 배정 (언어별·분야별)

**📍 당일 단계 — 실시간 진행**
- 부스 배치·안내
- QR 체크인 (셀러·바이어 도착 확인)
- 자동 통역사 연결 (리얼타임)
- 미팅 시간 조정
- 미디어 촬영·기록

**📊 사후 단계 — 리드 심사 & 전달**
- 모든 미팅 기록 수집 (체크인 데이터 + 영상 + 노트)
- 리드 점수 매기기 (MQL / SQL 분류)
- 품질 심사 ("정말 구매 의사가 있나?")
- 영업팀에 전달 (후속 액션 assignment)

#### 🔗 Harness와 Orchestration의 관계

| Harness (형태 있음) | Orchestration (형태 없음, 행위) |
|---|---|
| **명사** — "전시회라는 플랫폼" | **동사** — "사람들을 움직이는 행위" |
| 한 번 설계하면 재사용 가능 | 매번 새롭게 일어남 |
| 인프라·규칙·도구 | 판단·조율·결정 |
| 전시회가 없으면 오케스트레이션 불가 | 오케스트레이션이 잘되어야 하네스 가치 증대 |
**적용 — 스튜디오 워크스페이스에 대입**
   - **Harness** = 회원·강사·매출·일정 데이터 구조 + 입력 폼 + 자동 계산 규칙 + **AI 에이전트들의 역할 정의** (한 번 짜는 발판)
   - **Orchestration** = 사장님이 매출 한 줄 입력하면 → 세액 예측 에이전트가 예상 세금 알림 → 예비비 추천 에이전트가 "이만큼 빼두세요" 안내 → 리마인드 에이전트가 정산·신고일 알림 → 월말 리포트 에이전트가 한 장 요약 자동 생성. **사장님은 결정·검토만, AI들이 조율·실행.**
   - 즉 **사장님 입력 = Orchestration의 시작 트리거**이고, 실제 조율은 AI 에이전트들의 협업으로 굴러감. 본인 OS 선언문("결정만 하고 나머지는 시스템")의 프로덕트 버전.

### 과정 (타임라인별 + 삽질)

1. **출발 — 본업에서 출발** — 전시 주최사 디지털마케팅팀에서 일하다 보니 "행사라는 게 결국 *틀*과 *흐름* 두 층으로 굴러간다"는 게 자연스럽게 보임.
2. **명명 — 영어 단어로 잡기** — Harness(발판) / Orchestration(조율). 이 두 단어가 모호하지 않고 각자 정확한 자리가 있어서 정의에 쓰기 좋았음.
3. **분리 — 명사 vs 동사** — Harness는 한 번 설계, Orchestration은 매번 새로. 이 *명사/동사* 구분이 가장 깨끗한 차이축.
4. 이해하는데 굉장히 많은 시간이 걸렸음.. 사실은 용어를 몰랐을 뿐이지 예전에 바이브코딩 때 PRD, IA, Use-Case 등 작성하면서 구조 잡고 할 때 이미 했던 것임. 하지만 용어가 나오면서 오히려 모르는 것처럼 생각하게 됐음.

### 공유할만한 인사이트

1. **이 분리는 거의 모든 운영형 비즈니스에 통한다** — 전시·교육·헬스장·F&B·플랫폼… 본인이 *틀*을 잘 짜두면, 매일의 *흐름*은 가벼워짐. 본인 OS 선언문("결정만 하고 나머지는 시스템")의 비즈니스 버전.
2. **Harness 설계 = 미래의 결정량을 줄이는 작업** — 매해 다시 만들 필요 없게 만드는 게 핵심. 1년 한 번의 큰 투자가 매주의 결정 비용을 깎음.
3. **Orchestration이 죽으면 Harness도 의미 없음** — 부스·매칭표만 있고 사람들이 안 움직이면 그냥 빈 행사. 둘은 동시 작동해야 가치 발생.
