# MoveNow (무브나우) — AI 루틴 자동 생성 SaaS

## 미션1: 내 고객은 누구고 왜 쓰는가 — 클로드 코드로 프로덕트 구현하기

### Summary

2주차 무브나우(MoveNow) 기획을 실제 코드로 구현했다. 노코드(Softr+Airtable) 대신 **Next.js 14 + Supabase + Claude API** 풀스택으로 전환. 핵심 가치는 그대로 — 헬스장에 있는 기구만 쓰고, AI가 서브근육 타겟(윗가슴/아랫가슴 등)까지 고려한 맞춤 루틴을 자동 생성한다.

**고객 정의:**
- 고객: PT 트레이너 (B2B)
- 왜: 헬스장마다 기구가 다른데 루틴 앱들은 그걸 모름 / 서브근육 타겟 비율 조정이 트레이너 머릿속에만 있음 → AI가 대신

### 최종 구현 결과물

**한 줄 소개:** 개인 트레이너를 위한 B2B SaaS — 헬스장에 있는 기구만 사용하고, AI가 서브근육 타겟(윗가슴/아랫가슴 등)까지 고려한 맞춤 루틴을 자동 생성

| 항목 | 선택 |
|------|------|
| 프레임워크 | Next.js 14 (App Router) |
| DB / Auth | Supabase (PostgreSQL + 이메일 인증) |
| AI | Claude API (claude-opus-4-5) |
| 스타일 | Tailwind CSS |
| 배포 예정 | Vercel |

**완성된 기능:**

1. **인증** — 트레이너 회원가입/로그인, DB 트리거로 프로필 자동 생성, 미들웨어 로그인 보호
2. **헬스장 등록** — 브랜드+지점 구조, 기구 80여 종 카테고리별 등록, 기구마다 서브근육 자동 매핑
3. **회원 등록 6단계** — 기본정보 → 운동목적 → 분할설정 → 부위타겟 → PT설정 → AI 루틴 자동생성
4. **AI 루틴 생성** — 이 헬스장 기구만 사용 + 지정 서브근육 타겟 비율 반영 + PT 시간에 맞는 볼륨 자동 조절

**AI 루틴 출력 예시:**
```
Day 1  가슴 + 삼두
인클라인 벤치프레스    [윗가슴]     4세트 × 8-10회   90초
인클라인 체스트 프레스  [윗가슴]     3세트 × 12회    60초
펙덱 플라이           [전체]      3세트 × 15회    60초
트라이셉스 푸시다운    [삼두 외측두]  4세트 × 12회   60초
```

**개발 현황:**
- ✅ 인증 (회원가입/로그인)
- ✅ 헬스장 등록 + 기구 서브근육 매핑
- ✅ 회원 6단계 등록 플로우
- ✅ AI 루틴 생성 API (`/app/api/generate-routine/route.ts`)
- ⏳ Anthropic API 키 세팅
- ⏳ Vercel 배포
- ⏳ RLS 보안 정책 (실서비스 전 필요)

**목표:** 대구 헬스장 100개 계정 (1년) / 트레이너 개인 계정 단위 판매 / 현재 MVP 단계

### 과정 (타임라인별 + 삽질)

| 문제 | 원인 | 해결 |
|------|------|------|
| `npm create-next-app` 실패 | 폴더명 "무브나우" 한글 → npm이 거부 | 영문 폴더 생성 후 수동 이동 |
| `npx` 명령어 없음 | Node.js 자체가 설치 안 돼있었음 | nvm → Node.js v24 설치 |
| SQL "gyms already exists" | 스키마 SQL을 두 번 실행 | ALTER TABLE만 따로 실행 |
| "gym_brands does not exist" | ALTER TABLE이 CREATE TABLE보다 먼저 실행됨 | 두 쿼리 합쳐서 한 번에 실행 |
| 로그인 해도 페이지 안 넘어감 | `@supabase/supabase-js`의 `createClient` 사용 → 쿠키 미설정 | `@supabase/ssr`의 `createBrowserClient`로 교체 |
| 로그인이 3~4초씩 느림 | 미들웨어에서 `getUser()` → 매 요청마다 Supabase 서버에 JWT 검증 | `getSession()`으로 교체 (로컬 검증) |
| 회원가입하면 트레이너 프로필 2개 생성 | 코드에서 수동 insert + DB 트리거 동시 실행 | 수동 insert 삭제, 트리거 단독 처리 |
| 회원가입 자체가 안 됨 | Supabase 이메일 인증 활성화 상태 | 개발 단계에서 이메일 확인 비활성화 |

### 공유할만한 인사이트

**기술적으로**

1. **Next.js + Supabase 조합은 SSR 쿠키 처리가 핵심.** `@supabase/ssr` 안 쓰면 인증이 겉돈다. 공식 문서보다 패키지 이름이 더 먼저 나와서 `@supabase/supabase-js`로 시작하는 사람 많은데, SSR 환경에서는 반드시 `@supabase/ssr`이다.

2. **DB 트리거 쓰면 "회원가입 → 프로필 자동 생성" 로직이 훨씬 안정적.** 코드에서도 insert하고 트리거에서도 insert하면 중복 생성된다. 한 곳에서만 처리.

3. **미들웨어 성능은 작은 것 같아도 UX에 직결된다.** `getUser()` vs `getSession()` 차이가 3~4초. 매 페이지 이동마다 느끼는 지연이다.

**제품적으로**

4. **"헬스장 기구 등록"이 처음엔 귀찮아 보였는데, 이게 있어야 AI가 의미 있어진다.** 데이터 수집 단계가 곧 차별화다. 기구 목록이 없으면 AI는 아무 헬스장이나 있는 기구를 추천한다 — 그건 기존 앱과 똑같다.

5. **서브근육 타겟이라는 개념 자체를 AI가 처리할 수 있다는 걸 구조 잡으면서 발견했다.** "가슴 운동" 레벨이 아니라 "윗가슴 집중", "광배 하부 위주" 레벨에서 루틴을 짜는 게 트레이너가 실제로 하는 일이다. 이걸 AI에게 넘길 수 있다.

6. **고객 정의가 먼저다.** "헬스장"이 고객이 아니라 "트레이너"가 고객이다. 헬스장은 유통 채널. 트레이너가 루틴 짜는 데 쓰는 시간과 인지 비용이 진짜 페인.

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

### Summary

MoveNow의 AI 루틴 생성 파이프라인을 **하네스**로 정의했다. 단순히 "Claude한테 물어보기"가 아니라, 입력 데이터를 정제하고 제약을 강제하고 출력을 검증하는 구조. 오케스트레이션은 6단계 회원 등록 플로우 자체 — Step 1~5에서 모은 컨텍스트가 Step 6에서 Claude 호출로 수렴한다.

### 최종 구현 결과물

**하네스 구조 (`/app/api/generate-routine/route.ts`):**

```
[입력 레이어]
회원 분할 설정 + 서브근육 타겟 비율 + PT 설정
        ↓
[제약 레이어 — 핵심]
이 헬스장 기구 목록만 (Supabase 동적 조회)
        ↓
[프롬프트 어셈블리]
기구 목록 + 타겟 비율 + 시간/볼륨 → Claude 프롬프트 구성
        ↓
[Claude API 호출]
claude-opus-4-5 → Day별 운동명 + 서브근육 + 세트/렙/휴식
        ↓
[출력 파싱 + DB 저장]
JSONB → routines 테이블
```

**오케스트레이션 — 6단계 플로우:**

```
Step 1: 기본정보 수집
Step 2: 운동목적 선택 (다이어트/벌크업/체형교정 등)
Step 3: 분할 설정 (2~5분할, Day별 부위)
Step 4: 부위 타겟 (가슴=윗가슴/아랫가슴 비율)
Step 5: PT 설정 (횟수/시간/웨이트-유산소-맨몸 비율)
Step 6: → Claude 호출 → 루틴 생성
```

### 과정 (타임라인별 + 삽질)

**하네스 설계의 핵심 결정: 기구 제약을 프롬프트 안에 넣는다**

처음엔 "Claude한테 좋은 루틴 짜달라고 하면 되겠지"였다. 근데 Claude는 헬스장에 어떤 기구가 있는지 모른다. 하네스의 가장 중요한 역할이 **"이 헬스장 기구 목록을 프롬프트에 주입하는 것"** 으로 정해진 이유다.

Supabase에서 해당 헬스장의 기구 목록 조회 → JSON 직렬화 → 프롬프트에 삽입 → "이 목록에 있는 기구만 써"라고 명시적으로 지시.

> **삽질**: 처음엔 기구 목록을 그냥 이름만 나열했는데, Claude가 서브근육 타겟을 무시하고 볼륨 위주로만 짰다. 기구마다 `[서브근육]` 태그를 붙여서 넘기니까 타겟 비율을 잘 반영하기 시작함. **프롬프트 구조보다 입력 데이터 구조가 출력 품질을 결정했다.**

**오케스트레이션 — Step 간 상태 관리**

6단계 플로우에서 Step별 데이터를 Step 6까지 넘기는 방법: Next.js App Router에서 서버 액션 + `useState` 조합. 각 Step 완료 시 상위 컴포넌트 state에 누적 → Step 6에서 전부 모아 API 호출.

### 공유할만한 인사이트

1. **하네스의 핵심은 "AI가 실수할 수 없게 막는 것"이다.** 좋은 프롬프트 엔지니어링이 아니라 입력 데이터 자체를 제약하는 것. "없는 기구 쓰지 마" 명령어보다, 기구 목록을 명시적으로 넣어서 Claude가 그 목록 안에서만 선택하게 하는 구조가 더 강하다.

2. **오케스트레이션은 단계별 컨텍스트 누적이다.** 6단계 플로우는 UX 설계이기도 하지만 AI 컨텍스트 수집 프로세스이기도 하다. Step 1~5가 "Claude에게 넘길 정보"를 구조화하는 과정이고, Step 6이 그 컨텍스트를 소비하는 지점.

3. **JSONB는 AI 출력 저장에 적합하다.** AI가 뱉는 구조화 데이터는 스키마가 유연해야 한다. Day별 운동 수가 다르고 부위마다 구조가 조금씩 다를 때 JSONB가 정규화 테이블보다 훨씬 편했다.

### 과정 (타임라인별 + 삽질)

2주차에 무브나우 기획을 SNS에 올리려다 "아직 구상 단계"라서 보류했다. 3주차에 실제 코드로 구현하면서 "이 과정에서 뭘 배웠나"가 글감이 됐다. 화려한 결과물 스크린샷보다 **"왜 이걸 만드나"와 "어떤 삽질을 했나"를 먼저 쓰는 게 더 진짜 같다는 결론.**

### 공유할만한 인사이트

1. **"완성된 결과물"보다 "삽질 과정"이 더 읽힌다.** 2주차에 무브나우 기획을 올리려다 "아직 구상 단계"라서 보류했는데, 3주차에 돌아보니 그게 더 좋은 글감이었다. 완성 스크린샷보다 "npm 명령어 한 번도 안 쳐본 사람이 Node.js도 없다는 걸 그때 알았다"가 훨씬 진짜다. SNS 글은 성공 리포트가 아니라 사고 기록이다.

2. **"AI가 코딩을 대신해준다"는 말은 반만 맞다.** Claude가 코드를 써줬지만, "왜 이 코드가 필요한가"는 내가 알아야 했다. `@supabase/supabase-js`와 `@supabase/ssr` 차이를 모르면 로그인이 3초 느려지는 이유를 찾을 수 없다. 에러 메시지를 해석하고 어느 방향으로 물어볼지를 결정하는 건 여전히 사람 몫이다. 툴이 바뀐 것이지 사고하는 주체가 바뀐 게 아니다.

3. **고객 정의 없이 만든 것은 기획 단계에서 멈춘다.** 매주 만들어야 한다는 압박이 있을 때 제일 먼저 도망가고 싶은 게 "고객이 누구인가" 질문이다. 기술 스택 고르는 게 더 재밌다. 근데 2주차 무브나우처럼 기획만 하고 멈추는 이유가 거기 있다. 3주차에 코드를 실제로 치기 시작한 건 트레이너의 페인이 명확해졌기 때문이었다.

4. **스폰지클럽 3주가 내 서비스 한 개의 타임라인이 됐다.** 1주차 황철순 OS(개인 루틴 봇) → 2주차 무브나우 기획 → 3주차 무브나우 구현. 매주 "만들어서 공유해야 한다"는 구조가 없었으면 기획 단계에서 영원히 굴렀을 거다. 스터디 압박이 프로덕트 속도가 됐다.
