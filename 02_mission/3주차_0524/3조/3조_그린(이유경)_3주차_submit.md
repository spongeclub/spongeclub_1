#### 0단계: 기획 — PRD v1.0 → v1.3까지

**삽질 1: 앱의 정체성 자체를 잘못 잡았다 — "캘린더 앱"에서 "질환 추적 앱"으로**

처음 기획할 때 핵심 기능을 "메모 + 캘린더"라고 정의했다. 그런데 대화하면서 근본적인 문제를 발견했다. 캘린더는 날짜가 중심이라, 6개월~1년에 한 번 일어나는 일을 담기엔 너무 비어 보이고 흩어진다. 진짜 필요한 건 **질환이 중심**이고 시간이 축인 구조였다.

> "양성 종양이라는 질환을 열면 — 지금까지의 진료 기록, 측정값 변화(1.2cm → 1.4cm → 1.3cm), 의사 지시사항, 다음 예약이 한 화면에 쭉 보이는 것"

이 재정의 하나가 앱 전체 구조를 바꿨다. '캘린더 앱'으로 만들었다면 결국 날짜 붙은 메모장이 됐을 거다.

**삽질 2: iOS 네이티브 앱 → 웹 MVP(PWA)로 피벗**

처음엔 iOS 네이티브(React Native + Expo)로 시작하려 했다. 그 다음 Next.js 웹앱으로, 최종적으로 PWA로 결정했다. 결정적 이유:

> "사이드 프로젝트는 9할이 사용자 안 모임으로 죽는다. 웹 MVP는 1~2개월 만에 '이거 사람들이 쓰나?'를 검증할 수 있다."

나중에 iOS로 전환할 때 코드는 다시 짜야 하지만, 데이터 구조와 화면 흐름은 그대로 쓸 수 있다.

**삽질 3: 기능 범위 — 원하는 걸 다 넣으면 안 된다는 걸 배웠다**

처음에 원했던 기능 목록: 음성 녹음→AI 정리, 스마트 리마인더(예약 알림이 완료될 때까지 반복), 서류 스캔·보관, 다중 질환 관리. "없으면 이 앱을 아예 안 쓸 것 같은 기능 딱 하나"를 정하는 과정에서 MVP 심장이 결정됐다: **질환별 타임라인 + 메모**. 음성, 리마인더, 서류 스캔은 전부 v2.

**삽질 4: PRD v1.0 → v1.3 반복 — "닻" 수준이 되기까지**

바로 Claude Code 켜고 만들기 시작하고 싶었지만, PRD를 먼저 잡기로 했다. PRD v1.0은 기능이 너무 많았다. v1.1에서 쳐냈다. v1.2에서 데이터 모델을 구체화했다. v1.3에서야 "Claude Code가 매 세션 이 문서를 읽고 원칙을 지킬 수 있는" 수준이 됐다. 이 작업에만 일주일 넘게 걸렸다.

**삽질 5: 체크리스트를 HTML로 만들었다가 md로 다시 만들었다 (ㅋㅋ)**

진행 추적용 체크리스트를 HTML로 만들었다. 보기엔 예뻤는데 Claude Code가 직접 편집할 수 없었다. Claude Code가 체크박스를 토글하려면 마크다운(.md)이어야 한다. CHECKLIST.md로 다시 만들었고, 지금은 화면 완료 시마다 Claude Code가 자동으로 체크하고 진행 메모를 한 줄 남긴다.

#### 0.5단계: 데이터 모델 설계 — UI보다 먼저 잡아야 했던 것

**삽질 6: "수치 여러 개" 문제를 처음부터 제대로 설계해야 했다**

처음엔 진료 기록 하나에 "수치 칸" 하나만 뒀다. 그런데 당뇨는 공복혈당·당화혈색소 두 가지가 각각 따로 그래프에 그려져야 한다. 결국 4개 테이블 구조로 설계했다:

```
질환(Condition) → 측정항목(MeasurementItem) → 진료기록(Record) → 측정값(MeasurementValue)
```

이 구조가 확정되자 "종양이 3개면 측정 항목을 3개 만들면 된다"처럼 모든 케이스가 자연스럽게 풀렸다. 데이터 구조를 처음에 제대로 잡는 게 UI보다 훨씬 중요하다.

**삽질 7: 진료 기록이 '진료'에만 국한되지 않는다는 걸 나중에 알았다**

처음엔 VISIT_RECORD(진료 기록)만 있었다. 그런데 진료 날짜와 무관하게 적어두고 싶은 것들이 있다: "이달에 이런 증상이 있었다", "다음에 의사한테 물어볼 것". 따로 뺄까 고민했는데, Record에 `type` 필드 하나 추가하는 걸로 해결했다. `visit`(진료)과 `note`(메모) 두 종류. 단순한 결정이지만 데이터 모델 이름(VISIT_RECORD → RECORD)부터 화면 설계까지 전부 영향을 받았다.

**삽질 8: "변동 없음"과 "측정 안 함"은 다른 데이터다**

직접 다니던 병원에서 "격번 운영" 패턴이 있다는 걸 떠올렸다: 3개월에 한 번 가는데, 한 번은 검사하고 한 번은 약만 처방받는 식. 이 두 케이스가 데이터에서 다르게 표현돼야 했다.

- **측정 안 함** → 해당 항목의 측정값 행 자체가 없음 (그래프에 점 없음)
- **변동 없음** → 직전 값을 복사한 행이 생성됨 (그래프에 "안정" 점이 찍힘)

이 차이를 놓쳤다면 "지난번이랑 같아요"라고 했을 때 아무것도 기록 안 하게 됐을 것이다. 기록했다는 사실 자체가 데이터다.

#### 0.7단계: 데이터 탐색 — 완벽주의가 부른 삽질

**삽질 9: KOICD가 공식 기관인 줄 알았는데 사설이었다**

질환 이름 표준화를 위해 KCD(한국표준질병사인분류) 데이터가 필요했다. 검색해서 나온 koicd.kr에서 엑셀 다운로드를 찾았는데, 알고 보니 민간 회사가 운영하는 사이트였다. 공식 데이터는 **공공데이터포털(data.go.kr)**에 건강보험심사평가원 "상병마스터" 파일로 있었고, 공공누리 제1유형이라 출처 표시만 하면 상업적 이용도 가능하다. MVP에서는 흔한 질환 30~50개 추천 목록으로 먼저 나가고, 전체 KCD 내장은 v2.

#### 0.8단계: 디자인 방향 — 한 시간 동안 다섯 번 바뀐 컬러 시스템

**삽질 10: 디자인 레퍼런스를 읽을 수가 없었다**

레퍼런스로 ZERO 앱(Plus X × SK바이오팜, 뇌전증 환자용)과 SK바이오팜 케이스 스터디 링크를 가져왔는데, 두 곳 모두 JS로 렌더되는 SPA라서 Claude가 내용을 볼 수가 없었다. 결국 스크린샷 10장을 직접 캡처해서 붙여넣는 방식으로 분석했다.

**삽질 11: 세이지 그린+베이지 → 그리니쉬 화이트 → 블루 대시보드, 한 시간 안에 세 번 피벗**

디자인 방향이 결정 피로 속에서 계속 흔들렸다. 타임라인으로 정리하면:

|시점|컬러 결정|이유|
|---|---|---|
|기획 초반|세이지 민트 그린 + 노란 베이지|"헬스케어 앱이니까"|
|데이터 시각화 고민|세이지 + 회색조 (C안)|측정값은 회색조, 진료 시점만 액센트|
|레퍼런스 보고 나서|그리니쉬 화이트 베이스로 변경|베이지가 액센트 선택을 좁힌다|
|ZERO 앱 스크린샷 보고|푸른 그라데이션으로 전환|"이 톤이 내가 원하는 거야"|
|결정적 깨달음|블루 대시보드 + 코랄 액센트로 확정|앱 정체성 재정의|

**삽질 12: "치유 앱"에서 "대시보드"로 — 앱 정체성 자체가 바뀌었다**

가장 중요한 순간이었다. 세이지 그린을 고집했던 이유가 "그린=치유"의 느낌이었는데, 1시간 동안 컬러 결정을 반복하다가 한 문장을 깨달았다:

> "치유/치료보다는 차트/대시보드로 정보 제공이 메인인 것 같더라고, 내가 만들고 싶은 게."

이게 디자인 방향뿐 아니라 앱 전체 정체성을 정리한 순간이었다. PRD 원칙 #1 "질환을 시간축으로 추적하는 도구"와 완전히 정렬됐다. 그 전까지는 무드보드의 "도자기·린넨" 키워드가 다른 방향을 보고 있었던 것.

**삽질 13: 폰트도 두 번 바뀌었다**

처음: Pretendard + Geist Sans (분리) → 다시 고민해서 DM Sans + Pretendard로 확정. "맨날 프리텐다드만 써서 다른 거 써보고 싶다"고 했지만, 결국 Pretendard로 돌아왔다. (맨날 쓰는 데는 이유가 있다.)

**삽질 14: 그라데이션 정책 180도 전환**

초반엔 "그라데이션 전면 금지"를 디자인 원칙으로 박아뒀다. 블루 대시보드로 방향이 바뀌면서 "메인 헤더·강조 카드 1개에만 한정 허용"으로 완화했다. 정책이 바뀌면서 디자인 레퍼런스 MD가 v1.0 → v1.1 → v2.0 → v2.1까지 총 4번 업데이트됐다.

#### 0.9단계: Instructions 설정 — Claude Code를 길들이는 법

**삽질 16: "시키면 다 해줄 줄 알았다" — 원래 0.9단계에서 먼저 배웠다**

PRD를 던지면 AI가 알아서 와이어프레임 만들고, 나는 체크만 하면 된다고 생각했다. 실제론 달랐다. PRD에 없는 결정이 계속 나오고, 그때마다 내가 결정을 내려야 작업이 진행된다. 결정권자 역할은 사람이 가져가야 한다.

Claude Projects의 Instructions에 역할과 작업 원칙을 명시해두면 매 세션 반복 설명이 줄어든다. PRD를 Knowledge에 업로드하면 새 채팅마다 자동 참조된다. 이게 "하네스"의 실용적 최소 형태다.

#### 0.95단계: IA 설계 + GitHub 세팅 — 개발 직전의 마지막 준비

**삽질 16: + 버튼이 "질환 추가"냐 "기록 추가"냐**

IA를 그리면서 홈 화면의 + 버튼 역할을 처음엔 "질환 추가"로 설계했다. 그런데 생각해보니 앱의 핵심 사용 시나리오가 "병원 나와서 빠르게 기록"인데, + 버튼을 누르면 먼저 질환을 선택하고 그 다음에 기록 입력으로 가는 게 맞다. 결국 + 버튼 = 기록 추가 진입점(질환 선택 → 기록 입력)으로 변경했고, 질환 추가는 헤더 아이콘 + 질환 선택 화면의 "+ 새 질환" 두 경로로 분산했다.

**삽질 17: PRD가 v1.3까지 업데이트됐다**

IA 설계 결정사항들이 PRD에 반영 안 된 채로 Claude Code를 시작하려 했더니 "Claude Code가 옛 결정을 따를 위험이 있다"는 경고를 받았다. IA 확정 사항(보관함 헤더 진입, + 버튼 역할, 빈 상태 3종 카피 등)을 v1.3 패치로 한 번 더 반영했다. v1.1 → v1.2(디자인 변경) → v1.3(IA 변경)으로 PRD 업데이트가 세 번 있었다.

**삽질 18: GitHub 세팅에서 예상치 못한 것들**

GitHub 레포 연결하는 과정에서 작은 함정들이 있었다:

- `.DS_Store` 파일이 commit 목록에 자동으로 들어있었다. macOS Finder가 자동 생성하는 메타데이터 파일인데, 체크 해제하지 않으면 repo에 올라간다.
- `docdoc`으로 만들었다가 `doc-doc`으로 다시 레포를 만들었다. 이름 하나에도 컨벤션이 있다.
- 상위 폴더(GitHub/)가 아니라 doc-doc 폴더 안에서 작업해야 한다는 게 처음엔 헷갈렸다.

**삽질 19: Claude Code 앱 vs 터미널 claude 명령 혼동**

"터미널에서 claude 명령으로 시작하라"는 가이드를 따르려다, 이미 Claude Code 앱을 쓰고 있다는 걸 알았다. 둘은 같은 결과를 내는 다른 진입 방법이었다. Claude Code 앱에서 작업 경로를 doc-doc 폴더로 설정하면 터미널 명령과 동일하게 동작한다.

**삽질 20: PR 알럿이 떴다**

Claude Code 앱 우상단에 "풀 리퀘스트 상태를 확인할 수 없습니다" 알럿이 떴다. 당황했는데, 사실 1인 프로젝트에서 PR(Pull Request)은 아예 쓰지 않는다. Claude Code가 GitHub API로 PR 상태를 확인하려다 실패한 것이고, 무시하면 된다.

---

#### 2단계: 개발 환경 세팅 — 코드 한 줄 짜기 전에 1시간 소비

사실 코드 한 줄 짜기 전에 거의 1시간을 환경 세팅에 썼다.

**삽질 1: pnpm → npm 피벗** 처음엔 pnpm으로 세팅하려 했는데 `sudo corepack enable`이 필요했다. Claude Code의 Bash는 비대화형이라 비밀번호 입력이 안 된다. 별도 터미널에서 직접 해야 한다는 걸 처음 알았다. 결국 그냥 npm으로 선회.

**삽질 2: `~/.npm` root 소유 문제**

```
npm error code EACCES
npm error permission denied...
```

과거에 `sudo npm` 쓴 흔적으로 npm 캐시 디렉토리가 root 소유가 되어 있었다. 해결: `sudo chown -R 501:20 ~/.npm`. 근데 이것도 Claude Code 안에서 못 하고 직접 터미널에서 해야 했다.

**삽질 3: zsh history expansion 함정** 터미널에서 `!sudo chown -R 501:20 ~/.npm`을 입력했더니 zsh에서 `!sudo`를 history expansion으로 해석해서 전혀 다른 예전 명령어가 실행됐다. `!` 빼고 그냥 입력하면 됨.

**삽질 4: Next.js 초기화 시 마스터 문서 conflict** 루트 폴더에 이미 있던 PRD.md, CHECKLIST.md 등이 Next.js 초기화와 conflict. 임시로 상위 폴더로 옮겼다 복원했다.

---

#### 3단계: 디자인 시스템 설정

Tailwind v4가 v3랑 달라서 예상 못한 삽질이 있었다.

**삽질 5: Tailwind v4는 config 파일이 없다** v3에서는 `tailwind.config.js`에 커스텀 토큰 정의. v4는 CSS `@theme` 디렉티브로 바뀌었다. Claude Code가 알아서 v4 방식으로 처리해줬지만, 내가 "config 파일 어디 있어?"하고 한참 찾았다.

---

#### 4단계: 홈 화면 & 카드 재설계

**삽질 6: 첫 카드 디자인의 정보 위계 실패** 처음에 `display 56px`로 경과 시간(1개월, 3개월)을 크게 박았다. 직접 보니까 측정값보다 시간이 더 크게 보여서 어색했다. 정보 우선순위를 다시 생각해야 했다.

> 원래: 경과 시간이 display(56px)로 압도적  
> 수정: 측정값 = 경과 시간 = h2로 균형 맞춤

아이콘도 처음엔 없었는데, 카드만 3개 보면 어떤 게 어떤 질환인지 구분이 안 됐다. Condition 타입에 `iconName` 필드를 추가하는 방식으로 해결.

**삽질 7: Phosphor Icons export 이름 변경** `Activity` 아이콘을 import했더니 빌드 오류. 패키지 버전이 올라가면서 `ActivityIcon`으로 이름이 바뀌어 있었다. `Pulse`로 교체해서 해결.

---

#### 5단계: Dexie 시드 데이터 인프라

처음엔 `dummy.ts` 파일로 하드코딩 더미 데이터를 쓰다가, 진짜 IndexedDB에 올려서 다양한 케이스를 테스트하고 싶었다.

`db.ts`, `seed-data.ts`, `seed.ts`, `providers.tsx` 총 4개 파일로 인프라 구성. 가상 프로필 "지윤" (21 기록 + 25 측정값)으로 풍부한 시드 데이터 작성.

**삽질 8: useLiveQuery 시그니처 오류**

ts

```ts
useLiveQuery(() => ..., [], defaultValue) // 이렇게 썼더니 에러
```

이 버전의 dexie-react-hooks는 default value 인자를 안 받음. `?? []` nullish coalescing으로 해결.

---

#### 6단계: 질환 상세 화면 + Navigation 버그

**삽질 9: router.back()이 앱 밖으로 나감** Claude Code의 preview에서 `location.href`로 직접 URL 이동하다 보면 브라우저 history가 꼬인다. `router.back()`만 쓰면 history가 없을 때 Next.js 기본 404 페이지로 나가버린다.

ts

```ts
// 수정 전
router.back()

// 수정 후  
window.history.length > 1 ? router.back() : router.push('/')
```

### 공유할만한 인사이트

**1. Claude Code의 최대 강점은 "컨텍스트 유지"** 세션 시작할 때 PRD, CHECKLIST, 디자인 레퍼런스를 다 읽히고 시작하면, 이후 작업이 전부 그 원칙을 따른다. 중간에 "이 결정 PRD랑 충돌하지 않아?"라고 물어보기도 한다. 혼자 개발할 때 놓치기 쉬운 일관성을 AI가 잡아줌.

**2. 삽질의 80%는 환경 세팅** 코드 자체보다 환경 세팅(권한, 패키지, 버전 충돌)에서 시간을 많이 쓴다. 특히 비개발자라면 첫 세팅을 한 번 제대로 잡아두는 게 중요.

**3. CLAUDE.md가 Claude Code의 뇌** `CLAUDE.md`에 "PRD와 충돌하면 멈추고 물어봐", "커밋 메시지 형식: [세션N] 항목명 — 설명" 같은 작업 원칙을 적어두면 AI가 그걸 따른다. 매번 설명 안 해도 됨.

**4. 디자인 결정은 눈으로 봐야 알 수 있다** 처음에 display 56px 위계가 "설계 상"으론 맞아 보였는데, 브라우저에서 직접 보니까 바로 어색함이 느껴졌다. 빠르게 만들고 눈으로 확인하는 사이클이 핵심.

**5. 비개발자도 PRD + 디자인 레퍼런스를 먼저 작성해야 한다** Claude Code가 아무리 잘해도 "뭘 만들어야 하는지"는 사람이 먼저 정해야 한다. PRD v1.0→v1.3 과정이 귀찮게 느껴졌는데, 실제 개발에 들어가니까 그 준비가 없었으면 훨씬 더 오래 걸렸을 거라는 걸 알았다. 기획 문서가 Claude Code의 "기억" 역할을 한다.

**6. 체크리스트 포맷이 중요하다** HTML로 만들면 예쁘지만 Claude Code가 수정할 수 없다. 마크다운(.md)으로 만들어야 Claude Code가 직접 체크박스를 토글하고 진행 메모를 남길 수 있다. 작은 결정인데 워크플로우 전체가 달라진다.

**7. 레퍼런스 앱을 "왜" 좋아하는지 찾는 게 핵심이다** ZERO 앱을 보면서 "이 톤 좋다"고 느꼈지만, 처음엔 그 이유를 몰랐다. 대화하면서 "치유 느낌이라서 세이지 그린을 골랐는데, 사실 내가 만들고 싶은 건 데이터 대시보드"라는 걸 깨달았다. 레퍼런스의 표면(컬러)을 따라가면 길을 잃고, 본질(정보 위계, 대시보드 메타포)을 따라가면 일관성이 생긴다.

**8. 결정 피로가 올 때 "정체성 질문"으로 돌아가라** 한 시간 동안 컬러가 다섯 번 바뀌었다. 디자인 결정이 흔들릴 때마다 "이 앱은 치유 앱인가, 대시보드인가"로 돌아가니 결정이 빨라졌다. PRD의 핵심 원칙 한 문장이 흔들림을 막아주는 닻이었다.

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

### Summary

AI 코딩 워크플로우를 체계화하면서 "하네스(Harness)"와 "오케스트레이션(Orchestration)"이라는 개념을 접하고, 직접 적용해보려다 Claude한테 설득당한 과정이다. "부서별 AI 직원 병렬 실행"이라는 멋있는 그림에서 시작해서, 실용적인 최소 형태가 무엇인지 찾아가는 과정이었다.

**배경:** 피그마피디아 세미나(Claude Code + Figma MCP 디자인 시스템 자동화)를 보고 에이전트 오케스트레이션을 사이드 프로젝트에 적용하려 시도.

**결론:** 오케스트레이션 인프라보다 CLAUDE.md 하나 잘 쓰는 게 더 효과적이다. 인프라 만들다가 앱 못 만든다.

---

### 과정

#### 하네스(Harness)를 알게 된 경위

피그마 MCP + Claude Code를 활용한 디자인 시스템 자동화 세미나를 접했다. 거기서 처음으로 "하네스"라는 개념을 들었다.

**하네스가 뭔가?** 한 마디로, "Claude Code가 프로젝트를 일관되게 이해하고 작업하도록 만든 셋업 키트"다.

```
프로젝트/
├── .claude/
│   ├── agents/
│   │   ├── token-checker.md     ← 토큰 일치 검사 전담
│   │   ├── design-reviewer.md  ← 디자인 원칙 준수 검사
│   │   └── qa-reporter.md      ← 종합 QA 리포트
│   ├── commands/               ← 슬래시 커맨드
│   └── skills/                 ← 스킬 모듈
├── CLAUDE.md                   ← 프로젝트 컨텍스트 파일
└── docs/
    └── design-tokens.md        ← 토큰 매핑 테이블
```

---

#### 오케스트레이션 개념 이해

처음엔 "오케스트레이션"이라는 단어가 너무 추상적이었다. 직관적으로 이해한 방식을 정리하면:

**비유: 레스토랑 주방**

|역할|AI 오케스트레이션에서|
|---|---|
|오너 (나)|무엇을 만들지 결정|
|셰프 (메인 Claude Code)|전체 작업 총괄, 지시|
|파트 요리사 (서브 에이전트)|token-checker, design-reviewer 등|
|레시피 북 (CLAUDE.md)|작업 원칙과 규칙|

즉, **오케스트레이션 = Claude Code(오케스트레이터)가 서브 에이전트들에게 일을 나눠서 시키는 구조**.

---

#### 슬래시 커맨드 vs 스킬 vs 에이전트 구분

||슬래시 커맨드|스킬|에이전트|
|---|---|---|---|
|트리거|`/명령어` 수동|의도 감지 시 자동|역할 기반 호출|
|역할|사용자가 부르는 매크로|전문 지식 모듈|특정 역할 페르소나|
|위치|`.claude/commands/`|`.claude/skills/`|`.claude/agents/`|

---

#### 삽질: 개념 이해의 어려움

**삽질 1: 에이전트 오케스트레이션을 만들려다 Claude한테 대차게 설득당했다**

"부서별 AI 직원을 만들어서 병렬로 일 시키고 싶다"고 했다. Claude가 준비한 답변: Python SDK 코드, AgentDefinition 객체, 비동기 서브에이전트... 알아들을 수가 없었다.

다시 물었더니 돌아온 핵심:

> "솔직히 — 본인의 가장 큰 위험은 오케스트레이션을 못 만드는 것이 아니라, 오케스트레이션 만들다가 진료 관리 앱을 못 만드는 것이에요."

결론: 오케스트레이션은 인프라 구축이 아니라 사람의 결정을 대신 못 해준다. `.claude/agents/` 폴더에 역할별 마크다운 파일 3개 만드는 게 실질적 최소 형태다. 시작은 swiftui-builder, code-explainer, app-reviewer 3명으로.

**삽질 2: SDK가 뭔지 몰랐다**

"SDK를 쓰면 에이전트 만들 수 있어요"라는 말에 "SDK가 뭐야?"를 물었다. 정답: SDK = "남이 만들어둔 도구 세트". 그냥 코드로 Claude를 자동 호출하게 해주는 라이브러리. 비개발자에게 필요 없는 개념이었다.

**삽질 3: "웹앱 → Swift"를 "웹앱 → 웹/Swift"로 잘못 이해했다**

"웹앱을 Swift로 바꿀 수 있냐"고 물었는데, Claude가 "웹앱 = 웹, Swift = 네이티브 앱"이라고 교정해줬다. 웹앱은 Swift가 아니다. "웹 먼저 만들고 → 나중에 Swift로 다시 만드는" A 플랜으로 진행 확정.

**삽질 4: Claude Design, Claude 채팅, Claude Code가 다 다른 도구인 줄 몰랐다**

"화면은 클로드 채팅으로 만들어? 클로드 코드로 만들어?"라고 물었다가 세 번째 도구의 존재를 처음 알았다.

```
claude.ai        → 일반 채팅 (기획·대화)
claude.ai/design → Claude Design (디자인 시안·프로토타입)
터미널의 claude  → Claude Code (실제 코딩)
```

세 개가 별개 도구고, Claude Design에서 만든 시안을 "Claude Code로 보내기" 버튼으로 핸드오프하는 게 공식 워크플로우라는 것도 이때 알았다.

**삽질 5: "CLAUDE.md가 그냥 설명 파일 아냐?"** 처음엔 CLAUDE.md를 단순한 README라고 생각했다. 실제로 써보니까 Claude Code가 세션 시작 시 이 파일을 읽고 모든 작업의 기준으로 삼는다는 걸 알았다. "PRD와 충돌하면 멈추고 물어봐"라고 써두면 진짜로 그렇게 동작한다. 일종의 AI 계약서다.

**삽질 6: "에이전트를 만들면 알아서 실행되는 거 아냐?"** 아니다. 에이전트는 내가 호출해야 실행된다. 자동화되는 건 Hook(저장 시 자동 실행 스크립트)이고, 에이전트는 "이 역할을 맡은 AI"라는 페르소나 파일이다. "QA 돌려줘"라고 하면 qa-reporter 에이전트를 불러서 일을 시키는 구조.

**삽질 7: "Figma → 코드 자동화는 그냥 스크린샷 보내면 되는 거 아냐?"** 아니다. 스크린샷을 보내면 AI가 보고 짐작으로 코드를 짠다. Figma MCP 연동이 되어 있으면 컴포넌트의 실제 토큰 값(색상 변수명, 간격값 등)을 직접 읽어온다. "blue-500 색"이 아니라 "color-primary 변수"로 코드가 나온다. 디자인 시스템과 코드가 1:1로 연결된다.

---

### 공유할만한 인사이트

**1. CLAUDE.md는 AI와의 계약서다** Claude Code는 세션이 끝나면 기억이 없다. 매번 다시 설명해야 한다고 생각하면 지치는데, CLAUDE.md에 한 번 잘 써두면 그게 영구적인 컨텍스트가 된다. 쓸수록 효율이 높아지는 자산.

**2. 오케스트레이션을 만들다가 실제 앱을 못 만들 수 있다** 에이전트 시스템 구축이 목표가 되는 순간, 원래 만들려던 것이 뒤로 밀린다. 실용적인 최소 형태(`.claude/agents/` 폴더에 마크다운 3개)로 시작하고, 부족함을 느낄 때 확장하는 게 맞다. 도구는 일이 막힐 때만 보강한다.

**3. AI 시대에는 기획을 더 자세히 잡는 게 이득이다** "기획 너무 깊게 파면 안 됨, 빨리 코딩"은 사람이 코딩할 때 규칙이다. AI와 작업하면 정반대다. AI는 명세가 명확할수록 결과 품질이 폭증한다. "예쁘게 만들어줘" 30번 시키느니 PRD 한 번 잘 쓰는 게 빠르다. 특히 여러 에이전트를 굴리는 구조에선 PRD가 모든 직원의 공통 매뉴얼 역할을 한다.

**4. 하네스의 핵심은 "제약"이다** 에이전트, 슬래시 커맨드, 스킬 — 이것들이 복잡해 보이지만 핵심은 Claude Code가 내 프로젝트의 원칙을 어기지 못하게 만드는 가드레일이다. 1인 프로젝트에서 일관성을 유지하는 게 제일 힘든데, 하네스가 그걸 자동화해준다.

**5. 오케스트레이션은 "분업"이다** 모든 걸 Claude Code 하나에 시키면 컨텍스트가 길어지고 집중력이 떨어진다. 토큰 검사는 token-checker에게, 디자인 리뷰는 design-reviewer에게, QA는 qa-reporter에게. 사람 팀처럼 역할을 나누면 각각의 품질이 올라간다.

**6. 비개발자에게 가장 쓸만한 것: CLAUDE.md 먼저** 하네스 전체를 바로 도입하기는 어렵다. 그래도 당장 내일부터 CLAUDE.md만 잘 써도 Claude Code 활용도가 2배는 올라간다. 이것만이라도 먼저 해볼 것을 추천한다.

**7. 이 구조가 빛나는 순간: 다음 프로젝트** 처음 프로젝트에서 하네스를 잘 만들어두면, 다음 프로젝트는 그걸 복붙해서 시작하면 된다. 환경 세팅 삽질이 확 줄어든다. 지금 당장의 비용보다 미래의 레버리지를 보고 투자해야 하는 개념이다.
