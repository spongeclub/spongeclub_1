## 미션1: 내 고객은 누구고 왜 쓰는가 — 클로드 코드로 프로덕트 구현하기

### Summary
자기 이야기를 책으로 남기고 싶지만, 전문 작가가 아니라서 시작조차 못 하는 사람을 위한 **사전 인터뷰 웹앱**을 만들었다. 고객이 정식 작업 들어가기 전에 혼자 사용하는 도구로, AI가 20~25개 질문을 통해 인생의 재료를 끌어내고, 운영자(나)에게 정리본이 전달되어 정식 인터뷰의 출발점이 된다.

타겟은 1차로 30~40대 가업 2세 + 부모 세대, 서비스 자체는 일반인에게도 열림. 가격은 시범 15만원으로 시작해 검증 후 본가 결정.

AI를 셀링 포인트로 내세우지 않고, **"전문 작가가 아니어도 시도할 수 있다"**는 본질을 전면에 둠. AI는 자연스러운 도구로 뒤에 있고, _출간 경험자가 직접 동반한다_는 게 진짜 차별점.

### 과정 (타임라인별 + 삽질)

프로젝트 에서 만들고 싶은 거 정의 제대로 내려질 때까지 질의 응답 - 클로드 코드에 설명해줄 맥락 md 파일 정리해달라고 해서 받음-프로젝트 파일 쪽에 md 파일 저장-클로드코드에 폴더 지정 후 해당 md 파일 읽고, 질의 응답 달라고 프롬프트 시작-코트 및 작업 구상해나감-데모 단계라서 실제로 인터뷰 되는 기능은 일단 빼놓음 (앤트로픽 API 가 필요한데, 유료라서 좀 더 다듬고 쓰기로 결정)-웹페이지/어드민/고객용 DB 사이는 노션페이지까지만 만듦-대화 마지막에 프로젝트에 첨부할 해당 내용 홈페이지 주소 등 합쳐서 md 파일로 달라고 지시-프로젝트에 파일 첨부-프로젝트 첫 채팅방으로 가서 여태 나눈 대화 종합해서 프로젝트 지침 짜달라고 지시

#### 1단계. 사업 방향 확정까지

처음엔 *"3년차 친목 모임을 양질로 키우는 도구"*를 만들려고 했다. 그러다 한참 파보니 두 가지 문제 발견:

- (1) 내가 모임 유료화 안 해본 사람이라 그 분야의 근접성이 약함
- (2) 15명 친목 모임은 시장으로 보기 어려움 — _프로덕트_가 아닌 _운영 노하우_가 필요한 영역

**1차 폐기.** 모임 도구 아님.

다음으로 *"내 출판사로 남의 책 내주는 서비스(대행)"*를 검토. 객단가 높고, 시장 있음. 그런데 _"남의 책을 대신 내주는 사람"이라는 정체성_에 거부감이 들었다.

**2차 폐기.** 대행이 아니라, _"같이 통과해주는 동반자"_ 로 재정의.

이 두 번의 폐기에서 발견한 것: **내가 정말 풀고 싶은 문제는 "쓰고 싶은데 시작 못 하는 사람"의 문제다.** 내가 작년 에세이 쓸 때 한 번 통째로 엎고 다시 쓴 경험에서 알았다. _같은 사건도 어떤 시선으로 풀어내느냐에 따라 글의 결이 완전히 달라진다_. 그 첫 단추를 잡아주는 일이 내 자리였다.

#### 2단계. AI 셀링 포인트 안 쓰기로 한 결정 — 가장 큰 전환점

나는 전문가도 아니고, 대행을 쓰기엔 돈이 너무 많이 들었기 때문에 내 얘기를 하나하나 AI로 다듬고, 챕터마다 주변의 피드백을 받아가면서 썼다. 처음엔 이 사실이 부끄러웠고, _"전문 작가도 아닌데 자격이 있을까"_ 의심도 했다.

하지만 어떤 도움을 받았든 일반인이 스스로 삽질하며 만든 책을 출판까지 이뤄낸 경험이 생각보다 많지 않다는 것을 알았다. 이게 _숨길 약점_이 아니라 _차별점_일수도 있겠다고 생각.

그러나 동시에 **AI툴을 셀링 포인트로 내세우지 않기**로 결정. 이유는 두 가지:

- AI 자서전 시장이 이미 경쟁 (엄마의 인터뷰, RepetoAI 등)이고, _저렴·빠름_으로 포지셔닝되어 있음
- 내가 진짜 팔고 싶은 건 *"전문 작가가 아니어도 시도할 수 있다"*는 가치지, AI 자체가 아님. AI는 나와 고객을 도와줄 도구일 뿐

**삽질:** 분명히 초반 벤치마킹 하면서 찾아놓은 사이트들 있었는데, 도중에 이런 시장 비어있다고 AI가 단정했다가 내가 짚어줘서 다시 검색해 경쟁사 확인. 그제서야 진짜 포지셔닝이 잡힘 (_기념용 자동화_ vs _동반·브랜딩용 프리미엄_).

#### 3단계. 인스트럭션 먼저, 코드는 나중
웹앱 다 만들어진 뒤, AI 인터뷰의 _역할·말투·질문 순서·금지사항 등을 정의해둔 시스템 프롬프트를 마지막에 따로 분리된 파일(`system-prompt.md`)에 넣었다. 이 파일은 코드와 별개라서, 인스트럭션만 따로 열어서 수정할 수 있다. 다음에 인터뷰 결을 바꾸고 싶을 때  바로 바로 손볼 수 있게 된 것.


#### 4단계. Claude Code 작업 — 

절대적인 시간 부족 + Claude Code 입문자.. 처음엔 _질문에 일일이 답하기 피곤_해서 객관식으로 바꿔달라고 요청. 작업 속도 확 빨라짐.

**삽질 1.** CLAUDE.md 만들 때 폴더로 만들어버린 적 있음. 파일 vs 폴더 헷갈림. 물어보고 텍스트 파일로 다시 만들었다.

**삽질 2.** 인터뷰 시스템 프롬프트 분리(`system-prompt.md`)의 의미를 처음엔 못 잡음. 당장 인터뷰가 완전히 진행되는 툴을 원한게 아니었고, 이 단계는 조금 더 다듬고 싶었기에, 빈 파일로 남겨두고 나중에 좀 더 다듬고 채우기로 함

**삽질 3.** Anthropic API 비용 부담 때문에 _데모 모드_로 결정. 처음엔 _"API 안 꽂으면 인터뷰가 작동 안 되는데 이거 의미가 있나"_ 싶었음. 일단_DB 적재되는지 먼저 확인 + 어드민 코드 발급 + 손님 폼 + Notion 연동_ 까지 다 검증 가능. **검증 끝났고, API 꽂고, 인터뷰 시스템에 들어갈 내용 기획해서 넣기만 하면 가동되게끔

#### 5단계. 완성 후 — 지침서 박기

웹앱 완성 후 마지막에 system-prompt.md 빈 파일에 미리 작성해둔 인터뷰 시스템 프롬프트 통째로 붙여넣음.

### 공유할만한 인사이트

1. AI 를 앞세우는게 능사가 아닐 수도 있다. 내가 진짜 팔고 싶은 게 뭔지 고민해보는 과정. '_AI_ 를 통해서 만능으로 편리하게 다 할 수 있다'가 아니라 _"전문 작가가 아니어도 자기 책 한 권 남기기"_ 가 내가 주고 싶은 서비스였음. AI는 그걸 가능하게 해주는 도구일 뿐

2. 한 번에 완벽하게 만들어질거란 기대 버리기. 원래 모임 자체를 위한 어떤 웹페이지를 만들려고 했는데, 안에 컨텐츠가 비어있고, 유료화로 바로 넘어가기엔 친목으로 시작했고 가업승계 모임 사람들이라는 장벽이 존재. 내가 가진 자산들을 어떻게 연결 시킬 것인지에 대한 고민과 왜를 찾는게 더 중요하다고 생각.

3. 에이아이 툴을 잘 못다루다보니 냅다 해보고 삽질해보는 과정을 거치는 중인데, 프로젝트에서 먼저 기획 정의 내리고, 그 맥락을 잡아줄 지침을 달라 던가 코드에서 만든 작업물을 가지고 다시 프로젝트에 넣어 다시 지침을 위한 프롬프트를 짜달라던가 하는 식으로 하니까 생각보다 좀 더 흐름이 지금 상황이 나에게 자연스러웠던 것 같음. 남들은 어떻게 하는지 모르겠으나, 원래 지침이나 행동 정의를 무조건 제일 처음부터 잡고 작업을 시작해야한다고 생각했는데.. 생각보다 작업 시작하고 거꾸로 겅의를 내려도 나쁘지 않았다..? 현재의 나에겐 이 과정이 오히려 냅다 이것 저것 해볼 수 있게 해주었음.

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

### Summary

- **하네스 = AI한테 줄 지침서를 잘 만드는 일**
- **오케스트레이션 = 한 번에 다 시키지 않고 단계를 쪼개서 굴리는 일**

두 개 다 _내가 책 한 권 쓰면서 통과한 막힘과 풀림_을 토대로 짰다. 


### 최종 구현 결과물

**1. 하네스 적용:** `system-prompt.md` (AI 인터뷰 지침서)

- 역할 정의 + 진행 방식 + 5개 영역 20~25개 질문 + 톤·태도 + _절대 하지 말 것_ 목록 + 시작 인사 + 종료 시 정리본 출력 형식까지 담음
- 특히 _하지 말 것_ 부분이 핵심 — _"긍정 마무리 강요 금지" / "미리 결론짓지 말 것" / "한 번에 여러 질문 던지지 말 것" / "글쓰기 조언 절대 금지"_ 등. 내가 책 쓸 때 _이걸 했다가 망했지_ 싶은 함정들을 다 미리 막아둠

**2. 오케스트레이션 적용:** 인터뷰가 한 번에 다 굴러가지 않고 _단계가 분리됨_

- 손님 입장: 인터뷰 → 재료 정리본 받기 (사용자용)
- 운영자(나) 입장: 별도 정리본 받기 (운영자용 — 주의할 점 / 미답 영역)
- 정식 인터뷰는 _이걸 본 뒤에_ 진행

한 번에 _"이 손님 책 만들어줘"_ 시키지 않고, _재료 모으는 단계 / 운영자가 보고 결을 잡는 단계 / 본 인터뷰 단계_ 를 명확히 분리.


### 과정 (타임라인별 + 삽질)
처음엔 단어 자체가 어려웠다. _하네스가 뭐고 오케스트레이션이 뭐지._ 강의에서 _주방 비유_로 들었지만 막상 내 거에 적용하려니 막막함.

단어에 대한 정의보단 **내가 책 쓰면서 직접 겪은 일을 떠올려보자**고 했다.

- 책 쓸 때 처음 잡은 목차로 글을 쓰다가 글이 전체적으로 너무 다 우울해져서 한 번 통째로 엎은 경험이 있었다. _내가 미리 정의해둔 결_이 잘못되어 있었던 거다 → 이걸 AI한테 미리 알려주면 이런 실수를 줄일 수 있다 → **이게 하네스다**
- 책을 쓸 때 나는 인생 회고-> 큰 목차 쓰기 -> 작은 챕터 제목 쓰기 → 챕터별 글쓰기 식으로 단계를 쪼개 작업했다. 이런 단계 없이 글을 쓰려고 앉으면 우선 막막하고, 내용 자체가 중구난방으로 퍼질 수 있다.  또한 중요한걸 짚고 넘어가지 못할 수도 있다. 단계를 나누니까 매 단계마다 _내가 결을 다시 잡을_ 수 있었다 → **이게 오케스트레이션이다**

### 공유할만한 인사이트
**1. 어려운 단어부터 외우려 하지 말 것.** _하네스·오케스트레이션_ 같은 익숙하지 않은 걸 입력하려고 하기보단_내가 이미 해본 일_ 에 대입해보기. 그럼 그냥 _AI가 인터뷰 시 필요한 태도 및 하지말아야 할  것 등의 지침서 잘 짜기 / 일의 단계 쪼개기_ 였다. 단어가 아니라 _내가 통과한 경험_에서 출발해야 진짜 내 것이 된다.

**2. 지침서의 핵심은 _하지 말 것_ 목록이다.** _"이렇게 해라"_ 와 _"이건 하지 마"_ 가 같이 있을 때 원하는 방향으로 나올 가능성이 높다. 

**3. AI한테 한 번에 다 시키지 말기.**  단계를 쪼개서 매 단계마다 _내가 보고 결정_해야 하는 부분을 만들어야, 그 결과물이 _진짜 그 사람의 것_이 된다. AI를 알아서 굴러가게 두지 말고, _내가 매 단계마다 들어가는 자리_를 의도적으로 만들어두는 게 핵심. - EX) "이 부분은 내가 한 번 흐름 괜찮은지 보고, 수정할지 그대로 진행시킬지 결정할거니까 그 단계에선 내 허락 구해 ."
