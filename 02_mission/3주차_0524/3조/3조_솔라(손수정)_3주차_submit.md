### 공유할만한 인사이트

-  **GitHub Pages 와 호스팅 플랫폼(Vercel/Nettlify 등)의 차이**==
	GitHub Pages는 "구동"이라는 개념보다는 "파일을 그대로 전달 해주는 역할"
	예를 들면 종이에 인쇄해서 벽에 붙여 놓는 것.
	따라서 한 번 붙여놓으면 누구나 와서 볼 수 있지만, 그 종이가 스스로 뭘 하지는 못함.
	
	**가능한 것 ✅**
	- **소개 사이트, 포트폴리오** — 그냥 보여주기만 하면 되니까
	- **블로그** — 글을 미리 써서 올려두는 거니까
	- **간단한 웹 게임, 계산기** — 브라우저 안에서만 돌아가니까
	- **회사 홈페이지** — 정보만 보여주면 되니까
	
	**불가능한 것** ❌
	- **회원가입/로그인** — 누가 가입했는지 저장할 곳이 없음
	- **댓글, 게시판** — 사용자가 쓴 글을 저장 못 함
	- **쇼핑몰 결제** — 비밀 정보를 다룰 서버가 없음
	- **검색 기능** (DB 기반) — 검색할 데이터베이스가 없음

- **클로드도 잘못된 판단을 내리는 경우가 있다.**
	보안 관련 사항은 반드시 맨 처음 채팅 시작할 때 명시할 것.

- **궁금한 점** : 분명 며칠 전까진 레딧 검색이 잘 되었던 것 같은데 왜 안되는지 모르겠다(아직 클로드한테 못 물어봄)

## 미션2: 내가 정의하고 구현한 하네스 + 오케스트레이션

#### 내가 `정의`한
- **하네스** : 내가 하고 싶은 일을 클로드가 일관되게 처리하도록, 클로드에게 규칙(어떻게 일하는지)과 도구(뭘로 일하는지)를 쥐어주는 것
- **오케스트레이션** : 여러 팀(에이전트)이 일할 때 누가 먼저 하고, 누구한테 넘기고, 누가 감독할지 흐름을 짜는 것

#### 내가 `구현`한
- **하네스 (규칙 + 도구 두 층)**
	규칙 층:
	- 5개 SKILL.md 파일 — 5팀(파트너·비서·디자인·개발·기획)의 톤·역할·트리거·금기 박제
	- team-os-design.md 727줄 — 5팀이 다 공유하는 운영 규약
	- 페르소나 전환 규칙 — 명시 호출(파트너→비서팀) vs 자동 전환(비서팀→하위팀)
	도구 층:
	- 공유 게시판 team-board.md — 5팀이 일감 주고받는 단일 통신 채널
	- 박제 인프라 3층
	    - partner-decisions/ (결정 파일)
	    - partner-notes/raw-log.md + patterns.md (파트너 학습 2층)
	    - memory/ (5팀 공유 메모리)
	- 안전망: proposed/ 제안 모드 (본 파일 직접 못 건드림)
- **오케스트레이션 (흐름 짜기)**
	- 5팀 흐름 설계: 파트너 → 비서팀 → 하위팀(디자인/개발/기획) → 비서팀 → 본 파일 반영
	- 비서팀이 오케스트레이터 역할 — 우선순위 5단계 알고리즘, 인계 프로토콜, 자동 관전 트리거 3개(막힘 24h·핑퐁 3회·충돌)
	- 검수 루프 — 디자인 명세 → 개발 구현 → 디자인 검수 (다단 파이프라인)
	- 개발팀 내부 2-pass 패턴 — 작성자 모자/검토자 모자 번갈아
	- Human-in-the-loop 신호 — "응"/"다음"/결정 한 줄 (사람이 핸들 잡는 지점)
