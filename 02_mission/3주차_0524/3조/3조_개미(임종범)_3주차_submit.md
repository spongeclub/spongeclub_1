`즐거운 개미집`은 회사와 집만 반복하는 개미들을 위한 작은 모임/커뮤니티 웹사이트입니다.  
이번 미션에서는 AI와 함께 아이디어 수준의 모임 서비스를 실제로 접속 가능한 MVP 웹사이트로 구현했습니다.

핵심 목표는 단순한 소개 페이지가 아니라, 방문자가 `오늘의 질문`에 익명으로 답변하고, 다른 사람의 답변을 보고, 좋아요를 누르며, 모임 상세 페이지까지 확인할 수 있는 구조를 만드는 것이었습니다. 좌측 페이지는 웹사이트에 체류 시간을 늘리고 실질적인 모임 신천이라는 구매 전환까지 이어지는 구조입니다.

개발은 제가 직접 코드를 모두 작성하기보다, GPT와 Claude Code를 함께 활용해 진행했습니다.  
GPT는 요구사항 정리와 작업 지시문 설계를 맡았고, Claude Code는 실제 코드 수정과 검증을 담당했습니다. 이후 GitHub, Vercel, Supabase를 연결해 실제 배포까지 완료했습니다.

## 2단계. Supabase 연결과 DB 설계

Supabase에 `today_contents`, `today_answers` 테이블을 만들고, 오늘의 질문과 답변이 저장되는 구조를 설계했습니다.

처음에는 테이블과 RLS 정책을 만들었지만, 실제 답변 저장 단계에서 권한 문제가 발생했습니다.

### 삽질

답변을 작성했는데 화면에는 다음과 같은 메시지가 떴습니다.

> 답변 저장 기능이 아직 연결되지 않았어요. (운영자 준비 중)

원인은 Supabase의 RLS 정책만 설정하고, `anon` role에 필요한 `GRANT` 권한을 주지 않았기 때문이었습니다.

### 해결

`grant usage`, `grant select`, `grant insert` 권한을 추가한 뒤 답변 저장과 조회가 정상 작동했습니다.

이때 배운 점은 **RLS 정책과 GRANT 권한은 별개**라는 점이었습니다.

## 4단계. 답변 기능 MVP 구현

오늘의 질문 조회, 답변 작성, 답변자 정보 입력 모달, 답변 저장, 내 답변 카드, 타인의 답변 보기, 좋아요, 수정 기능을 구현했습니다.

처음에는 답변을 남긴 뒤 새로고침하면 다시 입력창이 뜨는 문제가 있었습니다.

### 삽질

답변은 DB에 저장되어 있었지만, 브라우저가 “이 사용자가 이미 답변했는지”를 다시 불러오지 못했습니다.

### 해결

로그인 기능을 넣는 대신, `localStorage`의 `client_id`와 현재 질문의 `content_id`를 기준으로 본인 답변을 복원하는 방식을 적용했습니다.

그 결과 같은 브라우저에서는 새로고침 후에도 본인 답변이 유지되도록 만들었습니다.

## 5단계. 중복 제출 방지

같은 사용자가 같은 질문에 여러 번 답변을 남기는 문제가 생길 수 있어, 코드 레벨에서 중복 제출 방지를 추가했습니다.

적용한 방식은 다음과 같습니다.

- 제출 직전 기존 답변이 있는지 확인
- 이미 답변이 있으면 새로 저장하지 않고 기존 답변을 불러오기
- 저장 중에는 버튼을 비활성화
- 중복 클릭 방지를 위한 잠금 처리 추가

DB 제약조건까지 넣지는 않았지만, MVP 단계에서는 같은 브라우저 기준으로 중복 답변을 막는 수준까지 구현했습니다.

로컬에서 기능을 확인한 뒤 GitHub private repository를 만들고 코드를 push했습니다.  
이후 Vercel과 GitHub를 연결해 `main` 브랜치에 push하면 자동으로 배포되는 구조를 만들었습니다.

### 해결

기존 Google 계정으로 Vercel에 로그인한 뒤, Vercel 설정에서 GitHub 계정을 연결하는 방식으로 해결했습니다.

이후 GitHub App을 설치하고 `joyful-ant-house` repository만 선택해 Vercel 배포를 완료했습니다.

### 공유할만한 인사이트
## 1. AI에게 “만들어줘”보다 “작업 범위와 금지 범위”를 주는 게 훨씬 중요했다

Claude Code는 코드를 빠르게 수정할 수 있지만, 아무렇게나 맡기면 예상하지 않은 파일이나 기능까지 건드릴 수 있습니다.

그래서 매번 다음을 명확히 정했습니다.

- 어떤 기능을 수정할지
- 어떤 기능은 절대 건드리지 말지
- `.env.local`은 수정하지 말 것
- secret key나 service role key는 사용하지 말 것
- 사용자가 승인하기 전 commit/push하지 말 것
- `tsc`, `lint`, `build`를 반드시 통과할 것

이런 조건들이 없었다면 비개발자 입장에서 어디가 바뀌었는지 통제하기 어려웠을 것입니다.

---
## 2. 비개발자에게 AI 개발은 “코딩”보다 “검증 흐름 설계”가 더 중요했다

제가 직접 모든 코드를 이해하고 작성한 것은 아니지만, 작업의 흐름은 계속 관리해야 했습니다.

특히 아래 순서가 중요했습니다.

1. GPT로 요구사항 정리
2. Claude Code에 실행 지시
3. 로컬에서 화면 확인
4. 오류 발생 시 원인 분리
5. `tsc/lint/build` 검증
6. 승인 후 commit/push
7. Vercel 배포 확인

결국 비개발자가 AI로 개발할 때 중요한 역량은 “코드를 직접 다 짜는 능력”보다, **어떤 순서로 확인해야 안전한지 아는 능력**에 가까웠습니다.

---
## 3. 작은 기능 하나에도 운영 판단이 들어간다

예를 들어 “익명 답변” 기능 하나에도 다음 문제가 따라왔습니다.

- 닉네임, 성별, 연령대를 받아도 되는가?
- 개인정보 안내 문구가 필요한가?
- 부적절한 답변은 어떻게 삭제할 것인가?
- 같은 사람이 여러 번 답변하면 어떻게 할 것인가?
- localStorage를 지우면 본인 답변을 복원할 수 없는 문제를 어떻게 볼 것인가?

즉, 기능 구현은 기술 문제가 아니라 운영 문제와 연결되어 있었습니다.

---
## 4. MVP는 완성품이 아니라 “테스트 가능한 질문”이어야 했다

처음부터 완성된 커뮤니티 사이트를 만들려고 했다면 범위가 너무 커졌을 것입니다.

이번에는 질문을 이렇게 좁혔습니다.

> 사람들이 오늘의 질문에 실제로 답변을 남길까?  
> 다른 사람의 답변을 보고 싶어 할까?  
> 이 흐름이 모임 신청으로 이어질 가능성이 있을까?

그래서 현재 결과물은 완성된 서비스라기보다, 앞으로의 모임 사업을 검증하기 위한 작은 실험 장치에 가깝습니다.

## 미션2: 하네스와 오케스트레이션

**제가 정의한 하네스는 AI가 좋은 답을 내도록 붙잡아주는 작업 구조입니다.** 

단순히 “잘 답해줘”라고 요청하는 것이 아니라, 역할, 입력값, 출력 형식, 판단 기준, 금지사항을 미리 정해 AI의 답변이 흔들리지 않도록 만드는 장치라고 이해했습니다.

저는 앞으로 하네스를 ‘AI와 협업할 때의 안전벨트’처럼 사용하고 싶습니다. 
특히 제가 만든 즐거운 개미집 OS에서는 비개발자인 제가 Claude Code와 함께 웹사이트를 만들고 있기 때문에, 작업 범위, 수정 금지 영역, 검증 명령, commit/push 전 승인 절차를 명확히 적어두는 것이 중요했습니다. 
예를 들어 Supabase secret key를 사용하지 않기, .env.local을 건드리지 않기, 오늘의 질문 기능과 모임 상세 작업을 분리하기, tsc/lint/build를 통과한 뒤에만 다음 단계로 넘어가기 같은 기준들이 저에게는 하네스입니다.

**제가 정의한 오케스트레이션은 여러 AI와 도구가 각자의 역할을 맡아 하나의 결과물을 만들도록 지휘하는 흐름입니다.** 
GPT는 요구사항을 정리하고, Claude Code는 실제 코드를 수정하고, GitHub는 변경 이력을 저장하고, Vercel은 배포를 담당합니다. 
저는 이 흐름을 무작정 한 번에 진행하지 않고, 요구사항 정리 → Claude Code 실행 → 로컬 검증 → 사용자 확인 → commit/push → Vercel 배포 → 실제 테스트의 순서로 운영하고 있습니다.

미션 1의 “나는 누구고 왜 쓰는가?” 프롬프트에도 이 개념을 적용해볼 수 있다고 생각합니다.
