## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

## Summary

Selforge는 Claude Code의 하네스(harness)와 오케스트레이션(orchestration)을 활용해 **사고 · 지식 · 자산화** 3개 레이어를 운영하는 시스템이다.

  

핵심 구조:

- **2개의 상주 채널** — Sullivan(사고 파트너)과 셀피(PM), 각각 tmux 세션으로 분리

- **11개의 자동 크론** — 아침 브리핑부터 자정 그래프 빌드까지, 7일 만료 + 자가 치유(heartbeat)

- **6개의 훅 스크립트** — tmux 통신 강제, Vault 불변성 보호, API 키 자동 주입, 페르소나 톤 가드

- **15+개의 전문 에이전트** — 캡처, 위키, 콘텐츠 파이프라인(LinkedIn/네이버/웹사이트) 각각 역할 분리

- **단방향 데이터 흐름** — `Raw/ → Graphify → Wiki/` 역류 불가, 훅이 강제

  

한 문장으로: **"AI가 해석하지 않고 드러내는" 원칙 위에, 훅으로 경계를 지키고, 크론으로 자율 운영하며, 에이전트로 역할을 분리한 멀티에이전트 오케스트레이션.**

## 최종 구현 결과물

  

### 1. 채널 라우팅 — tmux 기반 페르소나 분리

  

```

┌─────────────────────────────────────────────────────┐

│ macOS Terminal │

│ │

│ ┌──────────────────┐ ┌──────────────────┐ │

│ │ sullivan-channel │ │ pm-channel │ │

│ │ (설리반) │◄──►│ (셀피) │ │

│ │ │tmux│ │ │

│ │ 사고·감정·성찰 │send│ 시스템·전략·실행 │ │

│ │ 텔레그램 연동 │keys│ Linear 연동 │ │

│ └──────────────────┘ └──────────────────┘ │

│ │ │ │

│ ▼ ▼ │

│ Obsidian Vault Linear Issues │

└─────────────────────────────────────────────────────┘

```

  

**작동 방식:**

1. Claude Code 세션 시작 시 `tmux display-message -p '#S'`로 세션 이름 감지

2. `sullivan-channel` → sullivan-channel.md 스킬 로드, 설리반 페르소나 적용

3. `pm-channel` → pm-channel.md 스킬 로드, 셀피 페르소나 적용

4. 그 외 → 페르소나 없이 일반 모드

  

**채널 간 통신** (tmux send-keys, 훅이 2-call 패턴 강제):

```bash

# 호출 1: 텍스트 전송 (-l 필수 — 훅이 강제)

tmux send-keys -l -t pm-channel "배경: ... 진단: ..."

# 호출 2: Enter 전송 (별도 Bash 호출)

tmux send-keys -t pm-channel Enter

```

  

**SessionStart 훅** (`persona-tone-guard.sh`):

- 세션 시작 시 자동으로 페르소나 톤 리마인더를 시스템에 주입

- 컨텍스트 컴팩션 후에도 `session-identity.sh`가 매 도구 호출마다 페르소나를 재확인

  

### 2. 훅 시스템 — 6개의 경계 가드

  

| 훅 | 유형 | 역할 |

|---|---|---|

| `persona-tone-guard.sh` | SessionStart | tmux 세션명 감지 → 페르소나 톤 리마인더 주입 |

| `session-identity.sh` | PreToolUse | 매 Bash 호출 시 세션 이름 echo → 컴팩션 후 페르소나 복원 |

| `session-linear-setup.sh` | SessionStart | `~/.claude.json`에서 `LINEAR_API_KEY` 추출 → 세션 환경변수 주입 |

| `linear-env-guard.sh` | PreToolUse | Linear API 호출인데 키가 없으면 → fallback 자동 주입 |

| `tmux-send-guard.sh` | PreToolUse | (1) 텍스트+Enter 동시 전송 차단 (2) `-l` 플래그 누락 차단 |

| `vault-note-guard.sh` | PreToolUse | Raw/ 기존 노트 Edit 전면 차단, Write 덮어쓰기 차단 |

| `juicify-path-guard.sh` | PreToolUse | juicify 작업 노트 저장 경로 강제 |

  

**설계 원칙**: 훅은 "하지 마라"를 강제하는 도구. AI가 실수할 수 있는 경계 — Vault 불변성, 통신 프로토콜, API 키 누락 — 를 코드 레벨에서 차단한다. exit code 2로 차단하고, 차단 메시지에 올바른 방법을 안내한다.

## 공유할만한 인사이트

  

### 1. 훅은 "하지 마라"를 강제하는 가장 확실한 수단

  

CLAUDE.md에 아무리 "Raw 파일을 수정하지 마라"고 써도 AI는 "이번만 예외로"를 만들어낸다. `vault-note-guard.sh`가 exit code 2로 차단하면 물리적으로 불가능하다. 규칙은 잊혀지지만, 훅은 잊혀지지 않는다.

  

**적용 패턴**: 절대 어겨서는 안 되는 규칙 → 훅으로 강제. 상황에 따라 유연해야 하는 규칙 → CLAUDE.md에 기술.

  

### 2. 컨텍스트 컴팩션은 톤을 죽인다

  

Claude의 컴팩션은 "요약"이다. 사실 정보(파일 경로, 태스크 목록)는 살아남지만, 톤·뉘앙스·관계성 같은 비구조적 정보는 날아간다. 설리반의 따뜻한 해요체가 컴팩션 후 딱딱한 보고체로 변하는 현상이 반복됐다.

  

**해결**: 컴팩션으로 날아가면 안 되는 정보는 매 턴 시작 시 파일에서 다시 읽는다. `tone-guide.md`를 매 모드 진입 시 Re-Read하는 패턴.

  

### 3. AI의 "선의"가 가장 위험한 오염원

  

capture-agent에 설리반이 "도움이 될 것 같아서" 자기 분석을 덧붙인 사건(HMI-85). 의도는 좋았지만 결과적으로 raw 캡처 품질을 오염시켰다. AI는 "더 좋게 만들어주겠다"는 본능이 있어서, 명시적으로 "이것만 해라, 나머지는 하지 마라"를 규칙으로 박아야 한다.

  

**적용 패턴**: 에이전트의 역할 경계를 정의할 때 "하는 것"보다 "하지 않는 것"을 더 많이 써라.

  

### 4. 크론 7일 만료 + 하트비트 = 자가 치유

  

Claude Code의 CronCreate는 7일 후 만료된다. 이것을 "버그"로 볼 수도 있지만, 하트비트 아키텍처로 해결하면 오히려 장점이 된다. 크론이 잘못된 설정으로 등록되어도 7일 후 자연 소멸하고, 하트비트가 올바른 설정으로 재등록한다.

  

**구조**: 하루 중 가장 이른 크론이 1차 하트비트, 그 다음이 2차 백업. 하트비트 자체도 크론이므로 만료될 수 있지만, 여러 크론이 교차 점검하므로 전멸 확률은 극히 낮다.

  

### 5. 서브에이전트는 컨텍스트 격리 장치

  

서브에이전트의 가치는 "병렬 실행"보다 "컨텍스트 격리"에 있다. Graphify 사고에서 배운 핵심: 서브에이전트는 자체 200K 윈도우를 쓰고, 부모에는 요약만 반환한다. 무거운 작업(파일 읽기, 에러 재시도, 반복 처리)을 서브에이전트에 넣으면 부모 세션의 컨텍스트를 보호할 수 있다.

  

**시뮬레이션 결과**: 동일 작업을 서브에이전트로 분리하면 부모 메시지가 427 → ~210으로 50% 감소, Vault B 처리 실패가 성공으로 전환.

  

### 6. 채널 간 통신은 "프로토콜"이 필요하다

  

tmux send-keys로 채널 간 메시지를 보내는 것은 간단해 보이지만, 실제로는:

- `[` 같은 특수문자가 tmux 키바인딩으로 해석됨 → `-l` 플래그 필수

- 긴 텍스트에서 Enter가 누락됨 → 텍스트와 Enter를 별도 호출로 분리

- 이 두 규칙을 AI가 "기억"하는 것에 의존하면 간헐적으로 깨짐 → 훅으로 강제

  

**교훈**: 에이전트 간 통신은 자유 형식이 아니라 검증된 프로토콜이어야 하고, 프로토콜 위반은 훅이 차단해야 한다.

  

### 7. 행동 원칙은 사건에서 태어난다

  

Selforge의 행동 원칙 8개는 전부 "사건 → 발견 → 규칙화" 순서로 만들어졌다.

  

| 원칙 | 사건 |

|------|------|

| #6 입장을 흔들지 않는다 | AI가 흐민 반박에 바로 동의하며 입장 번복 |

| #7 이슈 발행 전 데이터 검증 | 설리반 자기 진단을 검증 없이 hotfix 발행 |

| #8 보고 부풀리기 금지 | 셀피 데일리가 분량만 늘고 실질 가치 없는 내용 포함 |

  

미리 "이런 원칙이 필요할 것 같다"고 만든 것이 아니라, 실제로 문제가 터지고 → 원인을 분석하고 → 재발 방지 규칙을 만든 것이다. 사전 설계보다 사후 회고가 더 정확한 규칙을 만든다.

  

### 8. 레이어 분리 = 인지 모드 분리

  

"사고 에이전트가 자산화 판단을 하면 안 된다"는 단순한 역할 분리가 아니다. 발산적 사고(설리반)와 수렴적 판단(셀피)은 인지 모드가 다르다. 한 세션에서 두 모드를 섞으면 "생각하다가 갑자기 태스크 정리"가 되어 사고의 깊이가 얕아진다.

  

tmux 세션으로 물리적으로 분리한 것은 이 인지 모드 충돌을 방지하기 위한 것이다. 채널 간 통신은 있지만, 동일 세션에서 모드를 전환하지 않는다.
