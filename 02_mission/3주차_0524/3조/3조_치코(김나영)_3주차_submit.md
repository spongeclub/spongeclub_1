- 대략 구조/방향은 정해져있었음 -> 스폰지클럽 7주 과제 현황판 맨 위에 들어갈 비주얼 컴포넌트

	- (b) 총 6개의 조가 참여함

		- (a) 7주 동안 집이 단계별로 완성되는 과정을 구현하고 싶음
		- (b) 조원들이 과제를 제출할 때마다 파인애플 본체, 창문, 문 등이 하나씩 추가되는 형태

- 고객 (3구조)
	- 첫 번째는 **클럽 멤버들**이다.
		- 멤버들은 숫자보다 “우리 조 집이 이만큼 지어졌네?”를 볼 때 더 직관적으로 진척감을 느낄 수 있다.
	- 두 번째는 **이 컴포넌트를 실제 현황판에 붙이는 사람**이다.  
		- 복잡하게 세팅하지 않고, 한 줄로 가져와서 바로 쓸 수 있어야 한다.
	- 세 번째는 **미래의 나**다.  
		- 나중에 조가 늘어나거나 단계가 바뀌어도, 여러 파일을 뒤지지 않고 한 파일만 고치면 되게 만들고 싶었다.

- WHY?
	- **퍼센트 숫자만으로는 사람들이 움직이지 않는다.**  
		- 집이 조금씩 완성되는 시각적 보상, 6개 조가 한 화면에서 비교되는 느낌, 마지막 단계로 갈수록 디테일이 채워지는 재미가 있으면 사람들이 “우리 조도 더 채워야지”라는 동기를 느낄 수 있다.
	- **조별 성과가 개인에 의해 만들어진다는 것을 동시에 연결**
		- 호버하면 강조되고 클릭하면 해당 조로 이동하는 형태.
		- 멤버들이 자기 조를 더 쉽게 찾고 눌러보게 하기 위해서였다.

### 공유할만한 인사이트

첫째, **왜 쓰는지 한 문장이 정해지면 기술 결정이 쉬워진다.**  
“숫자보다 집이 자라는 모습을 보여주고 싶다”는 목적이 있었기 때문에 단일 파일, 단계 설계, 클릭 이동 같은 결정이 자연스럽게 나왔다.

둘째, **결정은 빠르게 하고, 검증은 눈으로 해야 한다.**  
말로 오래 고민하는 것보다 모킹업 3개를 만들어놓고 비교하는 게 훨씬 빨랐다.

셋째, **첫 결과물을 너무 믿으면 안 된다.**  
처음 결과물이 괜찮아 보여도, 레퍼런스와 대조해보면 부족한 부분이 보인다.

넷째, **실제로 쓰는 사람뿐 아니라 붙이는 사람과 미래의 나까지 고려해야 한다.**  
그래야 당장 예쁜 결과물을 넘어서, 나중에도 고치기 쉬운 결과물이 된다.

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션


#### 하네스 = 스킬 안의 개입 규칙
**하네스/harness**는 “대화를 붙잡아주는 규칙”

예를 들면 이런 거야.

> 사용자가 너무 추상적으로 대답하면 바로 구체화 질문을 던진다.  
> 사용자가 핵심에서 벗어나면 다시 원래 질문으로 데려온다.  

- 지금 사용하고 있는 하네스 -> sense-poller.ts
	- `sense-poller.ts`는 텔레그램 메시지를 받고, 그 메시지를 처리하기 위해 `claude -p`를 새로 띄우고, 필요한 상태 파일을 관리하지.
		- 예를 들면: 텔레그램 메시지 수신, 메시지 1건마다 Claude 세션 spawn, `logical-day-date` 관리, `recap-due-at` 관리, 언제 recap을 만들지 판단, Claude에게 어떤 prompt를 넘길지 구성
	- 모델 바깥에서 **모델을 실행시키고, 입력을 넣고, 상태를 관리하는 코드**야.
그래서 `sense-poller.ts`는 센세봇의 대표적인 하네스야.


#### 오케스트레이션 = 여러 AI/세션을 어떻게 굴릴지 짠 구조 (운영구조)

**여러 세션이나 에이전트를 어떻게 연결하고 순서대로 굴릴지**에 대한 거야.

- 지금 사용하고 있는 오케스트레이션은 
	- 텔레그램 메시지가 오면 Claude 세션을 새로 띄운다
	- 분석가, 라이브러리, PM, 에디터 에이전트를 각각 다른 역할로 돌린다
	- 누가 언제 깨어나고, 어떤 데이터를 누구에게 넘길지 정한다
	이 전체 흐름을 짜는 게 **오케스트레이션**이야.


이 구조를 짜고 운영한 게 여기서 말하는 **진짜 오케스트레이션 작업**이라는 뜻이야.
**하네스는 AI 하나를 실제로 일하게 만드는 장치고, 오케스트레이션은 여러 AI/세션을 함께 굴리는 지휘 체계야.**
