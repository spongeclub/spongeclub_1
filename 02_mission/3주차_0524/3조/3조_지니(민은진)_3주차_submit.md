#### 2) 왜 쓰는가 — marketing-os가 해주는 일

`real-javis/marketing-os/` (Next.js 16 + Tailwind 4, [http://localhost:3002](http://localhost:3002/) 라이브)

**입력**: 자사 광고·계약 XLSX 업로드 (10MB, 8시트) **자동 처리**:

**출력**:

- Overview KPI 8개 카드 (광고비·인입·계약·ROAS·CPA·CPC·CTR·계약율)

- 월별 시계열 + 광고비 막대
- **10가지 마케팅 이론 룰** (70/20/10 · 3x Kill · ROAS Health · 학습 50건 · 시즌성 -30% · 가망 비율 · 중복률 · LTV:CAC 3x · CTR 벤치마크 · 상담→계약 전환율)
- 룰별 status (good / warning / danger / info) + 사실 근거 + 💡 권장 액션

### 공유할만한 인사이트
**1. 활용 마케팅 OS의 진짜 차별점 = 이론 기반 판단 + 이슈 예측** 단순 KPI 표는 OS의 1%. "잘하고 있는지" 룰로 자동 판단하고, 위험을 사전에 알리는 게 표와 OS의 경계. 룰은 fact + evidence + recommendation 세 묶음이어야 자동화로서 의미.

**2. 클라이언트 사이드 XLSX 파싱은 PII 보호의 가장 작은 첫 걸음** 이메일·휴대폰이 외부로 안 나감, Vercel 한도 부담 X, 10MB까지 OK. 단점은 첫 로드 1~3초. 마케팅 데이터는 PII 덩어리라 서버 안 거치는 게 신뢰의 기본값.

**3. 사용자가 명확해야 각 부품의 임계값이 정해진다** 같은 "CTR 벤치마크" 룰이라도 이지민이 다니는 회사와 다른 회사의 목표 CTR이 다름. 페르소나가 추상이면 임계값도 추상. 임계값은 사용자가 명확해진 다음에야 자기 옷처럼 맞게 튜닝 가능.

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

### Summary
하네스 - 모든 작업이 따르는 가이드(규칙/맥락)
오케스트레이션 = 어떤 부품이 언제·어떤 순서로 작동하고 어디서 사람한테 물어볼지 정한 흐름

### 최종 구현 결과물
**marketing-os 적용 계약서 1장** — 새 부품 하나에 하네스·오케스트레이션·승인 지점이 어떻게 박혔는지.

#### 🎼 하네스 (악보 — marketing-os가 따르는 규칙)

#### 🎼 오케스트레이션 (지휘 — marketing-os 안에서 부품들이 언제·어떻게)

|트리거|자동|사람 승인 지점|
|---|---|---|
|XLSX 업로드|4시트 자동 인식 + UTM 정규화 + 인입↔계약 매칭|(없음 — 데이터 그대로 신뢰)|
|KPI 계산|Overview 8개 + 매체별 13컬럼 + 월별 시계열 자동|(없음 — 수식 그대로)|
|룰 판단|10개 룰 status 자동 부여|**임계값 튜닝은 사람이 결정** (예: CTR 1% vs 1.5%)|
|이슈 예측|danger+warning 자동 상단 노출|**어느 이슈 먼저 손볼지 사람이 판단**|
|권장 액션|룰별 recommendation 자동 생성|**실제 액션 실행은 사람이 승인** (예산 이동·캠페인 끄기 등)|

#### 🎼 승인 지점 = 사람이 답을 줘야 하는 곳

- **임계값 튜닝**: 회사마다 다른 KPI 목표를 사람이 못 박아야 룰이 작동
- **이슈 우선순위**: 5개 이슈가 동시에 나오면 어느 것부터인지 사람 판단
- **실행 결정**: "이 캠페인 끄세요"라는 권장에 실제 OFF는 사람이 누름

### 과정 (타임라인별 + 삽질)
**marketing-os 만들면서 "하네스·오케스트레이션이 필요해진 순간 3개"**

#### 순간 ① — PII 외부 전송 이슈 직면

- 처음엔 서버 사이드 파싱 고민. 근데 이메일·휴대폰이 외부 서버로 흘러가면 신뢰 문제
- → **클라이언트 사이드 XLSX 파싱**으로 결정. 이건 하네스(PII는 자체 보유 강제)이자 오케스트레이션의 첫 승인 지점("외부 전송 X"라는 사람의 결정)

#### 순간 ② — UTM 표기 Carrot↔carrot 혼재 발견

- UTM 빌더 규칙은 "영문 소문자"인데 실제 데이터엔 대소문자 혼재
- 정규화 안 했으면 매체별 집계가 두 줄로 쪼개져서 KPI 전멸
- → **lowercase + 별칭 매핑**을 하네스 규칙으로 박음. 데이터 들어올 때 무조건 정규화

#### 순간 ③ — 룰 임계값이 회사마다 다름

- CTR 벤치마크 1.5%? 1%? 회사·업종·매체별 다름
- 모든 임계값을 코드에 박으면 jinny 회사 외에는 무용지물
- → **임계값을 사람이 정하는 변수로 빼고**, 코드는 기본값(업계 벤치마크)만 제공. 이게 OS의 "승인 지점"

**삽질**

- **자기 해석 함정 5번째 재발** — ⑤번 답을 "SNS 계정 만들기"로 추측. 사용자가 옵션 라벨이나 의도를 명시했음에도 자기식으로 풀어버린 함정. CLAUDE.md·메모리에 강제 박았는데도 같은 날 다시 발생. 하네스(메모리)와 오케스트레이션(자동 환기)이 다 있어도 사람이 그 위에서 한 번 더 확인이 필요하다는 교훈
- **CronCreate `durable=true` 무시** — 며칠 단위 자동 알림 불가능. 메모리 + 세션 시작 환기(C 옵션)로 대안 잡음. "다 자동"이 안 되니 명시적 사람 확인 지점을 박는 게 OS

### 공유할만한 인사이트
**1. "자동화한 개 = 부품 1개" — marketing-os 자체도 하나일 뿐** 단순 자동화 ≠ 오케스트레이션. real-javis + marketing-os + CarouselOS가 서로 알맞은 타이밍·맥락·우선순위로 조율되어야 진짜 OS. marketing-os 1개 만들었다고 OS 완성이 아니라, 다른 부품과 어떻게 손잡는지가 다음 단계.

**2. "승인 지점이 명시된 자동" = 임계값 판단이 사람의 몫인 이유** 모든 룰을 코드에 박으면 jinny 외 누구도 못 씀. 임계값을 사람이 정할 변수로 빼는 게 OS의 본질이고, 그게 1주차 선언문 "마케팅 액션 승인만 하고 나머지는 시스템"의 진짜 의미였음.

**3. "하네스 부족하면 오케스트레이션 망가짐" — UTM 정규화 안 했으면 KPI 전멸** Carrot vs carrot 표기 혼재 하나가 정규화 안 됐다면 매체별 집계가 두 줄로 쪼개져서 모든 KPI가 거짓말. 하네스(정규화 규칙)가 없으면 그 위의 어떤 오케스트레이션도 무의미.

## 미션3: 스폰지클럽을 하며 남기고 싶은 생각과 고민 SNS 글 작성

### Summary
3주차 마지막에 가서야 OS의 정의가 한 발 더 갔다. **"OS = 하루의 리듬 + 그 한 명에게 닿는 시스템, 그리고 자사 데이터로 먼저 증명하는 것."** 1주차에는 그림이었고, 2주차에는 부품이었고, 3주차에 사용자(이지민)가 명시되면서 비로소 살아 움직였고, 그 위에 marketing-os 1차 작동을 자사 데이터로 증명하면서 외부에 들이댈 수 있는 형태가 됐다.

### 최종 구현 결과물
**SNS 게시물 초안** (인스타·링크드인 단글):

```
스폰지클럽 3주차 마무리.

처음엔 OS를 그림으로 그렸다.
가운데 "나", 둘레에 "부품 9개". 멋있어 보였다.
일주일 지나니까 그림은 책상 어딘가에 있고, 나는 똑같이 흐트러졌다.
```

**가장 큰 발견 — ⑤번 답을 두 번 다시 적은 것**

- 1차: "신규 SNS 계정 만들고 글 업로드"

- 두 번째가 훨씬 작고 즉시 실행 가능. 이미 있는 자원을 활용하는 게 0→1보다 1→2가 작다

### 공유할만한 인사이트
**1. OS 청사진은 진화한다** — 1주차 그림 → 2주차 부품 → 3주차 시간 위의 흐름 + 사용자 + 자사 데이터 증명

**2. 사용자가 명확해야 OS의 다음 한 걸음이 작아진다** — 추상 "사용자 = 본인"일 때는 행동이 거대해진다. 페르소나(이지민)가 구체화되니 "자사 적용"이라는 작은 첫 걸음이 보였다

**3. 자사 데이터로 먼저 증명하는 게 외부 설득의 0번 도구다** — marketing-os를 jinny 회사 데이터로 1차 작동시킨 순간, 이지민에게 들이댈 케이스 스터디의 0번이 생겼다. 외부 클라이언트 잡고 시작하면 신뢰 사이클이 길어진다. 자사 적용 → 검증 → 영업이 가장 작은 첫 걸음

**4. 하네스가 OS의 안전망** — 호칭 함정·옵션 라벨 함정 같은 반복 실수는 함정모음·메모리에 박혀야 다음에 안 일어남. OS는 자동화 자랑이 아니라 같은 실수를 안 반복하는 능력

**5. "승인 지점이 명시된 자동"이 진짜 OS** — 다 자동인 OS는 사고가 나면 멈춤. 어디서 사람한테 묻는지 정의된 OS는 사고가 나도 사람이 잡아낼 수 있음. marketing-os의 룰 임계값 튜닝이 그 자리

**6. PPT는 어디 있는지 까먹지만 하루의 리듬은 매일 작동한다** — 청사진을 그림으로 그릴 시간에 매일 작동하는 트리거 1개를 만드는 게 OS
