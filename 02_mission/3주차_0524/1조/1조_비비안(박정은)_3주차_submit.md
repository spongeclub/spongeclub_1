## 미션1: 내 고객은 누구고 왜 쓰는가 — 클로드 코드로 프로덕트 구현하기

### Summary

셀피쉬클럽의 고객은 AI를 실무에 적용하고 싶은 실무자/1인 사업자/소규모 팀 운영자다. 기존 Webflow 기반 운영의 한계(수동 운영, 데이터 분산, 반복 디자인 작업)를 해결하기 위해, Next.js 자체 플랫폼을 구축하고 Claude Code를 활용해 비개발자가 독립적으로 운영할 수 있는 구조를 만들었다. 8주간 인프라/인증/결제/어드민/콘텐츠/회원/SEO/디자인 전 영역을 구현 완료.

### 최종 구현 결과물

**고객 정의:**
- AI 툴을 "들어보긴 했는데" 실전에 어떻게 쓰는지 모르는 사람
- 혼자 일하거나 소규모 팀을 이끌면서, 콘텐츠/마케팅/비즈니스 운영에 AI를 장착하고 싶은 사람
- 커뮤니티 기반으로 동료와 함께 배우고 실행하는 것을 선호하는 사람

검증 근거: Supabase 멤버십 가입자, 82개 프로그램 운영, 186개 후기. 핵심 가치 패턴은 **"막막했는데 바로 써먹었다"**, **"혼자였으면 안 했을 걸 같이 해서 했다"**.

**왜 이 플랫폼이 필요한가:**
- 프로그램 등록/마감/가격 변경 같은 운영 작업이 수동이고 느렸다
- 회원 데이터가 분산되어 한 사람의 전체 활동 이력을 볼 수 없었다
- 새 프로그램을 만들 때마다 상세 페이지를 처음부터 디자인해야 했다

핵심 Why: **"AI로 일하는 방식을 바꾸는 커뮤니티가, 자기 자신의 운영도 AI로 바꾸는 것"**

**구현 완료 현황 (Week 03~10, 약 8주):**

| 영역 | 완료 항목 |
|------|-----------|
| 인프라 | Next.js 16 + Tailwind v4 + Vercel 배포 + Cloudflare R2 이미지 |
| 인증 | BetterAuth + 카카오/구글 소셜 로그인 + 3코호트 온보딩 플로우 |
| 결제 | 포트원 연동 + 재고 레이스 컨디션 방어 + KST 시각 저장 + 모바일 결제 |
| 어드민 | 프로그램 CRUD, 블로그/AI툴 관리, 배너 시스템, FAQ 풀, 마감 토글 |
| 콘텐츠 | 공유회/챌린지/워크숍 분리, 상세 페이지 제작 시스템(Claude+어드민), 리뷰 티커, 보도자료 자동 수집 |
| 회원 | 마이페이지(다중 매칭 합산), 멤버십 가입, DB 정합성 보정(70건) |
| SEO | 323개 URL 리다이렉트 매핑, OG 태그 |
| 디자인 | 3색 팔레트 통일, DESIGN.md v2.0, Editorial Tech 컨셉 |

**전략 3가지:**
1. **운영 자동화** — 어드민에서 프로그램 등록/마감/가격 수정/배너 관리/FAQ 관리를 모두 처리
2. **콘텐츠 생산 자동화** — Claude 채팅으로 상세 페이지 HTML을 생성하고, 어드민 WYSIWYG 편집기로 수정하는 파이프라인
3. **회원 데이터 통합** — 전화번호+이메일 다중 매칭으로 한 사람의 모든 활동을 하나로 보여주는 마이페이지

### 과정 (타임라인별 + 삽질)

1. **카카오 로그인 — 2시간짜리 미궁 (Week 04)**
   카카오 개발자 콘솔에서 Redirect URI 등록 메뉴를 못 찾아 2시간 헤맴. REST API 키를 클릭해서 들어간 키 설정 페이지 안에 숨어 있었음. 게다가 Vercel에 등록한 키와 Redirect URI를 넣은 키가 달라서 한 번 더 실패. **카카오는 키별로 Redirect URI가 따로 관리된다.**

2. **Webflow 이미지 핫링크 차단 (Week 04)**
   기존 Webflow 사이트 이미지 URL을 가져다 쓰니 403 Forbidden. CMS API로 가져온 URL은 CDN 경로가 달라 접근 가능하다는 걸 발견, CMS API → Supabase Storage 업로드 방식으로 우회.

3. **Vercel 서버리스의 fire-and-forget 함정 (Week 05)**
   n8n 웹훅을 fetch()로 호출할 때 await를 안 붙이니 로컬에서는 되는데 Vercel 배포 후 알림톡이 안 감. 서버리스 함수는 응답 반환 후 즉시 종료되기 때문. **서버리스에서는 fire-and-forget이 작동하지 않는다.**

4. **전화번호 포맷 불일치로 DB 정합성 붕괴 (Week 06)**
   입력값을 정규화 없이 DB에 저장, 기존 데이터(대시 없음)와 불일치 → 같은 사람이 다른 번호로 인식 → membership 중복 생성 21건. **DB에서 식별자로 쓰이는 값은 반드시 저장 전에 정규화해야 한다.**

5. **Supabase의 기본 1,000행 제한 (Week 06)**
   신청자가 1,000명을 넘자 누적 카운트가 멈춤. `.select().length`로 세고 있었는데 Supabase는 기본 최대 1,000행만 반환. `count: "exact"` 옵션으로 DB 레벨 카운트 사용하도록 변경.

6. **모바일 결제 복귀 처리 실패 (Week 07)**
   PortOne v2 모바일 결제 시 외부 앱으로 이동 후 돌아올 때 같은 페이지에서 useEffect로 paymentId 감지하는 방식이 불안정. 별도 성공 페이지(success-preview)로 redirect + 서버 검증은 백그라운드로 처리하여 해결.

7. **하드코딩 재고 제한이 전체 결제를 차단 (Week 07)**
   스폰지클럽 매진 처리용 `STOCK_LIMIT = 0`이 공용 결제 API에 하드코딩되어, 새 프로그램도 모두 결제 차단. **상품별 설정은 DB에서 관리해야 한다.**

8. **Tailwind preflight가 Claude 생성 HTML을 전부 깨뜨림 (Week 09)**
   Claude가 만든 인라인 스타일 HTML을 렌더링하니 Tailwind CSS 리셋이 h1/p/ul 기본 스타일을 0으로 만들어 레이아웃 붕괴. `.detail-html-content` 클래스로 preflight를 선택적으로 무효화하여 해결.

### 공유할만한 인사이트

1. **작업 순서는 계획이 아니라 블로커 해소 시점에 맞춰야 한다** — 의존성 있는 작업은 선행 작업 완료 후에 해야 재작업을 줄인다. 반면 콘텐츠 마이그레이션은 디자인과 동시에 작업해서 "껍데기만 예쁘고 데이터 없는" 상황을 피할 수 있었다.

2. **기존 시스템을 연동할 때는 추정으로 구현하면 안 된다** — 무료 공유회 데이터가 purchase가 아닌 event 테이블에 저장된다는 걸 n8n 워크플로우 분석으로 발견. 추정만으로 구현했으면 기존 데이터와 다른 곳에 쌓이는 심각한 문제 발생했을 것.

3. **비개발자가 운영할 수 있는 시스템을 만드는 게 핵심이다** — 이 프로젝트의 진짜 가치는 "사이트를 만든 것"이 아니라, 비개발자(정은)가 개발자 없이 프로그램 등록/마감/가격 변경/상세 페이지 제작/배너 관리를 할 수 있는 구조를 만든 것.

4. **GIF → MP4 변환 같은 작은 최적화가 체감 임팩트가 가장 크다** — 42MB GIF를 2MB MP4로 변환, 페이지 로드 속도 95% 개선. 기능 구현 대비 시간은 미미했지만 사용자 체감 개선은 최대.

5. **도메인 전환 전에 SEO 매핑을 먼저 해야 한다** — Webflow sitemap에서 323개 URL 추출 후 카테고리별 리다이렉트 설정. 나중에 하면 이미 SEO 점수를 잃은 뒤.

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

### Summary

하네스(도구·레시피·스킬 등 주방 전체 세팅)와 오케스트레이션(여러 에이전트가 병렬로 작업을 분담하는 구조)을 실제 프로젝트에 적용한 사례와 삽질, 그리고 앞으로 적용할 방향을 정리. 동일 LLM이라도 하네스 설계에 따라 효율이 최대 6배 차이난다는 점에서, 하네스의 진짜 가치는 "반복 가능한 품질"이다.

### 최종 구현 결과물

**이미 적용한 하네스 4가지:**

1. **CLAUDE.md + AGENTS.md + BRIEFING.md + DESIGN.md (프로젝트 컨텍스트 하네스)**
   Claude Code가 프로젝트를 이해하고 일관된 코드를 생성하게 하는 "레시피북". 기술 스택, 아키텍처 원칙("프론트엔드에서 Supabase 직접 호출 금지"), 디렉토리 구조, 코딩 컨벤션, 완료/미완료 현황까지 문서화. 이 하네스가 없으면 매 대화마다 프로젝트 설명부터 다시 해야 함.

2. **/worklog 스킬 (작업 기록 하네스)**
   작업 종료 시 docs/worklog.md + Obsidian vault + work log.md 세 곳에 동시 기록하는 커스텀 스킬. "왜/한 일" 포맷 강제, 주차 자동 계산(Week 01 시작일: 2026-03-16 기준) + 폴더 자동 생성. 미결정 사항 발생 시 decisions.md에도 자동 추가.

3. **상세 페이지 제작 시스템 (콘텐츠 생산 하네스)**
   Claude 채팅 프로젝트 파일 3종 — 카피라이팅 가이드(186개 후기 분석 → 참여자 실제 표현, 가치 패턴, Before→After 패턴 추출) + 디자인 가이드(유형별 HTML 샘플 10개, 유형별 섹션 조합 표) + 스킬(섹션별 대화형 인터뷰 → HTML 생성). 공유회 5문항, 워크숍 5문항, 챌린지 7문항으로 유형별 질문이 다름.

4. **/create-closing 스킬 (메타-하네스)**
   누구나 인터뷰를 통해 자기 환경에 맞는 하루 마무리 스킬을 만들 수 있게 한 스킬. 하네스를 만드는 하네스. 4단계 인터뷰(프로젝트 파악 → Obsidian 기록 → GitHub Commit&Push → 마무리 작업)로 개인화된 스킬 파일 생성.

**이미 적용한 오케스트레이션 4가지:**

1. **n8n 자동화 파이프라인** — 신청/결제 → Next.js API Route(DB 저장) → n8n 웹훅(await, 실패해도 결제 보존) → 솔라피 알림톡 + 슬랙 알림 동시 발송
2. **GitHub Actions 자동 동기화** — selfishclub-ax 레포 push 시 GitHub Actions가 자동으로 aaa 레포에 워크로그 동기화
3. **보도자료 자동 수집** — Google News RSS에서 "셀피쉬클럽" 키워드로 보도자료 자동 수집, 1시간 캐시
4. **/worklog 스킬** — 하나의 명령으로 3곳 동시 기록 + 주차 자동 계산 + 폴더 자동 생성

### 과정 (타임라인별 + 삽질)

**n8n 자동화 파이프라인 삽질:**
- Vercel 서버리스에서 await 없는 fetch가 중단되는 문제 (서버리스 함수는 응답 반환 후 즉시 종료)
- n8n 슬랙 credential이 다른 계정으로 설정 → 알림이 엉뚱한 채널로 감
- 솔라피 발신번호도 틀어져 있었음
- 알림톡 템플릿 변수 매핑 — `#{프로그램설명}`에 넣을 텍스트 미확정으로 아직 open 상태
- 핵심 설계 결정: n8n fetch에 await를 붙이되, 실패해도 결제는 보존하도록 try-catch로 감싸기. 알림 실패 때문에 결제까지 실패하면 안 됨.

**GitHub Actions 자동 동기화 삽질:**
- 다른 레포에 push하려면 별도 토큰(AAA_REPO_TOKEN)이 필요 → 레포 시크릿에 등록
- Obsidian vault 경로 변경(aaa vault → selfishclub ax vault) 시 /worklog 스킬의 경로와 주차별 폴더 구조 전면 수정 필요 (Week 08)

### 공유할만한 인사이트

1. **하네스의 진짜 가치는 "반복 가능한 품질"이다** — CLAUDE.md 없이도 코드를 시킬 수 있지만, 매번 "프론트엔드에서 Supabase 직접 호출하지 마", "API 응답은 { data, error } 패턴으로" 같은 규칙을 반복해야 한다. 하네스가 있으면 누가 언제 작업해도 동일한 품질 기준이 유지.

2. **오케스트레이션에서 가장 중요한 건 "실패 격리"다** — n8n 알림 연동의 핵심 설계 결정은 알림 발송 실패 시 결제가 롤백되지 않게 만든 것. 여러 에이전트가 병렬 작업할 때 한 곳의 실패가 전체를 무너뜨리지 않도록 격리하는 것이 핵심.

3. **하네스를 만드는 하네스(메타-하네스)가 확장성의 핵심이다** — /create-closing 스킬은 /worklog 스킬이 하드코딩되어 공유 불가능하다는 문제에서 출발. 인터뷰로 각자 환경에 맞는 스킬을 자동 생성하는 구조. 사람이 스킬·체인을 사전 정의하는 OMC 방식에 가깝되, 인간이 인터뷰로 방향을 잡아주는 하이브리드.

4. **기존 시스템의 오케스트레이션을 먼저 이해해야 새 오케스트레이션을 설계할 수 있다** — n8n 워크플로우를 분석하지 않고 "대충 purchase 테이블에 넣으면 되겠지" 했다면 기존 데이터와 다른 곳에 쌓이는 심각한 문제가 생겼을 것.

**앞으로 적용할 만한 것들:**
- 에이전틱 AI 하네스 — 블로그 태그 자동추천, 맞춤 프로그램 추천, CRM 개인화 메시지, 영상 요약 카드 자동 생성
- Spawn Task 스타일 오케스트레이션 — 대규모 업데이트 시 Claude Code가 여러 세션을 병렬 생성하여 브랜치별 작업 후 메인에 병합
- CRM 오케스트레이션 — 이탈 예측 + 재참여 메시지 생성 + 알림톡 발송 파이프라인 (n8n + Claude API + 솔라피)

## 미션3: 스폰지클럽을 하며 남기고 싶은 생각과 고민 SNS 글 작성

### Summary

8주간 프로젝트를 지속할 수 있었던 개인 동기와, 세션에서 다룬 "근접성"이 이 프로젝트에 어떻게 적용되는지를 정리. 운영자로서 직접 현장에 가까이 있기에 발견할 수 있었던 문제들과, 그것이 만든 차별점.

### 최종 구현 결과물

**나의 Why:**
"AI로 일하는 방식을 바꾸겠다고 말하는 커뮤니티가, 정작 자기 사이트는 수동으로 운영하는 모순을 해결하고 싶다." 셀피쉬클럽 운영자(비비안/정은)로서, 매번 Webflow에서 페이지를 수동으로 만들고, 회원 데이터를 엑셀로 관리하고, 마감 처리를 하드코딩하는 상황이 AI 커뮤니티답지 않았다. **"우리가 가르치는 것을 우리 자신이 먼저 실천하자"**가 5~10년 버틸 수 있는 Why.

**근접성의 3가지 혜택:**

1. **문제 검증 바이패스** — "AI 실무 적용을 배우고 싶은 사람들이 모이는 곳이 필요하다"는 이미 검증된 문제. 82개 프로그램, 186개 후기, 기존 멤버십 가입자가 증거. 시장에 이미 존재하는 문제에서 출발한 것.

2. **유저 행동 직접 파악** — 운영자이기 때문에 유저가 어떤 프로그램에 신청하고, 어디서 이탈하고, 어떤 후기를 남기는지 직접 볼 수 있음. 마이페이지 조회 로직 변경도 "다른 이메일로 신청한 내역이 안 보인다"는 실제 유저 불만에서 출발. UTM 추적도 코호트별 전환율 직접 확인 목적.

3. **가까이 있어야만 생기는 통찰** — membership에 있지만 member에 없는 데이터 70건 발견, 결제 취소해도 무료 신청이 완료되는 버그, 동시 결제 시 재고 초과 판매 가능성, 전화번호 포맷 불일치 21건 중복, 1,000명 넘자 카운트 멈추는 버그. 운영 현장에 가까이 있어야만 발견할 수 있는 문제들.

### 과정 (타임라인별 + 삽질)

근접성 탐색 섹터 5개(현재/이전 직장, 취미, 자주 활동하는 커뮤니티, 친구) 중, 이 프로젝트는 **"현재 직장/활동하는 커뮤니티"** 섹터에서 출발. 셀피쉬클럽이라는 커뮤니티를 직접 운영하면서 발생하는 문제를 직접 해결하는 구조이므로, 근접성이 최대치에 가깝다.

### 공유할만한 인사이트

근접성이 높을수록 "문제를 발명"하지 않아도 된다. 운영 현장에서 매일 부딪히는 문제를 해결하는 것 자체가 프로덕트가 되고, 그 과정에서 쌓이는 삽질과 해결 경험이 가장 강력한 차별점이 된다. 82개 프로그램과 186개 후기, 그리고 8주간의 삽질 기록이 그 증거다.
