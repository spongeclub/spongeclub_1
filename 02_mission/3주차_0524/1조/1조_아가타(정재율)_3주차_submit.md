### 최종 구현 결과물

매일 자동으로 굴러가는 흐름 1개:

```
아침 8시·점심 2시·저녁 10시 (KST)
   ↓ GitHub Actions 자동 발사
텔레그램 봇이 내 폰에 호흡 카드 보냄
   ↓ 내가 답
세션이 답을 받아 자동 분류·저장
   ↓
옵시디언 vault에 누적 (Daily/Inbox)
   ↓
매일 23:30 + PC 켤 때 자동
dashboard 갱신 (시각화 8 패널)
```

볼 수 있는 것:
- 매일 몸·마음 한눈에 
- 시점별 답변 패턴
- 자주 나온 키워드
- 깨달음 누적
- 자유 메시지 흐름
- 마음챙김 들숨날숨 호흡 위젯 (자기돌봄)
- 자기사랑 영역 (추후 컨텐츠)

### 과정 (타임라인별 + 삽질)

**1단계 — 왜 호흡 시스템인가 

1인 기업가는 외부 게이트(상사·동료·정기 회의)가 없어 매일 자기 점검이 사라지기 쉽다. 호흡의 하루 = 그 외부 게이트를 자가 구축하는 도구.

도구 선택은 "본질에 부합하는가" 1줄 평가로 했다. 멋있어 보이는 외부 스킬 여러 개를 검토했지만, "이게 정말 매일 작동하나"에서 대부분 탈락. 결국 텔레그램 봇 + 옵시디언 + 단순 자동화 조합으로 좁힘.

**2단계 — 자동 발송 첫 시도와 막힘

호흡의 하루의 본질 = "PC가 꺼져 있어도 매일 자동 발사". Anthropic 클라우드의 cron 기능을 등록했다. 하지만 폰에 메시지가 오지 않음. 등록만 하고 "내일 작동하겠지"로 넘긴 게 문제.

**해결**: 다음날 routines 페이지의 실행 로그를 직접 열어보니 "외부 API(telegram.org) 접근 차단" 메시지 발견. 같은 "클라우드"라도 외부 호출 정책이 다른 것을 그제야 인지.

**3단계 — GitHub Actions로 전환**

검증된 다른 클라우드(GitHub Actions)는 외부 호출이 자유롭고 무료. bash + curl 한 줄짜리 스크립트로 5분 만에 작동. 즉시 수동 1회 발사로 검증 → 폰 도착 ✓.

**해결 패턴**: 한 인프라가 막히면 **다른 단순한 인프라로 빨리 갈아탄다**. 막힌 인프라를 우회하려고 복잡하게 만들지 X.

**4단계 — 끝-끝 흐름 검증 (5/24 오후)**

발송만 작동해도 = 시스템이 작동하는 게 아님. 끝까지 = "cron 발사 → 폰 도착 → 답 → 세션 받기 → 옵시디언 저장 → 답장"이 모두 자동.

수동으로 1회 굴려서 모든 단계 확인. 중간에 한 곳이라도 막히면 사용자가 매일 안 쓰게 됨.

**5단계 — 시각화·자동 갱신 (5/24 저녁)**

답을 매일 저장만 하고 안 보면 = 데이터가 묻힌다. 시각화 dashboard 추가 + Windows Task Scheduler로 매일 23:30 자동 갱신. 옵시디언 옆에 띄워두면 매일 자연스럽게 보게 됨.



### 공유할만한 인사이트

1. **테스트베드 = 본인 1~3개월.** 가족·친구·고객 확장 전, 본인이 매일 살아본다. 본인이 매일 안 쓰는 도구는 누구도 안 쓴다. 확장은 검증된 가치만.

2. **"클라우드"라고 다 같은 게 아니다.** 자동화 도구를 클라우드에 올리면 자동으로 굴러갈 거라 추정한다. 하지만 어떤 클라우드는 외부 서비스(텔레그램·슬랙 등) 호출을 차단한다. 자동화의 핵심이 외부 API 호출이라면 = **그 클라우드가 외부 호출 허용하는지 먼저 5분 테스트**. 차단되면 다른 클라우드로 빨리 갈아탄다. 막힌 곳을 우회하려고 복잡하게 만들지 X.

**클라우드 = 어디 멀리 있는 서버 = 다 같은 거 아닙니까?** ← 보통 이렇게 생각함.
**실제로는**: 클라우드 서비스마다 **할 수 있는 것·못 하는 것이 다르다**. 특히 **외부 서비스에 전화 거는 능력**.

비유:
- 클라우드 = 사무실
- 외부 API = 다른 회사(텔레그램·슬랙·구글)에 전화하기
- A 사무실: 내부 업무만 가능. 외부 전화 차단됨
- B 사무실: 외부 어디든 자유롭게 전화 가능
- → 이름만 "사무실"이지 능력 완전 다름. **들어가 보기 전엔 모름**


**호흡 시스템에서 실제 일어난 일

| 시도  | 클라우드                                   | 결과                                                                |
| --- | -------------------------------------- | ----------------------------------------------------------------- |
| 1차  | **Anthropic 클라우드** (Claude Code의 cron) | 내부 작업은 잘 함. 그런데 텔레그램에 메시지 보내려 하니 = **외부 호출 차단 (보안 정책)**. 폰에 메시지 X |
| 2차  | **GitHub Actions**                     | 외부 어디든 호출 OK. 5분 만에 텔레그램 발사 작동 ✓                                  |
같은 "클라우드"라는 이름이지만 능력 = 정반대. **사용 문서·spec 봐도 안 적혀 있음**. 한 번 발사해서 막혀봐야 안다.


**다른 사람에게 공유하는 가치

본인이 자동화 만들 때 자주 하는 실수:
- "이 도구 좋아 보이네 → cron 등록 → 다음날 결과 확인하자"
- 다음날 = 안 됨. 디버깅 = 1~6시간 (어디서 막혔는지 모름)

이걸 안 겪으려면:
1. 그 도구가 **외부 API 호출 가능한지 미리 검색·문서 확인**
2. 모호하면 = **5분짜리 테스트 발사 (외부 API 한 번 호출해보기)**
3. 막히면 = **다른 클라우드로 갈아탐** (해결하려고 시간 X)

## 미션2: 내가 정의하고 적용해보고 싶은 하네스 + 오케스트레이션

### Summary

**하네스**: AI 모델이 일하는 작업실 (도구·권한·룰·기억). 같은 요리사라도 주방이 다르면 다른 음식이 나오듯, 같은 Claude라도 하네스가 다르면 다른 결과.

**오케스트레이션**: 여러 작업실의 협업 흐름. 음식점 = 주방·홀·카운터·사장이 각자 일하지만 함께 굴러가야 음식점이 됨.

**호흡의 하루 = 하네스 3개 + 부품 8개의 오케스트레이션.**

### 최종 구현 결과물

#### 하네스 3개

| #   | 이름                        | 작업실 안                              | 역할                 |
| --- | ------------------------- | ---------------------------------- | ------------------ |
| 1   | **GitHub Actions runner** | bash·curl·jq                       | 매일 정해진 시간 호흡 카드 발사 |
| 2   | **PARTNER 세션**            | Claude + 텔레그램 채널 + 옵시디언 권한 + 분류 룰  | 답 받기·분류·저장·답장      |
| 3   | **structure_test 세션**     | Claude + 워크로그·skill·dashboard 스크립트 | 사용자와 작업·정정·확장      |

#### 오케스트레이션 흐름

```

GitHub Actions cron 
   ↓
Telegram Bot API
   ↓
사용자 폰 (push 알림)


[자동 — PC + 세션 켜져 있을 때]
사용자 답 → PARTNER Phase 2 분류
   ↓

   ↓
사용자 폰에 "✓ 저장" 답장


[자동 — Windows Task Scheduler 매일 23:30 + PC 로그온]
python build_dashboard.py
   ├─ OS_WIKI/Daily/*.md 파싱 
   └─ Supabase fetch (daily-breaths 마음 — 본인 다른 사이트)
   ↓
dashboard_live.html 갱신
```

= **8 부품 자동 흐름.** 사용자 손이 가야 하는 것 = 폰에서 답 + 가끔 dashboard 열기.


### 과정 (타임라인별 + 삽질)

**1단계 — 하나의 도구로 다 하려다 막힘**

처음엔 "Claude Code 안에서 모든 게 가능할 것"으로 기대. 자동 발송도 Claude 안의 cron으로 시도. 그러나 외부 API 호출이 막혀 작동 X.

**해결**: 한 작업실(하네스) 안에서 다 해결 X. 발송은 발송 전문 작업실(GitHub Actions runner — bash + curl)이 더 잘 한다.

**교훈**: 1인 기업가가 1 도구만 마스터하려는 함정. 각 작업에 가장 단순한 작업실이 따로 있다.

**2단계 — 분류·저장은 또 다른 작업실이 필요**

GitHub Actions는 발송만 한다. 사용자 폰에서 답이 돌아오면 누가 받을지? 받은 답을 어디에 어떻게 저장할지? = 또 다른 하네스 필요.

**해결**: Claude Code 세션 1개를 "분류·저장 전용"으로 띄움. 텔레그램 채널 연결 + 옵시디언 vault 권한 + 분류 룰. 메시지가 도착하면 → 키워드 보고 → 호흡 답인지 자유 메시지인지 분류 → 해당 폴더 저장 → 답장.

**교훈**: **같은 Claude라도 어떤 하네스(권한·룰·기억)에 박는가**에 따라 다른 일을 한다. 발송 하네스·분류 하네스·작업 하네스 = 세 개의 하네스. 각자 단순.

**3단계 — 시각화는 분리된 부품으로**

저장만 하면 데이터가 묻힌다. 시각화 dashboard 필요. 하지만 분류·저장 하네스 안에 시각화까지 박으면 = 그 하네스가 복잡해지고 깨지기 쉬움.

**해결**: 시각화 = 완전 별도 부품 (Python 스크립트). 옵시디언 vault만 읽음. Windows Task Scheduler가 매일 23:30 + PC 켤 때 자동 실행.

**교훈**: **부품을 분리하면 각자 단순해진다**. 한 부품이 깨져도 다른 부품은 살아 있음.

**4단계 — 부품을 흐름으로 연결**

발송·분류·저장·시각화 4 부품이 각자 있어도 = 시스템이 아님. 흐름으로 연결돼야 = 사용자 입장에서 "매일 자동 굴러감"으로 느껴진다.

**연결 방식**: cron 시간 → 텔레그램 → 폰 → 답 → 채널 → 분류 → 저장 → (별도 트리거) → 시각화. 각 부품은 자기 일만 알고, 흐름은 사용자 1명에게 한 시스템으로 보임.


### 공유할만한 인사이트

1. **하네스(작업실)는 도구가 아니라 환경이다.** 같은 모델·같은 도구라도 권한·룰·기억이 다르면 완전히 다른 일을 한다. 1인 기업가가 만드는 "내 도구"의 본질은 = 어떤 환경(하네스)에 박는가.

2. **부품 분리가 시스템 안정의 핵심.** 한 부품에 여러 책임 넣으면 = 깨지기 쉽고 디버깅 어려움. 발송·분류·저장·시각화는 각자 단순하게 분리. 한 부품 깨져도 나머지는 살아 있게.

3. **단순한 부품이 가장 안 깨진다.** 자동화 첫 부품은 bash + curl 한 줄로 시작. LLM·복잡한 로직은 단순 부품 작동 검증 후 추가. 처음부터 복잡하면 = 어디 막혔는지 모름.

4. **흐름을 사용자 입장에서 그려라.** "내가 폰에서 답하면 → 어디로 가서 → 어떻게 저장되고 → 어디서 다시 보는가" 한 그림으로 그려본다. 그 그림에서 한 곳이라도 빈칸이면 = 시스템 미완성.

5. **본인 사용 → 막힘 발견 → 그 시점에 도구 추가.** 미리 도구 다 만들고 사업 시작 = "할 일은 많은데 결과는 안 나옴" 함정. 1인 기업가의 가장 흔한 함정 (Matt Gray "implementation problem").
