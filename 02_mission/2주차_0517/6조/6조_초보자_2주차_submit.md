## 미션1: Second Brain → 회사 AI 에이전트 시스템 설계 & Phase 1 구축

### Summary

1주차에서 내린 OS 선언 — **"나는 의사결정만 하고, 나머지는 시스템이 한다"** — 를 회사 업무에 직접 적용했다.

개인 Second Brain(Obsidian)에 쌓아온 지식 구조를 토대로, **Claude Code + MCP 기반 멀티 에이전트 AI 시스템**을 설계하고 Phase 1 인프라를 구축했다. 단순한 기획이 아니라 실제 `/agents/` 폴더 구조, 시스템 프롬프트, 체크리스트, 스코어링 모델, 리포트 템플릿까지 실제로 만들었다.

**OS 정의 — 나의 버전:**
> "OS는 나의 Second Brain을 연료로 삼아 회사의 반복 업무를 자율 처리하는 시스템이다. 사람은 최종 승인만 한다."

### 최종 구현 결과물

**기획 문서:**
- `AI_에이전트_시스템_기획_로드맵.md` (v1.9) — LLM OS 기반 멀티 에이전트 아키텍처 전체 설계

**Phase 1 인프라 (완료 항목):**
- `/agents/` 전체 폴더 구조 생성
- 에이전트 시스템 프롬프트 6개 — Overall Agent + A(계약서) / B1(실적) / B2(예측) / C(M&A) / D(과제)
- 계약서 체크리스트 — NDA / 용역계약 / MOU 등 유형별
- 스코어링 모델 — `fit_scoring.json` (M&A·과제 핏 평가), `dcf_model.json` (DCF 파라미터 v1.0)
- 리포트 템플릿 4종 — 리스크 리포트 / 경영보고서 / M&A 리포트 / 과제 지원서
- `contracts.csv`, `revenue.json` 데이터 구조 초기화
- Audit Trail 설계 — `/agents/logs/audit_log.md` 누적 로그 구조 정의

**에이전트 아키텍처 요약:**
```
사람 (최종 승인)
    ↑
Overall Agent (Opus — 오케스트레이터)
    ↑
A 계약서 / B1 실적 / B2 예측 / C M&A / D 과제 (Sonnet)
    ↑
도구 & 메모리 인프라 (Gmail MCP / OneDrive / 웹검색 / 로컬 파일)
```

### 과정 (타임라인별 + 삽질)

**1. 첫 시도 — 에이전트들이 한 덩어리**

처음엔 "회사 업무를 AI로 자동화하자"는 방향만 잡고 기획을 시작했다. 그런데 막상 설계하다 보니 에이전트들이 기준 없이 한 군데 뭉쳐있었다. 계약서 분석도, 경영 실적도, M&A도 다 하나의 에이전트가 하는 구조. '이게 실제로 작동할까?' 싶은 불안감이 생겼다.

**2. 분리 작업 — 에이전트를 쪼갠다**

기능별로 에이전트를 분리하는 작업을 했다. A(계약서) / B1(실적) / B2(예측) / C(M&A) / D(과제)로 쪼개고, Overall Agent가 오케스트레이션하는 구조로 바꿨다. 그제서야 각 에이전트가 뭘 해야 하는지 명확해졌다.

**3. 근본적인 문제 발견 — 지식 기반이 없다**

에이전트를 분리하고 나니 더 큰 문제가 보였다. 에이전트가 판단을 내리려면 기준이 필요한데, 그 기준이 없었다. 계약서를 분석하려면 체크리스트가 있어야 하고, M&A 핏을 평가하려면 자사 역량 정보가 있어야 한다. 순수하게 LLM만 믿으면 매번 답이 달라진다.

**4. Second Brain 개념 접목 — 지식 기반을 시스템에 넣는다**

1주차에 카파시의 LLM Wiki 개념을 공부했던 게 여기서 연결됐다. Obsidian에 쌓아온 지식 구조를 에이전트의 메모리로 변환하는 방식으로 발전시켰다. `company_profile.md`, 계약서 체크리스트, `dcf_model.json`, `fit_scoring.json` — 이 파일들이 에이전트의 "두뇌"가 됐다. 지식 기반이 생기자 설계가 훨씬 단단해졌다.

### 공유할만한 인사이트

**1. Second Brain이 AI 에이전트의 연료다**
개인 Obsidian에 지식을 정리해두지 않았다면 이 설계 자체가 불가능했다. `company_profile.md`(자사 역량·인증·실적), 체크리스트, 스코어링 기준 — 이 모든 게 Second Brain에서 나왔다. 카파시의 LLM Wiki 개념이 이 구조에서 정확히 살아있다.

**2. OS의 핵심은 "사람이 판단할 것"과 "시스템이 할 것"의 경계를 긋는 것**
에이전트가 자율 수행하는 범위와 사람 승인이 필요한 범위를 명확히 분리했다. 이메일 발송, M&A 의사결정, 과제 제출 — 이것들은 절대 에이전트가 단독 실행 못한다. 이 경계가 없으면 OS가 아니라 그냥 챗봇이다.

**3. Advisor 패턴 — Sonnet이 초안, Opus가 검토**
고위험 산출물(M&A 리포트, 경영 보고서)은 Sonnet 서브에이전트가 초안을 쓰고, Opus가 Advisor로 재호출해 검토한 뒤 사람에게 넘긴다. 단일 Opus보다 멀티 에이전트가 90.2% 높은 성능을 낸다는 Anthropic 연구 결과를 실제 설계에 적용했다.
