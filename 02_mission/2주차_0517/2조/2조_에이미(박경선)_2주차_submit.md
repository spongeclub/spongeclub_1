## 미션1: 각자만의 정의로 [운영체제]라고 정의내리는 OS 구현


> [!info] 내가 정의한 「운영체제」
> 반복되는 일을 한 화면 안에서 끝낼 수 있게 도구 간 이동을 없애고, 디자인·톤·구조를 코드로 강제해서 결과물의 일관성을 사람의 의지에 맡기지 않는 통합 작업 환경.

## Summary

이 정의를 **인스타그램 캐러셀 콘텐츠 제작** 도메인에 맞춰 **「집다움 OS」** 라는 이름의 웹앱으로 구현했다.

- **Before**: 캐러셀 1건 만들기까지 Notion·Claude·Figma·Photoshop·이미지생성 AI (레퍼런스사이트).    인스타.  6개 이상의   도구를 오감
- **After**: OS 안에서 주제 선택 → AI 카피 → 슬라이드 편집 → PNG 다운까지 한 화면

배포 URL: https://jipdaum-os.vercel.app

#OS구현 #2주차 #집다움 #캐러셀자동화

## 최종 구현 결과물

### 구현된 화면 (6개)

| 화면 | 기능 |
|---|---|
| 로그인 | 팀 공용 비밀번호 1개 (iron-session + bcrypt) |
| 대시보드 | 발행 예정·최근 발행 콘텐츠 한눈에 |
| 📋 발행 계획 | 50개 주제 풀 + 25주 발행 스케줄 |
| ＋ 새 콘텐츠 (2탭) | ① 아이데이션 (주제·제목 AI 생성) → ② 에디터 (슬라이드 9장 편집 · PNG export · 캡션 · 해시태그) |
| 라이브러리 | 발행 완료 콘텐츠 보관 |
| 사진 아카이브 | 업로드·태그·검색 |

### 기술 스택

- **프론트엔드**: Next.js 14 (App Router) + React + TypeScript
- **인증·DB·파일**: Supabase
- **텍스트 AI**: Anthropic Claude (`claude-sonnet-4-6`) — JSON 강제 출력
- **이미지 AI**: Google Gemini 2.5 Flash Image (Nano Banana)
- **호스팅**: Vercel (GitHub 연동 자동 배포)
- **디자인 시스템**: CSS 변수로 토큰 주입 → **자유 px 입력 금지** 가 일관성의 핵심
> [!info] 잠깐, 이게 다 뭐예요? (비전공자용 풀이)
> 
> | 항목 | 한 줄로 | 식당 비유 |
> | --- | --- | --- |
> | Next.js + React + TypeScript | 사용자가 보는 화면을 만드는 풀세트 | 홀·메뉴판 |
> | Supabase | 데이터·사진·로그인을 한 곳에서 관리 | 창고+금고+출입증 |
> | Claude | 캐러셀 카피를 써주는 AI | 작가 |
> | Gemini (Nano Banana) | 인테리어 이미지를 만들어주는 AI | 사진작가 |
> | Vercel | 만든 앱을 인터넷에 띄우는 서버 | 건물 |
> | CSS 변수 | 디자인 일관성을 강제하는 룰 | 인테리어 매뉴얼 |
### 데이터 시드

- 4개 팔레트: `Warm Terracotta` / `Calm Sage` / `Urban Charcoal` / `Vintage Mustard`
- 50개 콘텐츠 주제 (A~E 카테고리)
- 25주 발행 스케줄 (주 2회 — 화요일 저장형 / 금요일 영감형)
- Supabase 테이블 2개 (`contents`, `photos`) + Storage 버킷 1개 (`photos`)

## 과정 (타임라인별 + 삽질)

### Phase 1 — 정의·기획

> [!note] 시스템 정의 문서부터 작성
> 코드 한 줄 짜기 전에 「디자인 시스템 v1.0」(색·폰트·spacing 토큰)과 「콘텐츠 시스템 v1.0」(브랜드·필러 5개·Hook 패턴·시스템 프롬프트) 2개의 MD를 먼저 썼다. 이게 OS의 헌법 역할.
> !! 다니의 강의안 따라하기

**확정한 의사결정**

- 팀 2~3명 운영
- PNG export까지만 자동화 (인스타 업로드는 수동 — 메타 정책 위반 회피)
- AI 호출은 OS 안에서 바로
- 사진 보관도 OS 내장
- 콘텐츠 기획 자동화 추가

### Phase 2 — 기술 스택 결정

### Phase 3 — 핵심 구현

- 슬라이드 9장 컴포넌트 (`cover` / `content` / `text` / `closing`) — 모든 px·색이 토큰만 참조
- Claude API 연동 → 시스템 프롬프트(MD 압축본)로 **JSON 카피 강제 출력**
- 2탭 UI 설계: **아이데이션 → 에디터** 단계 분리
- `html2canvas + JSZip` 으로 슬라이드 9장을 PNG zip 으로 일괄 다운

### Phase 4 — 콘텐츠 마스터플랜

- 50개 주제를 5개 카테고리(A~E)로 분류
- 25주 스케줄(주 2회 × 화·금) 작성
- 「한 줄 훅 = 직접 해본 경험」 원칙을 코드 레벨에 박음 → 일반 정보가 아닌 본인 경험이 차별화 축
- 대시보드에 있던 주제 풀을 별도 `/plan` 탭으로 분리

### Phase 5 — 배포

GitHub 저장소 생성 → Vercel 연동 → 환경변수 8개 등록 → 자동 배포.

### Phase 6 — 트러블슈팅 (마지막 날, 4시간 + 진행 중)

> [!warning] 만들기는 끝났는데, 막상 인터넷에 올리니 줄줄이 오류가 터졌다
> 코드 자체는 잘 작동했는데, **외부 서비스(AI·DB·호스팅)와 연결하는 부분**에서 문제가 계속 발견됨. 4시간 매달렸지만 일부는 아직 해결 중.

## 공유할만한 인사이트


> [!success] 1. 도구 선택이 비전공자의 가장 큰 진입장벽이다
> 비전공자가 웹앱 만들 때 가장 헤매는 건 코딩이 아니라 **"어떤 도구를 써야 하지?"** 의 단계. 이번 프로젝트에서 도구를 두 번 바꾸면서 알게 된 차이를 공유.
> 
> **🔧 개발 환경: Lovable vs Claude Code**
> 
> | | Lovable | Claude Code |
> | --- | --- | --- |
> | **비유** | 밀키트 | 재료부터 요리 |
> | **사용** | 채팅으로 "이런 앱" → 미리보기 | 터미널에서 AI와 코드 직접 다룸 |
> | **장점** | 진입 장벽 낮음, 빠른 첫 결과 | 복잡한 로직·디자인 시스템·외부 API 자유 |
> | **한계** | 서버사이드 AI 호출·복잡 로직 어려움 | 기본 개념 약간은 필요 |
> 
> **우리의 선택: Claude Code**
> - 디자인 토큰을 코드로 강제해야 했음
> - 서버사이드에서 Claude·Gemini API 호출 필요
> - "빠르게 만들기"보다 "오래 운영할 OS"가 목표
> 
> **🏠 호스팅: Netlify vs Vercel**
> 
> | | Netlify | Vercel |
> | --- | --- | --- |
> | **비유** | 범용 부동산 | Next.js 전용 부동산 |
> | **누가** | 독립 회사 | Next.js 본가 |
> | **장점** | 정적 사이트 호스팅 강함 | Next.js 호환성 100% |
> 
> **우리의 선택: Vercel**
> - Next.js로 만들었기 때문에 본가인 Vercel이 사실상 표준
> - 환경변수·자동 배포·로그 관리가 직관적
> - 무료 플랜으로 충분, 서울 리전 제공
> 
> → 비전공자에게 진짜 필요한 건 **"도구 지도"**. 이 비교 표 하나만 가져가도 첫 한 달 시행착오가 사라진다.

> [!success] 2. 한 글자 오타로 4시간
> 환경변수 이름 `SUPABASE`가 `UPABASE`로 입력됨. S 누락. 원인 발견까지 1시간 이상 소요.
> 
> 사람 눈은 식별하지 못하나 컴퓨터에겐 완전히 다른 문자열. 한글 입력 상태에서 영문 타이핑 시 비가시 문자도 섞일 수 있음.
> 
> → 키·비밀번호는 복사·붙여넣기 원칙. 입력 후 즉시 검증.

> [!success] 3. AI 추천도 의심해야 한다
> 의아했던 두 사례.
> 
> - **호스팅**: 첫 추천은 Lovable. 검토 결과 Vercel이 표준이며 더 적합 → 전환.
> - **이미지 AI**: 첫 추천은 OpenAI DALL·E 3. 검토 결과 Google Gemini(Nano Banana)가 품질·비용 모두 우위 → 전환.
> 
> AI는 학습 시점 정보로 추천한다. 최신·최적 옵션은 알지 못할 수 있음.
> 
> → "왜?"로 한 번 질문하고, 외부에서 검증한 뒤 결정하는 습관 필요.

> [!success] 4. 화면 캡쳐로만 소통한 비효율
> 모든 단계에서 화면을 캡쳐해 AI에 전달. 사소한 작업도 예외 없음.
> 
> 원인: 화면을 텍스트로 설명할 능력 부족.
> 해결: 자주 쓰는 화면(Supabase·Vercel 등) 구조의 사전 학습.
> 
> → AI 협업의 소통 비용은 도메인 이해도에 반비례한다.
