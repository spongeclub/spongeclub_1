## 미션1: <흐민의 Sullivan 따라 만들기 — 나만의 AI 사고 파트너 1차 구축기>

### Summary : 이번 미션에서는 흐민 님의 SelfForge 구조 중 1층에 해당하는 Sullivan을 참고해, 나만의 AI 사고 파트너를 직접 구축해보는 실습을 진행했다.

처음에는 텔레그램 봇을 만들면 Claude와 바로 대화할 수 있을 것이라고 생각했다. 하지만 실제로 진행해보니 텔레그램 봇은 Claude 자체가 아니라, 메시지를 받을 수 있는 입력 창구에 가깝다는 것을 알게 되었다.

즉, 텔레그램 봇을 만드는 것과 그 메시지를 Claude Code 세션으로 전달하는 것은 완전히 다른 단계였다. 이번 과정에서 가장 크게 배운 점은 “봇 만들기와 Claude 연결하기는 다르다”는 것이었다.

Sullivan은 단순히 메모를 저장하는 도구가 아니라, 내가 던진 생각을 받아주고, 질문을 되돌려주고, 일상을 기록 가능한 구조로 바꾸는 AI 사고 파트너에 가깝다는 것도 이해하게 되었다.

### 과정 (타임라인별 + 삽질):### 1. 흐민 님의 Sullivan 구조를 이해했다  
  
처음에는 흐민 님의 세션을 듣고 Sullivan이라는 개념을 접했다.  
  
SelfForge는 **“나를 벼리는 대장간”**이라는 의미를 가진 개인 OS 구조였고, 그중 Sullivan은 사고를 받아주고 확장해주는 AI 사고 파트너에 가까웠다.  
  
Sullivan의 핵심은 텔레그램에 형식 없이 던진 메모, 아이디어, 질문, 링크, 감정 등을 자동으로 분류하고, Obsidian이나 로컬 노트에 날짜별로 저장하며, 아침 브리핑과 저녁 회고까지 이어지게 만드는 것이었다.  
  
처음에는 이 구조가 단순히 “텔레그램으로 Claude와 대화하는 것”이라고 생각했지만, 실제로는 텔레그램, Claude Code, 행동 정의 파일, 자동 실행 환경이 함께 연결되어야 하는 구조라는 것을 알게 되었다.  
  
---  
  
### 2. 텔레그램 봇을 만들었지만 Claude로 메시지가 들어오지 않았다  
  
세션을 듣고 나서 BotFather를 통해 텔레그램 봇을 만들고 토큰을 연결했다.  
  
처음에는 텔레그램 봇을 만들면 Claude와 바로 대화할 수 있을 것이라고 생각했다. 하지만 실제로는 Claude가 텔레그램으로 메시지를 보내는 것은 가능했지만, 내가 텔레그램에 보낸 메시지가 Claude Code 세션으로 들어오지는 않았다.  
  
이때 가장 헷갈렸던 부분은 **“텔레그램 봇이 있으면 대화가 되는 것 아닌가?”**라는 생각이었다.  
  
나중에 정리해보니 텔레그램 봇은 Claude가 아니라, 메시지를 받을 수 있는 **우체통** 같은 존재였다.  
  
내가 메시지를 보내도 그 메시지를 Claude에게 전달해주는 중간 연결 장치가 없으면 Claude는 그 내용을 알 수 없었다.  
  
즉, 봇을 만드는 것과 Claude Code로 메시지를 전달하는 것은 완전히 다른 단계였다.  
  
---  
  
### 3. Python 에이전트 방식도 시도했다  
  
처음에는 Python으로 Telegram 메시지를 받아 분류하고 저장하는 방식도 시도했다.  
  
Python 에이전트를 만들었고, 테스트 메시지를 보냈을 때 일상으로 분류되어 저장되는 것까지는 성공했다.  
  
하지만 이후 **409 Conflict 에러**가 발생했다.  
  
원인은 Claude Code의 텔레그램 연결 방식과 Python 에이전트가 같은 봇을 동시에 사용하려고 했기 때문이었다.  
  
쉽게 말하면, 하나의 우체통을 두 명의 배달원이 동시에 열려고 하면서 충돌이 난 것이다.  
  
이 과정을 통해 Python 에이전트 방식과 Claude Code 방식은 동시에 쓰면 안 되고, 어떤 방식으로 갈지 먼저 정해야 한다는 것을 알게 되었다.  
  
---  
  
### 4. Claude Code 중심의 흐민 방식으로 방향을 정했다  
  
Python 방식은 가볍고 단순했지만, 내가 만들고 싶은 Sullivan과는 조금 달랐다.  
  
Python 방식은 메시지를 받아 저장하는 데는 적합했지만, 내가 원한 것은 단순한 저장 봇이 아니었다.  
  
내가 만들고 싶었던 것은 내 생각을 받아주고, 질문을 되돌려주고, 일상과 학습을 연결해주는 AI 사고 파트너였다.  
  
그래서 최종적으로는 Claude Code가 중심이 되는 흐민 방식으로 방향을 정했다.  
  
이 방향을 선택하면서 Sullivan은 단순한 자동 분류기가 아니라, 내 사고를 확장해주는 대화형 시스템에 가깝다는 점을 더 분명히 이해하게 되었다.  
  
---  
  
### 5. Sullivan 행동 정의 파일을 작성했다  
  
이후 Sullivan이 어떻게 반응해야 하는지를 정의하기 위해 행동 정의 파일을 만들었다.  
  
핵심 규칙은 다음과 같았다.  
  
- 생각을 그대로 받는다.  
- 사용자의 말을 함부로 정리하거나 판단하지 않는다.  
- 질문은 너무 많이 던지지 않는다.  
- “왜?”보다는 “어떤?”, “그래서?”, “그게 왜 중요해?”처럼 사고를 확장하는 질문을 사용한다.  
- 기록은 일상 / 공부 / AI학습으로 나누어 저장한다.  
  
이 과정을 통해 AI에게 원하는 행동을 시키려면 단순히 “잘해줘”라고 말하는 것이 아니라, 어떤 방식으로 반응해야 하는지 규칙을 문서로 명확히 정의해야 한다는 것을 알게 되었다.  
  
행동 정의 파일은 Sullivan의 성격과 역할을 정하는 기준 문서에 가까웠다.  
  
---  
  
### 6. 실행 환경을 구성했다  
  
그다음 Sullivan 프로젝트 폴더와 노트 저장 폴더를 만들었다.  
  
기록이 저장될 수 있도록 로컬 폴더 구조를 만들고, 일상 / 공부 / AI학습으로 나누어 기록할 수 있는 기본 구조를 준비했다.  
  
또한 Windows 시작프로그램에 Sullivan 실행 파일을 등록하고, 아침 브리핑, 점심 체크인, 저녁 회고를 위한 자동 실행 일정도 등록했다.  
  
현재 터미널에서는 Sullivan 세션이 시작되었고, 아침 8시 3분, 점심 12시 7분, 밤 10시 5분에 실행되는 일정까지 확인된 상태다.  
  
---  
  
### 7. 현재 남은 문제를 확인했다  
  
현재까지 Sullivan 프로젝트의 기본 구조와 실행 환경은 만들어진 상태다.  
  
터미널 연결은 성공했고, Sullivan 세션도 정상적으로 시작되었다. 아침 브리핑, 점심 체크인, 저녁 회고 일정도 등록된 상태다.  
  
하지만 아직 텔레그램에서 보낸 메시지가 Sullivan 쪽으로 안정적으로 들어오는 수신 연결은 완성되지 않았다.  
  
그래서 다음 단계는 새로운 기능을 더 만드는 것이 아니라, 지금 만든 구조가 실제로 작동하는지 하나씩 확인하는 것이다.  
  
우선 텔레그램에서 메모 하나를 보내고, 그 메시지가 Sullivan으로 들어오는지 확인한 뒤, 일상 / 공부 / AI학습 중 하나로 저장되는 흐름을 테스트해야 한다.

### 공유할만한 인사이트### 1. 텔레그램은 내가 생각한 카카오톡 같은 대화 서비스가 아니었다  
  
이번 미션에서 가장 크게 배운 것은 텔레그램이 내가 막연히 생각하던 카카오톡 같은 대화 서비스와는 성격이 다르다는 점이었다.  
  
처음에는 텔레그램 봇을 만들면 Claude와 바로 대화할 수 있을 것이라고 생각했다.  
  
하지만 실제로는 텔레그램 봇은 대화 상대라기보다 입력 창구에 가까웠다.  
  
내가 텔레그램에 메시지를 보내면 그 메시지는 봇에게 도착하지만, Claude가 그것을 읽으려면 중간 연결 장치가 필요했다.  
  
이걸 이해하고 나니 **“왜 봇은 만들었는데 Claude가 내 말을 못 듣는지”**가 비로소 이해되었다.  
  
---  
  
### 2. 봇 만들기와 시스템 연결은 완전히 다른 일이다  
  
두 번째 인사이트는 봇 만들기와 시스템 연결은 완전히 다른 일이라는 점이다.  
  
봇 만들기는 우체통을 만드는 일이고, Claude 연결은 그 우체통을 열어 메시지를 Claude에게 전달하는 배달원을 세팅하는 일에 가까웠다.  
  
처음에는 봇을 만들고 토큰을 연결하면 끝이라고 생각했지만, 실제로는 그 이후에 메시지를 받아오고, Claude Code 세션으로 전달하고, 다시 응답을 보내주는 흐름이 필요했다.  
  
앞으로 자동화 시스템을 만들 때는 **“화면상으로 연결된 것처럼 보이는가?”**보다 **“데이터가 실제로 어디에서 어디로 이동하는가?”**를 먼저 확인해야겠다고 느꼈다.

## 공유할만한 인사이트 : 기획과 스토리보드 이미지 영상까지 함께 만들 수 있었던 것이 첫 번째이다.

레퍼런ㅅ 이미지로 구성하는 전체 페이지를 만들고 그곳에 필요한 이미지를 한꺼번에 만들 수 있다는 것이 너무 좋았고, 파일 형식인 투명한 배경의 PNG와 크로마키 스크린 등 원하는 파일 형식이 함께 만들어지는 것이 너무 신기하고 좋았다. 

스토리보드 / 영상에 필요한 요소와 타임별 요소 전체를 만들 수 있는 영상 작업 기획지시서가 만들어졌다. 

영상을 만들 때 요소 등을 알고는 있었지만, 영상을 만들다 보면 순서가 없고 뒤죽박죽인 경향이 많아서 만들다가도 포기하기 일쑤였는데, 이렇게 만드는 과정마다 문서화되어서 정리되고 그것을 바탕으로 이후 작업을 이어나가니까 오늘은 이렇게 했지만 다음에는 좀 더 내가 원하는 영상물을 만들 때 어떤 것을 채워야 하고 어떤 요소를 먼저 해야 할지 정리가 되었다. 

영상 제작까지 이곳에서 모두 한다는 것은 사실상 아직은 나에게 무리가 있다는 생각이 들었다. 이전에 기획을 하고 이미지 생성 등 따로 진행하던 것들을 한 화면에서 진행하며 레퍼런스 이미지와 내가 하려는 방향을 한번에 확인하고 그 결과를 가지고 이미지를 만드는 게 너무 인상적이었고,
이미지나 영상을 글자로 보고 상상하는 것이 아닌 결과물을 보고 그것을 바탕으로 수정해 나갈 수 있었다는 것이 가장 좋았던 것 같습니다.
