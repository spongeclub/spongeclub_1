## 미션1: 각자만의 정의로 [운영체제]라고 정의내리는 OS 구현


### Summary

"공간 큐레이션 콘텐츠 제작자를 위한 나만의 OS"를 설계하고 구현했다.

내가 정의한 OS는 컴퓨터 운영체제가 아니라, 하나의 콘텐츠가 태어나서 발행되기까지의 전 과정을 관통하는 작업 시스템이다.

흩어진 정보 수집 → 검증 → 구조화 → 시각화 → 발행을 끊김 없이 연결하는, 1인 콘텐츠 제작자의 일상 운영체제.

핵심 철학: "한 곳만 수정하면 모든 곳이 따라온다"

### 최종 구현 결과물

OS 아키텍처 (3계층)

1. 저장소 계층 (Storage Layer) — 옵시디언 볼트
    - `1_inbox` (수집) / `2_places` (장소 데이터) / `3_carousels` (캐러셀) / `4_published` (발행 완료) / `_attachments` (자원)
    - 장소 노트 프로퍼티에 `verified: false` 필드 도입 → 검증된 정보와 추측 정보 분리
2. 처리 계층 (Processing Layer) — Claude 채팅 + 웹클리퍼
    - 외부 정보(블로그, 매거진)는 Web Clipper로 자동 수집
    - 크롤링 차단된 네이버 지도는 캡처 → AI 인식으로 우회
    - Claude가 정보를 검증하고 옵시디언 노트로 정리
3. 출력 계층 (Output Layer) — 캐러셀 스튜디오 v5 (HTML 단일 파일)
    - 8장 슬라이드 자동 생성 (표지/지도/장소3/코스/팁/마무리)
    - 1080×1350 PNG 일괄 다운로드
    - 인스타/스레드/링크드인 캡션 자동 생성

핵심 OS 원칙들

- 단일 진실 공급원(Single Source of Truth): `places` 배열 하나가 지도, 장소 슬라이드, 코스, 캡션 모두의 소스. 한 곳 수정하면 모든 슬라이드 자동 동기화
- 콘텐츠와 도구의 분리: 편집툴 UI는 고정 톤, 결과물은 5개 프리셋 + 커스텀 + 사진 자동 색 추출로 콘텐츠마다 다른 무드
- 검증 가능성: 추측 정보는 절대 콘텐츠로 변환하지 않는 강제 규칙

### 과정 (타임라인별 + 삽질)

Day 1: 도구 탐색

- 옵시디언 + Claude로 업무 자동화 목표 설정
- Web Clipper 도입 → 보안 우려 검토 후 안전성 확인
- 폴더 구조와 템플릿 설계 시작

Day 2: 캐러셀 도구 1차 시안

- 참고 블로그(editor_dongwon)의 "한 줄이 중요해진 세상" 인사이트 흡수
- 첫 캐러셀 시안 제작 (SVG)
- 🚨 삽질 1: 정사각형 비율(1:1)로 잘못 만듦 → 인스타 표준은 4:5(1080×1350)

Day 3-4: HTML 풀버전 개발 (v2 → v5)

- v2: 편집툴 UI와 결과물 톤 분리, 5개 테마 + 사진 자동 색 추출
- v3: 인트로를 지도로 교체, 더블클릭 업로드 추가
- v4: 동선 자동 최단경로 정렬 (브루트포스 알고리즘)
- v5: 데이터 구조 통합 — places 배열 하나로 모든 슬라이드 동기화

🚨 삽질 2: AI 추측의 위험성

- 카페 소보네르 정보를 Claude가 추측으로 채움 → 검증 안 된 정보로 콘텐츠 만들면 신뢰도 무너짐을 깨달음
- → `verified` 필드와 `status: 방문전/방문완료` 규칙 도입

🚨 삽질 3: 네이버 지도 크롤링 차단

- web_fetch로 네이버 지도 접근 시도 → robots.txt에 차단
- → "스크린샷 + AI 인식" 우회 패턴 확립

🚨 삽질 4: 동선 무시 문제

- 처음엔 마커가 입력 순서대로만 연결됨 → 실제 동선과 무관
- → 모든 순열을 평가하는 브루트포스 + 드래그로 수동 조정 가능한 하이브리드 구조

🚨 삽질 5: 데이터 일관성 실종

- v4까지는 지도 마커, 장소 슬라이드, 코스 슬라이드가 서로 따로 놀음
- 동선 바꿔도 장소 소개 순서는 그대로 → 콘텐츠 흐름 깨짐
- → v5에서 데이터 구조 자체를 통합. "한 곳 수정 → 전체 동기화" 원칙 확립

### 공유할만한 인사이트

1. "OS"의 핵심은 데이터 구조다

도구는 결국 데이터를 어떻게 흘리느냐의 문제다.

v2~v4는 기능을 늘리는 방향이었지만, v5에서 데이터 구조 자체를 재설계한 것이 가장 큰 도약이었다.

새 기능을 추가하기 전에 "이 데이터가 어디에 살아야 하는가"부터 물어야 한다.

2. AI의 가장 큰 위험은 "그럴듯한 추측"

Claude가 가본 적 없는 카페의 분위기를 그럴듯하게 묘사한 사건은, 콘텐츠 제작자에게 치명적인 위험이었다.

검증 가능성을 데이터 구조에 박아두지 않으면(verified 필드처럼), AI는 언제든 환각으로 채널을 무너뜨릴 수 있다.

3. AI는 "발견" 아닌 "구조화"에 강하다

네이버 지도 크롤링이 막혀 있어도 문제없었다.

정보 발견은 사람이 하고, 캡처를 던지면 AI가 구조화해주는 패턴이 가장 안정적이었다.

수집은 사람, 정리는 AI — 이 역할 분담이 핵심.

4. 좋은 도구는 "수정 가능성"으로 평가된다

완성품보다 중요한 건 "쉽게 고칠 수 있는가"다.

v5가 좋은 이유는 화려해서가 아니라, 다음 콘텐츠를 만들 때 places 배열만 갈아끼우면 끝나기 때문이다.

### 최종 구현 결과물

### 과정 (타임라인별 + 삽질)

기획 단계

- 참고 블로그에서 후킹 라인 공식 도출: "감정/관점(짧게) + 구체 대상(크게)"
- 5개 후보 중 시의성 있는 "5월 완도, 지금 가야 하는 이유 3가지" 선택

제작 단계

- 옵시디언 장소 노트 3개 작성 (소 보네르는 `verified: false` 상태로 기록)
- 캐러셀 스튜디오 v5에서 데이터 입력
- 동선 자동 최적화 → 박람회 → 식당 → 카페 순서 확정
- "흙·모래" 톤 프리셋 적용 (자연 친화적 무드)

🚨 삽질 1: 추측으로 채운 후킹

- 처음엔 카페 정보를 Claude가 추측으로 채움 → "오션뷰 통창" 같은 키워드가 검증 안 됨
- 네이버 지도 캡처로 실제 정보 확인 필요 → 실제 방문 전까지는 빈 칸으로 두는 규칙 도입

🚨 삽질 2: 디자인 시스템이 콘텐츠를 잡아먹음

- 편집툴이 흙색이면 결과물도 자동으로 흙색 → 다른 주제 콘텐츠는 어쩌지?
- 편집툴 UI와 결과물 톤을 코드 레벨에서 분리

### 공유할만한 인사이트

1. "한 줄"이 콘텐츠의 8할

참고 블로그가 알려준 진리.

같은 콘텐츠도 후킹 한 줄에 따라 조회수가 5만 vs 100만으로 갈린다.

표지 후킹은 콘텐츠 제작의 시작이지 끝이 아니다.

후킹 라인을 먼저 정하고 거기에 맞는 장소를 큐레이션하는 역방향 워크플로우가 훨씬 효과적이다.

2. 캐러셀은 "찐팬 제조기"

릴스가 빠르게 터지는 콘텐츠라면, 게시물(캐러셀)은 저장·재방문률이 높아 팔로워의 충성도를 만든다.

알고리즘 노출보다 저장 가치가 있는 정보 밀도가 핵심.

3. 톤은 콘텐츠를 따라가야 한다

캐러셀 5장 = 5가지 무드가 필요할 수도 있다.

도구의 디자인 시스템이 콘텐츠를 종속시키면 그 도구는 한 가지 톤의 채널만 운영 가능하다.

편집툴과 결과물의 분리가 1인 콘텐츠 제작 도구의 핵심 설계 원칙이다.
