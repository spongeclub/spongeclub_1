# Personal OS 구현 사례 — 암묵지를 시스템으로 만드는 과정

> honey-curator 프로젝트(2026-05)를 중심으로

---

## 1. 왜 "운영체제"인가

"Personal OS"라는 표현은 비유가 아니라 정확한 정의다.

운영체제는 자원을 관리하고, 인터럽트에 응답하고, 프로세스를 스케줄링한다. honey-curator가 하는 일이 정확히 그것이다. 주의(attention)라는 희소 자원을 관리하고, 텔레그램 메시지라는 인터럽트에 라우팅 규칙으로 응답하고, 큐레이션을 매주 월요일 9:03에 스케줄링한다.

차이는 컴퓨터 OS는 CPU를 위한 것이고, 이 시스템은 코니라는 사람의 인지 자원을 위한 것이라는 점이다.

---

## 2. 암묵지(tacit knowledge)란 무엇이었나

마이클 폴라니(Michael Polanyi)는 "우리는 말할 수 있는 것보다 더 많이 안다(We know more than we can tell)"고 했다. 암묵지는 명시화하기 어려운 지식이다 — 경험, 직관, 취향, 판단 기준.

이 프로젝트에서 코니의 암묵지는 다음과 같았다:

- "왜 이 링크를 저장했는가" — 링크를 클릭하는 순간의 끌림
- "이 정보가 내게 어떤 의미인가" — 카드에 한 줄로 표현되는 관점
- "무엇이 반복되는 관심사인가" — 패턴으로만 보이는 자기 사고의 지도

이것들은 저장 행위 자체에 이미 담겨 있었다. 시스템이 하는 일은 그 행위에서 암묵지를 꺼내 물어보는 것이다.

---

## 3. 시스템 설계에서 표면화된 암묵지 5가지

### 3-1. 자동화 대상 선별의 원칙

**암묵적 판단**: "큐레이션을 전부 AI에게 맡기면 안 된다."

이 판단은 처음에 명시되지 않았다. 그러나 설계 과정에서 자연스럽게 구현된 구조가 그것을 드러냈다. 수집(tip-collector), 분류, 초안 생성은 완전 자동화됐지만, 최종 선별은 코니의 "OK" 한 마디가 필요하다.

**표면화된 원칙**: 자동화 가능 여부는 "반복적인가"가 아니라 "이 순간에 내 맥락이 필요한가"로 결정된다.

처리(processing)는 시스템이, 판단(judgment)은 사람이. 이 경계가 Personal OS의 핵심 설계 원리다.

### 3-2. 상태 저장 위치의 선택

**암묵적 판단**: "시스템의 상태는 내가 볼 수 있는 곳에 있어야 한다."

큐레이션 세션 상태(대기/승인/만료)를 파일시스템에 저장하는 것이 기술적으로 더 빠르지만, 노션 DB를 선택했다. 이유는 명시적으로 설명되지 않았으나 결과적으로 드러난 것은 신뢰의 조건이다.

**표면화된 원칙**: 블랙박스 상태는 신뢰를 만들지 못한다. Personal OS는 사용자가 언제든 시스템의 현재 상태를 직접 확인할 수 있어야 지속된다.

부수 효과로 이식성이 확보됐다. Phase 2에서 인프라가 교체되어도 노션 DB 스키마는 유지된다.

### 3-3. 승인 흐름의 마찰 설계

**암묵적 판단**: "확인 절차가 번거로우면 시스템을 안 쓰게 된다."

대안은 노션 DB에 직접 들어가서 수정하는 방식이었다. 그러나 최종 구현은 텔레그램 채팅창에서 "OK" 한 단어로 전체 승인이 완료되도록 했다.

실전 테스트에서 확인된 것: "체크표시로 그냥 대충 알아들으면 안돼?" — 정확한 명령어가 아니어도 의도를 파악하도록 시스템이 유연하게 반응했다.

**표면화된 원칙**: 승인 UI의 목적은 정확한 입력을 받는 것이 아니라 사용자의 인지 부하를 최소화하는 것이다. 마찰이 낮을수록 시스템이 유지된다.

### 3-4. 암묵지를 묻는 시스템이 암묵지를 다룬다

**암묵적 판단**: "스크랩 행위 자체가 내 관심사의 표현이다."

honey-curator v2에서 추가된 `저장 동기` 필드는 단순 기능 추가가 아니다. "왜 저장했는가"를 물음으로써 시스템이 코니에게 자기 자신을 거울로 보여준다(단계 3.5: 미니 거울).

이것은 Polanyi의 암묵지 개념의 직접적 적용이다. 저장 행위에 내재된 암묵지를 "왜 저장했어요?" 한 질문으로 표면화한다. 시스템이 계속 축적되면 패턴 태그 데이터는 코니의 사고 지도(map of mind)가 된다.

**표면화된 원칙**: Personal OS의 가치는 효율 향상만이 아니다. 자기 사고 패턴을 관찰 가능하게 만드는 것도 핵심 기능이다.

### 3-5. 점진적 이식 가능성의 보존

**암묵적 판단**: "완벽한 인프라보다 빠른 검증이 먼저다."

Phase 1은 Claude Code 세션이 켜져 있어야 작동하는 구조다. 서버가 없다. 그럼에도 Phase 1을 먼저 구현하고 테스트한 이유는 명시되지 않았지만, 설계에 이미 담겨 있었다: 노션 DB 스키마, 라우팅 로직, 프롬프트는 Phase 2에서도 그대로 유지된다.

**표면화된 원칙**: Personal OS의 각 Phase는 독립적으로 가치를 만들면서 인터페이스를 보존해야 한다. "완성"이 목표가 아니라 "지금 작동하는 것"이 목표다.

## 4. 이 접근이 "Personal OS"에 부합하는 이유

OS 비유가 성립하려면 세 가지 조건이 필요하다:

**1. 인터럽트 처리 (interrupt handling)**
텔레그램 메시지가 들어오면 라우팅 규칙에 따라 세 가지 프로세스(tip-collector / honey-curator / tip-oracle) 중 하나가 실행된다. 메시지의 성격(URL 포함 여부, 대기 세션 존재 여부)이 인터럽트 벡터 역할을 한다.

**2. 스케줄링 (scheduling)**
매주 월요일 9:03 자동 큐레이션, 화요일 11:07 catch-up. 주기적 프로세스가 사람의 개입 없이 실행된다.

**3. 상태 관리 (state management)**
큐레이션 세션(대기/승인/만료)이 노션 DB에 영속된다. 세션이 끊겨도 상태는 유지된다.

세 조건이 모두 충족된다.

---

## 5. 남은 과제

이 시스템이 완성이 아닌 이유도 드러났다:

- **의존성 문제**: Claude Code PC 세션에 묶여 있다. Phase 2(Node.js + Vercel)로 이식하면 해소된다.
- **피드백 루프 부재**: 저장한 카드가 실제로 얼마나 참조되는지 추적하지 않는다. tip-oracle 사용 로그가 쌓이면 "어떤 카드가 살아있는 지식인가"를 알 수 있다.
- **망각 처리**: 오래된 카드의 가중치를 낮추는 메커니즘이 없다. 지식 반감기(knowledge half-life) 개념을 적용하면 카드 DB가 살아있는 시스템이 된다.

---

## 6. 결론

> "Personal OS는 업무 자동화 시스템이 아니라, 자기 자신을 관찰하고 신뢰하는 인프라다."

honey-curator 프로젝트가 보여주는 것은 기술이 아니다. 어떤 판단은 사람이 해야 하고 어떤 처리는 시스템이 해야 하는지를 구분하는 능력, 마찰을 설계하는 감각, 자신의 행위 패턴을 시스템이 거울처럼 보여줄 때 그것을 읽는 태도 — 이것들이 Personal OS를 만드는 사람에게 필요한 것이다.

기술은 도구다. 암묵지를 표면화하려는 의지가 먼저다.
