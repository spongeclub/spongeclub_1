웹사이트가 아니라 내 흐름을 굴리는 로컬 OS로 재정의하기

2026-05-12부터 2026-05-17까지 Yulia 프로젝트는 Telegram bot/Next.js site에서 local-first OS runtime으로 방향을 틀었다. 핵심은 interface, control, execution, memory를 분리하고, 매일 돌릴 수 있는 흐름으로 만드는 일이었다.

Period: 2026-05-12 - 2026-05-17 Source: yulia repo docs, git history, current working diff Output: flow diagram + implementation narrative

최종 흐름도

예시 그림처럼 중앙에 Yulia OS runtime을 두고, 왼쪽에는 입력과 작업 신호, 오른쪽에는 실제로 사람이 만나는 채널과 산출물을 배치했다.

내가 만든 구조

Interface Plane

말을 걸고 결과를 보는 곳

Telegram은 개인 DM, Discord는 운영 알림, CLI는 로컬 실행, Obsidian은 memory를 읽는 창이다.

Control Plane

상태를 잡아두는 곳

Paperclip은 issue, routine, owner, approval을 맡는다. 기억 저장소나 brain으로 쓰지 않는다.

Execution Plane

실제로 일을 하는 곳

Hermes worker가 Paperclip issue를 읽고, Gemini CLI와 npm scripts가 distill, batch, report 작업을 실행한다.

Memory Plane

오래 남기는 곳

raw, source, distilled Markdown이 기억의 본체다. Obsidian으로 읽고, graphify와 Yulia reply의 입력으로 쓴다.

데이터가 흐르는 방식

0512-0517 작업 타임라인

2026-05-12

처음에는 Next.js, Vercel, DB, Telegram bot을 묶은 사이트형 서비스로 보았지만, 개인 OS에는 배포된 웹앱보다 로컬 루프와 Markdown memory가 더 중요하다고 판단했다.

공유할 만한 인사이트

OS는 화면보다 흐름이다

이번 작업에서 OS를 만든다는 건 UI 하나를 만드는 일이 아니라 interface/control/execution/memory plane을 나누는 일에 가깝다는 걸 확인했다.

작업 상태와 기억은 다르다

Paperclip을 brain으로 쓰면 기억이 흐려진다. 상태는 Paperclip, 장기 기억은 Markdown/Obsidian, 실행은 Gemini CLI로 나누는 편이 오래 간다.

매일 돌릴 수 있어야 한다

로컬 OS에서는 “배포 가능한가”보다 “내가 매일 실제로 돌릴 수 있는가”가 더 중요한 성공 기준이었다.
