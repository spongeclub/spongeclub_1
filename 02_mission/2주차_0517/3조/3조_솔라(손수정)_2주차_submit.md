# 2주차 과제 — 솔라

## 미션1: 각자만의 정의로 [운영체제]라고 정의내리는 OS 구현

### Summary
스폰지타임즈 MVP 캐러셀 디자인을 반자동 생성하는 OS를 구현했다.
캔바나 디자인 툴을 다루는 능력은 없어서, 매번 직접 만들게되면 주 1회 이상 발행이 힘들 것 같기에 매 주 정기 발행하는 'MVP콘텐츠'먼저 캐러샐 생성기 앱을 먼저 만들었다. 

운영체제로서의 정의: **"콘텐츠만 채우면 시각적 일관성이 자동으로 유지되는 시스템"**. 디자인 결정을 매번 다시 하지 않도록 컬러·타이포·캐릭터·슬라이드 시퀀스를 모두 룰로 박아두고, 코드는 그 룰을 실행하는 역할만 맡긴다.

### 최종 구현 결과물
**1) 룰북 (5개 md 문서)**

- `00-design-system.md` — 공통 디자인 토큰. 컬러 팔레트, Pretendard 타이포 스케일, 절대 원칙(다크카드 남용 금지, 형광펜 슬라이드당 1~2개 등)
- `01-cover.md` — 표지 슬라이드 OS
- `02-body.md` — 본문 슬라이드 OS, 콘텐츠 유형 4종별 명세
- `03-cta.md` — CTA 슬라이드 OS, AI 질문 생성 룰
- `04-character-prompt.md` — 캐릭터 AI 프롬프트 생성 로직

**2) 웹앱 (Vite + React 18 + TypeScript)**

- 입력 폼 → 미리보기 → PNG/MP4 추출 → ZIP 묶음 다운로드까지 원스톱
- 영속화: 폼 데이터는 localStorage, 영상 파일은 IndexedDB(용량 때문에 분리)
- 캐릭터 프롬프트 빌더: 입력값에 따라 영문 프롬프트 자동 생성 → 복사 → 이미지 생성 AI에 붙여넣기 → 생성된 이미지 수동 누끼 → 캐릭터 PNG 업로드하면 슬라이드 자동 배치

![259](attachments/Pasted%20image%2020260515164554.png)

**3) MVP 캐러셀 표준 구조**

표지(풀배경) → 본문 N장(카드 레이아웃) → CTA(질문 + 캐릭터 멘트 + 팔로우 카드). 콘텐츠 유형에 따라 슬라이드 수는 고정(10장) 또는 유동(≤10장).

### 과정 (타임라인별 + 삽질)
**1단계: 규칙을 먼저 글로 적고, 코드는 나중에**

처음엔 디자인에 대한 생각도, 어떤 종류의 캐러셀을 만들지도 추상적으로 머릿속에만 존재했다. 그래서 우선 다니의 STIC 프롬프트를 스폰지타임즈의 입장으로 조금 수정 + ask your question 스킬로 대화를 나눈 뒤 필요 항목을 정리했다. 이번 주차에 캐러셀을 발행했어야 했기 때문에, 그대로 그 채팅방에서 말을 이어나갔다.

처음엔 바로 작업에 돌입하려고 했지만, 대화를 나누다보니 선택할 사항이 많아지고, 채팅방에서 진행하기에는 한계가 있다고 느꼈다. 그레서 웹앱을 만들기로 결심했다.
그래서 컬러·폰트·간격·콘텐츠 종류 같은 걸 클로드와 함께 결정하고, md 문서로 정리했다.

**2단계: 웹앱 구현 시작**

**2-1단계: 표지 제작**

클로드 채팅에서 가져온 md 파일을 가지고 클로드 코드로 넘어와 웹앱 구현을 시작했다. 처음엔 모든 유형의 발행물을 한번에 구현하고 싶었지만, 컨텐츠마다 성격도 너무 다르고 그렇게 하면 너무 복잡해 질 것 같아 우선 이번 주에 발행하기로 결정한 'MVP 캐러셀'생성기 웹앱만 만들기로 결정했다.

스폰지 크루들과 스폰지타임즈 발행물의 구분을 위해 타임즈 발행물은 커버 디자인을 통일하기로 하여 커버 부분에서 많은 시간을 소요했는데, 이때 중요했던 부분이 스폰지타임즈의 캐릭터를 표지에 크게 배치하는 것이었다. 이 때는 다니의 캐러셀 공유회를 안 들었던 상태라 API를 연결하지 못해서 대신 프롬프트 자동생성기를 한 켠에 마련했다. 원하는 행동을 입력하면 자동으로 프롬프트가 나오게되는,, 사실 따로 다른 곳에서 프롬프트를 생성해도 되지만 그 수고로움을 조금이나마 덜어낼 수 있지 않을까 라는 생각으로 제작하게 되었다.

[클로드의 말]
영문 프롬프트 자체를 룰화하고, 웹앱이 입력값을 받아 프롬프트를 자동 조립하게 만들었다. 일관성은 프롬프트의 고정 부분(외형/스타일 디스크립터)이 담당한다. AI 결과물의 흔들림을 프롬프트 표준화로 잡는 접근이다.

**2-2단계: 본문 제작**

본문을 제작하는 과정에서 여러가지 문제점이 있었다.
1. 이미지를 그냥 넣기에는 심심함
2. 이미지가 여러개인 크루도 있음
3. 1주차는 미션이 2개라서 미션 2개를 보여줘야 하는 경우도 있음

그래서 이 부분을 보완하기 위해 클로드코드와 논의를 하다가,
**이미지가 여러 장 일때는 디졸브 기능을 넣고 디졸브 타임도 조절할 수 있게 한다.**
**미션이 여러 개일 경우 또한 디졸브 처리, 속도 조절 기능 추가**
이렇게 추가했고, 이 과정에서 캐러셀들이 거의 MP4 형식으로 뽑혀야 해서 그 기능도 추가 했다. (생각해보니 아직 동영상+이미지 조합은 해보지 않았다)

**2-2단계 삽질: preview tool로 사용자 데이터가 날아간 사건** [클코입장]

가장 아팠던 부분. Claude Code의 미리보기로 자동 클릭/주입 테스트를 했더니 미리보기에서 상태를 바꾸자 사용자 작업분이 덮어 씌워졌다. 문제는 이거였다. 미리보기 도구가 띄우는 브라우저랑 사용자가 쓰는 브라우저가 **같은 저장 공간(localStorage)을 공유**하고 있었던 거다. 두 차례 데이터 손실이 있었다.

이후 안전 규칙을 명문화했다:(솔라 : 서로 타협했다. 그 이후 클코가 뭘 바꿀때마다 더 조심히 물어본다.)
- 미리보기는 **읽기 전용**(화면 캡처, 콘솔 확인 정도)으로만 쓴다
- 사용자가 폼에 뭔가 입력 중일 때는 핵심 코드 수정을 안 한다. 코드가 바뀌면 화면이 새로고침되면서 **아직 저장 안 된 입력이 다 날아가기** 때문
- 꼭 수정해야 하면 사용자가 작업 마칠 때까지 기다리고 → 백업 받아두고 → 그 다음에 고친다

사실 매번 디자인이 완료되면 로컬에 파일로 저장하긴했지만, 나중에도 참고하고싶어서 데이터가 날아가는건 원치 않았다. 그래서 이 과정에서 백업 내보내기/가져오기 버튼을 만들었다(json 파일/영상은 저장 안되는 한계)

**3단계 : 진행중인 사항**

로컬에만 저장하는 한계가 싫었고, 웹으로도 배포하고 싶어서 다니가 알려준  superbase로 연결하고 있다. 그리고 로그인 방식을 솔라/스폰지타임즈 크루/스폰지 크루 세 부류로 분리해서, 스폰지 크루들도 캐러셀 웹을 다뤄볼 수 있게 만드는 것이 최종 목표이다.

또한 한 웹에서 모든 캐러샐을 생성하고 싶어서 나중에 다른 캐러셀 생성기를 합치기 용이하도록 이를 사전에 언급했고, 클코가 파일을 따로 분리?해서 코드를 짰다고한다.

2. 아직 내용을 채우는 스킬은 따로 만들지 않아서 주어진 자료를 바탕으로 내용을 채워주는 기능을 추가하고 싶다.

### 공유할만한 인사이트
**1) 자동화의 진짜 가치는 "작업 시간 절약"이 아니라 "결정 횟수 절약"이다**

이 OS의 진짜 가치는 매번 "다크 카드 써도 될까? 형광펜 몇 개까지?"를 고민하지 않게 된 것이다. 디자인 토큰 + 절대 원칙이 그 결정을 미리 박아뒀다. 시간 절약보다 **인지 부담 절약**이 본질이었다. 작업 시간만 보면 자동화의 효용이 작아 보이지만, 매번 같은 고민을 안 해도 된다는 점이 훨씬 크다.
다음 주에는 MVP 캐러셀은 하루 컷 하고 다른 캐러셀 생성기를 만드는 것이 목표.
끝나기 전에 주 3회 발행 할 수 있음 좋겠다.

**2) AI 도구의 동시성 함정 — origin 공유는 데이터 공유다**

Claude Code preview tool이 자체 브라우저를 띄우지만 같은 localStorage를 공유한다는 사실을 모르고 자동 클릭을 시켰다가 데이터를 두 번 날렸다. AI 에이전트와 사용자가 같은 영속화 레이어를 쓰는 환경에서는 **읽기/쓰기 권한 분리**가 안전 규칙 1번이어야 한다. "AI가 자동으로 해줄 수 있는 일"과 "AI에게 시키면 안 되는 일"의 선을 미리 그어둬야 사고가 안 난다.
→ 이점은 초반에 분리할 수 있는가? 한 번 물어봐야겠다. 매번 나에게 물어보는게 귀찮다.
