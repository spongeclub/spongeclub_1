### 🔍 적용 가능성 분석

#### 이미 갖춰진 것 (바로 활용 가능)

| 항목 | 설명 |
|------|------|
| 제출 감지 데이터 | 미션 파일 frontmatter `submitted: true/false` 이미 존재. 조별 집계 바로 가능 |
| 멤버 목록 | `99_meta/멤버목록.md`에 조별 인원·닉네임 정리됨 (1~4조 13명, 5조 12명, 6조 13명 = 77명) |
| 파일 구조 | `02_mission/{주차}/{조}/{조_닉네임_주차_submit.md}` 패턴이 일관됨 |

#### 구현 시 주의사항

| 항목 | 내용 |
|------|------|
| cron 시간대 | GitHub Actions cron은 UTC 기준. KST 목요일 오후 7시 = UTC 목요일 오전 10시 (`0 10 * * 4`) |
| 멤버목록 파싱 | 마크다운 리스트 형식(`- 닉네임(본명)`) → 정규식 파싱 필요. `## N조` 헤더로 분할 |
| 채널 매핑 | 조 번호 → 슬랙 채널 ID 매핑 테이블 필요 (설정 파일로 관리) |
| 실시간 알림(F) 방식 | 방법A: `on: push` 트리거 / 방법B: 제출 워크플로우 내장 — B가 더 정확하고 지연 적음 |

#### 현재 구조와 안 맞는 부분

| 설계 초안 | 실제 레포 | 조치 |
|-----------|----------|------|
| SNS 제출 감지 | SNS 관련 파일/frontmatter 없음 | ⚠️ 가장 큰 블로커 — SNS 트래킹 구조 먼저 정해야 Phase 3 진행 가능 |
| 집짓기 성장 단계 데이터 | 저장소 없음 | 조별 현재 단계를 기록할 파일 필요 (예: `92_status/growth.json`) |
